## Problem Statement

HimaHarness 已能围绕 HimaPack、Campaign、Site 和 Resident Agent 开展受控工程工作，但用户希望把它用于更广泛、需要多角色长期配合的问题：从 GitHub Issue 完成开发、测试和审查；从 idea、访谈与产品材料形成可信的 functional spec；在既有 Campaign 的某个环节委派团队协作。

用户已明确公司级产品承载协议：不同产品和芯片设计业务将以 HimaHarness 为共同承载平台，通过它组织能力、编排工作并交付工程 Pack。用户描述已有约 3–4 类业务初步跑通，下一步关心的是新增业务能否复用已有能力，以及架构是否具备与主流 Harness/Agent 平台相符的扩展方向；这一描述不代表所有业务均已完成独立验收。公司级定位不自动引入中央共享服务、多租户或集群，也不要求架构从此不再变化。

单个 Agent 或一次性 subagent 无法充分表达用户需要培养的团队：每位成员应有独立上下文、职责和长期身份，经验可以积累，配合方式可以改进，人类能在固定工作空间里查看任务与成员的实际工作、选择接收人追加指令并介入。用户不应充当成员之间的消息转发器，也不能只能在后台执行结束后得到一段无法核查的汇报。

当前实现仍以 Pack/Campaign 为主要执行入口。既有 Agent Team 面板主要呈现 Campaign 子任务委派，并不等于可独立使用的持久 HimaTeam。新增能力必须复用既有可靠执行与工程能力，同时解决独立任务身份、混合运行时接入、可靠的成员通信、记忆范围和统一安装交付。

产品讨论还需要直接把文件附加到目标或追加指令。只有 GitHub 工作目录、路径输入或上传控件不够：用户需要知道文件是否保存、内容是否可读，成员的判断依据来自哪里，以及哪些内容只是本次讨论材料、哪些已经成为可复用经验。

用户要求保持架构简单。开源组件的引入应减少自研与重复系统，不能使团队功能变成另一套调度平台，也不能将部署多个服务、维护运行环境的负担留给普通用户。

## Solution

在 HimaHarness 中建设 HimaTeam：一项可定义、复用、编排、管理并持续改进的 Agent 团队协作能力。团队入口与 Campaign、Data Insight 同级，但能力不受页面限制；Guide、普通会话、讨论项目、Campaign 和 Fabric 节点均可使用同一团队机制。

平台既接入模型，也组织拥有原生工具、上下文和执行能力的完整 Agent。HimaTeam 用于需要多种专业上下文、持续交接和共同判断的工作；其价值是扩大可交付的业务能力，并积累可复用的团队方法与经验。新增业务优先通过 Pack、Skills、工具适配、领域验证和必要视图接入；只有真实消费者证明通用合同有缺口时才修改平台内核。单 Agent 足够的工作继续使用单 Resident，团队能力不成为所有 Pack 的必经层。

用户可以通过对话描述阵型，选择成员的 coding CLI、模型、Skills、职责、材料和协作关系，保存成可版本管理的团队定义。团队拥有固定工作空间，每件工作有自己的任务空间。人类和真实成员可以交流、交接、复核和纠正，成员在授权范围内自主推进。

首期使用已选 OAR、Pi、OpenCode、按兼容性需要升级的 DeepSeek Harness 和 Hindsight，并保留既有 Hima Host、HimaFabric、DBOS、数据库和资产能力。Agent 间通信由既有 Host 职责内的最小持久消息机制承接，不引入聊天服务器或新 UI 库。macOS、Linux 均须完整安装并在本机工作；macOS 可按 Hindsight 服务或执行隔离的独立需要携带受管 Linux 虚拟运行环境，移除 Zulip 不自动移除这些需要。用户无需另外部署服务器或安装 Docker。

**首期必须交付的用户场景：**

| 场景 | 用户操作与工作过程 | 可验收交付 |
| --- | --- | --- |
| GitHub 开发测试 | 用户给出 Issue、仓库和边界；混编团队开发、测试、独立审查、退回修正 | 对应明确提交的 PR、测试证据、评审结论和剩余问题 |
| Estack 式产品定义（以知识研究推动产品创新的方法） | 用户附加文档与 idea；团队研究取证、提出方案、反证、修订 | 说明价值、产品影响、行为、边界和验收的 functional spec，保留来源及未知 |
| Campaign/Fabric 委派 | 已有业务提供角色要求、上下文、输入和交付合同；一个节点可委派完整团队工作 | 经原任务合同验收的结果与产物，外层流程据实接续 |
| 直接讨论与人类介入 | 用户在会话中创建或调用团队，附加材料、选择成员追加指令、纠正、批准、暂停、停止或恢复 | 可追溯的讨论与决定，按需形成明确任务，不强制先创建 Pack/Campaign |
| 后续使用 | 用户重新调用已培养的团队，或复制其定义创建新团队 | 前者保留有权使用的成员经验，后者不默认复制私人记忆和项目历史 |

**目标操作路径：** 安装并检查组件 → 配置模型及工作授权 → 在 Guide 或团队入口创建团队 → 查看并保存定义 → 进入任务与成员总览 → 提供目标与附件 → 查看成员实际输入、输出、工具轨迹和结果 → 选择接收人追加指令或进行审批/控制 → 查看代码、测试或规格成果 → 在后续任务中使用可追溯经验。Campaign 调用团队时，从原业务进入对应任务并能返回，无需在团队入口重复建任务。

现有 Guide、Campaign/Fabric、Data Insight、单 Resident Agent、Pack/Site 和资产操作继续成立。Guide 派工后保持可交互；用户无需了解 OAR、DBOS 或记忆 bank 才能完成工作。界面具体按钮命名是实施设计，不能用本规格的操作说明冒充已实现 UI。

## User Stories

以下按“作为某类使用者，我希望具备某项能力，以便获得相应收益”的结构记录用户故事。保留 1–88 的追踪编号；89–92 补充共同业务承载、组件组合与真实交接要求。

1. 作为 macOS 用户，我希望安装 HimaHarness 后能在本机使用完整团队能力，以便不必准备 Linux 服务器。
2. 作为 Linux 用户，我希望同一产品提供可安装的完整团队环境，以便在办公服务器或工作站运行团队。
3. 作为普通用户，我希望安装包配齐所选组件和 Pi/OpenCode 等运行依赖，以便无需分别安装多个平台。
4. 作为 Mac 用户，我希望 Hima 管理随包运行环境的启动、退出和数据，以便不必自行维护 Docker 或虚拟机。
5. 作为使用自部署模型的用户，我希望配置服务地址、模型和 API key，以便使用办公网络中已获准的模型。
6. 作为团队配置者，我希望不同成员使用不同模型与凭据，以便不受 Guide 默认模型配置限制。
7. 作为用户，我希望看到组件就绪、故障及需要处理的配置，以便能够实际完成首次启动。
8. 作为用户，我希望凭据与可分享的团队定义分开保存，以便复用定义时不会泄露密钥。
9. 作为用户，我希望用对话描述团队阵型，以便不必手写配置才能开始。
10. 作为团队管理者，我希望查看和编辑成员职责、Skills、工具、知识范围及交付要求，以便知道每位成员负责什么。
11. 作为团队管理者，我希望在同一团队混用 Pi 和 OpenCode，以便为不同职责选择合适运行时。
12. 作为团队管理者，我希望负责人也可以使用 Pi 或 OpenCode，以便负责人的业务角色不被某个运行时绑定。
13. 作为用户，我希望保存和版本管理团队定义，以便在之后的工作中重复使用。
14. 作为项目维护者，我希望能导出团队定义或纳入项目 Git，以便审阅与追溯阵型变化。
15. 作为用户，我希望成员身份和经验不随会话结束而消失，以便持续培养团队。
16. 作为用户，我希望更换成员模型或运行时后仍保留其身份和获准经验，以便升级工具时不丢失培养成果。
17. 作为用户，我希望将新任务交给现有团队，以便复用其已经积累的方法和经验。
18. 作为用户，我希望按定义创建新团队时得到独立成员和工作空间，以便复用阵型而不默认复制私人记忆。
19. 作为用户，我希望看到复制团队时携带的通用方法与资料，以便明确选择允许复用的内容。
20. 作为执行中的用户，我希望团队定义修改默认只影响新任务，以便当前工作不会被悄悄改变。
21. 作为执行中的用户，我希望能明确将修改应用到当前任务并完成交接，以便必要调整不必丢弃全部工作。
22. 作为 Guide 用户，我希望从现有对话创建或调用团队，以便不必先切换到专门页面配置。
23. 作为 Guide 用户，我希望委派后 Guide 仍能响应其他问题，以便团队执行不占住我的管家会话。
24. 作为普通讨论参与者，我希望不创建 Pack 或芯片设计 Campaign 就能使用团队，以便讨论产品和一般工程问题。
25. 作为 Campaign 使用者，我希望业务流程可以调用团队并提供上下文，以便成员不需要我重新解释全部背景。
26. 作为 Pack 作者，我希望流程节点能委派一项团队工作，以便在固定外层流程中使用灵活协作。
27. 作为 Campaign 使用者，我希望团队成果通过原节点验收后再接续，以便成员的完成声明不替代业务判断。
28. 作为用户，我希望单 Resident Agent 足够时仍可直接使用它，以便简单工作不被强制组织成团队。
29. 作为用户，我希望串行协作也能保留成员职责与经验，以便团队不以并行数量定义。
30. 作为用户，我希望团队入口和 Campaign、Data Insight 同级且相互可导航，以便在一个 HimaHarness 中完成工作。
31. 作为团队参与者，我希望有跨任务保留的团队工作区和任务/成员总览，以便持续与同一支团队协作。
32. 作为团队参与者，我希望每件工作有独立任务身份、目标、材料、成员工作和交付入口，以便多个任务的上下文不混在一起。
33. 作为用户，我希望成员详情显示实际观察到的输入、输出、工具调用/结果、阻塞与交接，以便了解他们如何得出结论；不可见或缺失的记录如实标明。
34. 作为用户，我希望点击任务或成果引用能查看实际记录和产物，以便核查进展，而不是只看摘要。
35. 作为用户，我希望在当前任务中选择成员作为接收人、追加指令并附加材料，以便无需负责人逐条转述职责范围内的要求。
36. 作为成员，我希望能向同伴提问、交接产物和请求复核，以便自主完成协作。
37. 作为负责人，我希望能在契约内增加调查、退回研究和重新分工，以便根据证据调整工作。
38. 作为用户，我希望普通进度和记录更新不触发全员重复回答，以便协作不消耗无关上下文。
39. 作为用户，我希望将讨论或研究交给明确参与的成员并约定收束条件，以便得到多角色判断而无需群聊或工程工作流。
40. 作为产品讨论参与者，我希望选择或拖入文件直接附加到任务目标或定向追加指令，以便不必先配置知识库或代码仓库。
41. 作为用户，我希望发送前能看到附件清单、进度、失败与移除操作，以便确认实际交付了哪些材料。
42. 作为用户，我希望区分文件保存、内容解析和成员实际读取，以便不误以为上传成功就是理解成功。
43. 作为用户，我希望附件在后续讨论和重新打开后仍可访问，以便持续围绕同一份材料工作。
44. 作为成员，我希望在授权范围内读取原件或有来源的解析内容，以便不同运行时都能讨论用户提供的材料。
45. 作为用户，我希望文档结论能指向原文件和可用的页码、章节或片段，以便核查依据。
46. 作为用户，我希望无法解析、部分可读和不支持的格式明确显示，以便不会收到根据文件名编造的结论。
47. 作为开发任务发起者，我希望给出 GitHub Issue 后团队推进到约定交付，以便减少人工转交开发、测试和评审工作。
48. 作为开发成员，我希望并行修改使用独立分支和工作副本，以便不会覆盖同伴正在做的修改。
49. 作为测试或评审成员，我希望验证明确的提交版本，以便结论准确对应最终交付代码。
50. 作为用户，我希望真实失败触发修复、复测和重新评审，以便团队交付通过证据支持的结果。
51. 作为用户，我希望收到 PR、测试证据、评审结果和剩余问题，以便决定是否接受工程交付。
52. 作为仓库负责人，我希望合并遵循人工节点或预先授权，以便团队不会自行扩展发布权限。
53. 作为产品负责人，我希望从 idea 和文档出发组织研究、反证与修订，以便形成有依据的产品定义。
54. 作为研发人员，我希望 functional spec 讲清功能价值和产品影响，以便理解为什么要做这个功能。
55. 作为研发人员，我希望规格明确用户流程、功能细节、异常边界和验收，以便能够据此拆解与实现。
56. 作为决策者，我希望规格保留事实、假设、分歧和待验证项，以便不被一致口吻掩盖未知。
57. 作为用户，我希望否决提案或未达目标也能形成诚实完整的交付，以便保留有价值的研究认识。
58. 作为成员，我希望按当前工作召回相关经验，并能主动查询，以便长任务不只依赖开场提示词。
59. 作为用户，我希望成员私有经验、项目材料和团队方法具有不同范围，以便跨任务复用不会串用项目数据。
60. 作为用户，我希望反馈和纠正及时保存，以便上下文压缩或索引延迟不会让纠正丢失。
61. 作为用户，我希望 Agent 总结先作为有依据的候选，以便未经验证的判断不自动成为永久规则。
62. 作为团队负责人，我希望在授权内采纳改善协作的方法并保留依据，以便团队能逐步改进。
63. 作为用户，我希望能撤销或纠正经验，并看到重新采用的依据，以便过时结论不反复影响任务。
64. 作为用户，我希望团队需要新角色时先向我提出理由，以便团队规模和职责保持受控。
65. 作为成员，我希望继续使用运行时原生 subagent 和上下文压缩，以便平台不会削弱 coding agent 的工作能力。
66. 作为用户，我希望配置简单可选的预算，并保留原任务约束，以便不必维护复杂计费或额度系统。
67. 作为用户，我希望暂停、停止、撤权和重要纠正及时生效，以便普通消息排队不会阻碍控制。
68. 作为用户，我希望人工节点只暂停依赖它的工作，并明确到期处理，以便其他已授权工作仍可推进且沉默不会成为同意。
69. 作为用户，我希望收到请求与实际执行结果分别呈现，以便知道任务是否真的停止、交接或完成。
70. 作为用户，我希望显式退出 HimaHarness 后本次团队执行终止，以便不需要管理退出后仍工作的隐形服务。
71. 作为用户，我希望重新打开后保留团队、通信记录、任务和成果但不自动开工，以便由我决定是否继续。
72. 作为用户，我希望选择继续后先核对外部状态再恢复，以便不会重复创建 PR、重复提交操作或丢失已完成工作。
73. 作为用户，我希望意外崩溃与主动退出分别处理，以便可靠恢复不会覆盖我的停止意图。
74. 作为用户，我希望记忆服务故障时允许不依赖新检索的工作继续，以便短暂故障不会无故阻塞全部团队。
75. 作为用户，我希望成员通信或运行时投递故障时能看到实际状态并通过 Hima 暂停或停止工作，以便团队不会在未知状态下继续扩展协作。
76. 作为用户，我希望核心执行记录或控制失效时停止发起新操作，以便系统不会在失去事实与控制后继续工作。
77. 作为已有用户，我希望升级保留 Pack、Site、历史会话、运行记录和资产，以便采用团队能力不会破坏当前工作。
78. 作为已有用户，我希望 Guide、Campaign/Fabric、Data Insight 和单 Agent 路径继续可用，以便只在需要协作时使用团队。
79. 作为用户，我希望安装、升级和数据恢复由产品提供清楚的流程，以便不需要了解各组件内部结构。
80. 作为产品验收者，我希望用真实混编开发和文档研究用例验证价值，以便组件安装成功或模拟成员输出不被当成完整产品成功。
81. 作为用户，我希望在任务中集中看到真正等待我回答或决策的事项，以便无需逐个翻阅成员输出寻找阻塞。
82. 作为用户，我希望回答只作用于原问题、原授权范围和有效版本，以便迟到回复或同伴声称已批准不会误授权新的操作。
83. 作为成员，我希望提问或委派后得到可追踪的接纳回执，并能继续无依赖的工作，以便不占着唯一执行资源等待同伴。
84. 作为用户，我希望继续任务后知道成员是恢复原会话、由保留材料重建还是等待我处理，以便理解上下文的实际连续性。
85. 作为用户，我希望任务活动与成员详情区分实时输出、已保存证据及缺失记录，以便重新打开时不会把临时显示当成完整历史。
86. 作为任务发起者，我希望成员既能访问获准的 GitHub、研究来源和模型，又不能访问其他成员或平台的私有服务，以便隔离不妨碍实际工作。
87. 作为已有用户，我希望团队服务启动失败不阻塞无关的 Guide 或其他工作，以便新增能力的故障影响保持有限。
88. 作为用户，我希望备份和恢复清楚说明敏感数据保护、凭据处理及缺失项，以便不会把不完整或未保护的导出误当成可恢复备份。
89. 作为业务产品负责人，我希望新产品和芯片设计任务主要通过 Pack、Skills、工具和领域验收接入同一 Harness，以便复用已经建立的执行与交付能力。
90. 作为 Pack 作者，我希望通过目标、输入、约束和交付合同调用团队，以便调整团队阵型或合格运行时时不必理解其原生会话与内部通信细节。
91. 作为任务发起者，我希望团队成果经验证、必要资源收束和持久提交后自动交给后续节点，以便无需由我或 owner Agent 手工转交脚本、宣告完成或逐步推进。
92. 作为平台维护者，我希望接入新的模型、Agent 或知识组件时仍能解释已有方法、经验、来源和工程成果，以便技术迭代不使已积累的业务资产失去用途。

## Implementation Decisions

1. **职责边界。**

   - HimaTeam 组织角色、持久成员、负责人、协作契约、工作空间和成员经验；HimaFabric 承担任务约束、权限、环境、验收、产物及运行事实；DBOS 是唯一机械推进与恢复内核。Pi/OpenCode 均为 Resident Agent 实现，可直接服务 Fabric，也可承担成员或负责人工作。
   - DSH 继续承载现有 Hima 产品与 Guide，不是每个团队必需的额外业务负责人。
   - Fabric 是 Hima 自有的业务执行基础设施，DBOS 是它实现持久执行所使用的内核。Pack 方法与获准的动态任务定义工作内容和依赖；Fabric 落实任务合同、Site/Permit、资源与领域验收；Hima 的流程解释器运行在 DBOS 中，由 DBOS 承担机械推进、等待和恢复。Fabric、HimaTeam、owner Agent 均不另行维护竞争的节点推进循环。
   - DSH 提供现有会话、模型/工具与插件宿主，承载 Guide 和既有 Campaign owner；Resident 自主完成被委派工作，Team 组织成员之间的业务分工。以上是职责边界，不预设五个独立服务或一条层层转述提示词的链路。

2. **组件与范围修订。**

   - OAR 负责运行时接入，Pi/OpenCode 负责自主执行，Hindsight 负责记忆提炼与检索，DSH 按兼容性和收益升级。用户本次明确撤销首发 Zulip/群聊依赖；Agent 通信与工作详情由现有 Host、数据库、执行适配和 Desktop 承接最小增量，不引入聊天服务器、新 UI 库或第二调度器。
   - 其余组件选择保持；新增实体或模块须有消费者与明确收益。
   - 相对当前产品，主要新增运行依赖为 OAR、Pi 和 Hindsight；OpenCode、Fabric、DBOS 与 Host 已有，DSH 按资格验证升级。HimaTeam、最小通信、任务/成员视图和附件交付在既有产品职责内建设；受管 VM/容器仅按服务与隔离的实际依赖决定。当前 Resident 直连 OpenCode ACP 的成功不能替代 OAR 混编资格。
   - 团队与业务合同使用 Hima 所有的稳定身份、材料、成果和经验引用；原生 session、事件及记忆后端细节留在适配边界。新执行者须验证目标/材料交付、观察、控制、收取和实际恢复能力，能力不足时如实限制用途，不承诺任意 Agent 无条件兼容；不为未来替换预建通用插件平台。

3. **多入口共用能力。**

   - Guide、普通会话、独立团队入口、Campaign 和 Fabric 节点使用同一团队身份与任务接口。团队入口是管理和参与协作的入口，不是唯一调用路径。单 Agent 工作不强制建队；串行/并行不决定是否为团队。Campaign 外层 owner 仍负责整体业务，团队负责人只负责被委派范围。
   - 公司级承载表示不同业务共同使用这些合同和能力。Pack 可在节点中委派团队，成员也可在当前授权内请求 Fabric 执行既有工具与工程任务；后者仍经同一任务接纳与执行事实返回，不产生另一个 Run owner。业务专属方法、测量与判断留在 Pack/Skills/领域适配中，不按产品名称在通用调度内核追加特例。

4. **团队定义与身份。**

   - 团队定义保存版本、成员及角色配置、Skills、协作关系和交付约定。团队成员是长期身份；原生 session 和执行进程只是当前工作载体。角色、成员、团队定义版本、任务空间、执行代次、成果与消息关联分别表达。这些是逻辑身份和引用，不预设每项必须成为独立服务或数据库表。凭据与机器路径等本地绑定不进入可分享定义。

5. **定义修改与复制。**

   - 新版本默认用于新任务；活动任务固定其版本。明确应用修改时记录变更并在合适边界交接；停止、撤权与事实纠正不受版本固定阻碍。调用现有团队保留有权使用的成员经验；按定义创建新团队创建新身份与工作空间，不默认复制项目历史和私人记忆。成员活动上下文不同时接受无关任务的双重指挥，不建立跨项目成员排班池。

6. **独立任务来源。**

   - 扩展既有任务开工与来源合同，明确区分 Pack/Campaign 委派与独立团队任务，冻结来源、团队定义版本、输入、权限、环境和验收。不得用空 Pack、伪造 Pack digest 或第二执行账本绕过现有入口限制。既有 Pack 编译、旧 Run 身份和历史解释保持兼容；不热改正在使用的方法。

7. **任务合同与执行粒度。**

   - 团队整体工作及成员委派须可关联，合同包括目标、材料、工作范围、负责人/执行者、交接、验收、人工节点和失败处理。任务可以仅是讨论、研究或形成判断，不强制编码、测试、PR 或 Pack 工程流程。只有人类输入、材料与尚未激活成员的草稿可以先保留在任务空间而没有 Run。
   - 首次激活任何团队成员，包括回复、讨论、研究和评审，都须打开或关联冻结合同下的受控 Run/effect，具有资源容量、权限、执行代次和停止目标；不能另建绕过 Fabric/DBOS 的讨论执行路径。后续消息可以在同一任务的合法执行内接续，不要求每条消息创建 Run。
   - 负责人作调查、分工、退回和接续的业务决定；Fabric 管理需要委派、交接和验收的工作，DBOS 保持机械推进。成员内部搜索、修改、测试循环与原生 subagent 由运行时自主组织，不把每条通信或工具调用变成业务节点。提问和委派先返回已持久接纳的回执，不把等待同伴或人类的结果阻塞在尚未结束的工具调用中；成员可继续不依赖答复的授权工作。
   - 真正等待时在可支持的工作边界让出资源，单容量条件下先保存上下文并确认关闭原执行，再运行子工作。返回结果作为有关联的新输入交回；普通追加输入不强制新建执行代次，只有原执行关闭或授权替换等情况才新建代次。互相等待须有依赖与期限，不能无限自动往返。
   - 跨成员委派及流程节点交接复用现有 TaskResult 边界：收取实际产物，完成合同要求的验证，持久保留已验证交付，确认必要所属资源收束，再提交可消费结果；下游通过已提交值和明确产物引用取输入，按已授权方法自动接续。普通信息交流不要求结束成员会话；有独立验收要求的工作不能用聊天摘要或消息 accepted 回执替代结果提交。没有声明人工节点时，不要求人类或 owner 再做一次机械 complete。
   - DBOS 恢复执行进度，Fabric/执行适配器仍须核对原外部效果及资源。投递未知、材料变化、验证拒绝和关闭未知按各自原因等待或修正，不盲目重跑工程。自动修正仅在已实现并获授权的路径中成立；其他阻塞显示证据和可执行的处理入口，不以持续轮询冒充问题已解决。

8. **成员调用身份。**

   - 现有 DSH live session 绑定的 owner 与控制接入不能直接套用到外部 Pi/OpenCode。Hima 为成员提供受认证、绑定任务与权限的调用能力；实际调用范围由 Host 解析，不能信任模型自行填写的成员、项目或记忆范围。团队负责人使用不同运行时不产生第二业务 owner。
   - 每次成员工具请求及实际效果提交都重新核对任务、有效代次、授权、到期与撤销，不把一次开工检查缓存为整个会话的权限。成员使用 Host 所有的受限通信入口，仅接受成员凭据；若沙箱需要网络连接，则使用与人类页面/管理路由隔离的接口面，不额外部署网关。成员不能携带人类会话或桌面退出凭据越权控制。
   - 原生 shell 不因存在 Host 工具检查就自动获得逐操作拦截保证，仍由经过验证的运行环境与权限约束。首期人类参与者沿用该 Hima 实例的已认证操作者权限，不建立同事账号目录或多人权限共享体系；操作者可通过本机或已获准的局域网入口使用产品，不能仅凭 IP 互通视为获授权。
   - Host 将有效认证上下文映射为持久的操作者主体，再检查对当前任务的操作权；浏览器标签页与 DSH 对话 session 不是不同的人。重新打开、切换会话或换页面不改变指定回答者，成员凭据不能声明 human 主体。

9. **OAR 接入。**

   - 在既有执行适配职责中覆盖准备、启动、输入/消息、状态核对、收集、停止与资源释放。各成员使用隔离的进程、工作上下文与运行时配置，避免通过修改共享进程环境切换 API key 或目录。保留 Pi/OpenCode 原生工具、Skills、压缩与 subagent 能力；不逐个审批 native subagent。
   - 运行时自带队列不作为持久投递证明，Hima 保存投递意图、原生会话身份和执行代次并处理恢复。资格验证使用已保留原生会话身份跨适配器重启恢复，不假定存在通用会话发现接口；找不到身份或丢失创建回执时核对所属资源与外部效果，保持未知，不直接另起一次工作。
   - 固定版本适配器是否支持待处理权限请求及回复必须单独核实；已自动回答的权限事件只能作为观察记录，不能再呈现成等待人批准的请求，也不为此并行引入第二运行时控制器。

10. **任务与成员工作区。**

   - 在现有 Desktop/Workbench 展示团队定义、任务/成员总览、成员详情、阻塞及成果引用。成员详情读取实际输入、输出、工具调用与结果，区分实时临时输出、保留记录、截断与缺失；保留来源身份、执行代次、稳定顺序和产物引用，不虚构全局因果次序、子 Agent 内部过程或模型推理。任务内可有有界只读活动列表，点击进入成员及成果；不建设独立团队信息流产品。
   - 人类选择接收成员追加指令和附件；真正待回答的提问、人工节点及获准评审请求集中显示，回复仍返回各自原始处理入口。这是现有事实的投影，不是第二调度队列。输入草稿不暂停成员执行；页面更新不覆盖草稿。任务不依赖频道、房间、@、在线状态或聊天界面。

11. **定向通信与唤醒。**

   - 人类和成员可向明确接收的成员发出要求、提问、交接或复核请求；记录真实发送者、接收成员、teamId、taskId 和 messageId。Host 根据认证身份、任务及权限解析地址，不接受模型伪造发送者。团队新目标默认交负责人整理；人类可在当前任务中直接追加职责范围内的指令，负责人可见。明确派工、交接与等待结果到达唤醒相关成员，普通进度不唤醒全员。
   - 忙时普通输入排队，控制与重要纠正及时处理；多角色讨论明确参与者与收束条件，不要求 IM 广播。成员可向当前任务获授权的人类参与者提问或请求决策，不要求先把人注册成可派工的长期 Agent 成员。输入正文或工具结果应携带 Host 生成的来源、成员、任务及关联标识，使运行时能区分人类要求、同伴信息与文档引用；仅在日志中标作者不足以证明模型实际看到了来源。
   - 所有同伴信息均不能代替权限或人工批准。

12. **持久投递与恢复事实。**

   - 消息和附件引用在投递前由 Host 持久保存，记录地址、messageId、关联任务、实际目标 session/执行代次与投递回执。
   - 保留最小投递状态 pending（待投递）、accepted（目标运行时有接收证据）、unknown（无法核实是否收到）、rejected（明确拒绝）；Host 已接纳请求、运行时已收到与业务已接受/执行是三个不同事实，accepted 不代表业务成功；仅有 OAR 适配器内存队列的接纳回执不足以标为目标运行时已收到，须保留实际投递位置与证据。
   - 按稳定 messageId 去重已接纳业务请求，恢复先核对原目标与实际效果；无法证明时保留 unknown，不盲重发外部操作，不承诺 exactly-once。业务决定与已冻结合同另行记录，追加指令不暗改历史。该机制是协作通信记录，不建设通用聊天、可编辑消息历史或 IM 服务。逻辑消息身份与各次投递尝试分开；同一请求同内容接回原事实，内容冲突拒绝。
   - 并发投递通过现有存储的原子认领约束；恢复时只在核对原尝试后绑定新的获授权执行，不能将所有待处理消息永久挂在失效会话，也不能因换代重复执行。读取消息不等于业务已处理。继续使用已有等待机制作为基线；DBOS 通知只能在有实测收益后作为可选唤醒提示，接收方重读权威事实。
   - 消息保存与通知发送不是一个原子事务，漏发通知仍须可推进；不采用新的 broker、流服务或逐消息工作流。

13. **任务与指令附件。**

   - 复用普通对话的选择、拖放、粘贴和上传能力，为 Guide、任务目标与定向追加指令接通统一的材料引用与授权交付。保存原始文档、稳定身份、类型、大小、内容身份与来源关系；原件、解析结果及引用分别可追溯。不能把 Host 私有绝对路径直接当作 Mac/Linux VM 或 Pi/OpenCode 已可访问的材料。
   - 发送前附件状态、失败/重试与移除行为可见；重新打开讨论仍能读取或明确报告材料不可用。

14. **附件读取边界。**

   - 文件已保存、已解析、Agent 实际读取及经验采纳分别表达。长文按需读取有来源片段，不能只凭文件名回答。当前解析基础覆盖可提取文本的 PDF、Markdown、TXT；DOCX/PPTX 可上传原字节不等于已有解析。图片现有链路可能归一化，不能未经补证承诺保留相机源字节。
   - 具体格式、限额和扫描/表格/图片覆盖在兼容验证中形成明确清单；对未支持或部分可读材料显示原因。首期文档业务验收必须证明实际内容被成员使用，而非只显示附件卡片。

15. **Hindsight 首期接法。**

   - 以 Host 统一 API 读写为首期接入设计，成员通过共同受限工具面按需查询，Host 在任务接续时提供相关上下文。优先复用既有经验采纳与知识装配接口，不并行开启多套原生自动写回/自动注入以造成重复和越权。服务凭据由 Host 管理；仅绑定本机端口不视为鉴权。
   - Native provider 凭据与 Hindsight 服务凭据分别处理，不新建复杂账号代理平台。

16. **记忆范围与纠正。**

   - 分清成员在项目内的私有经验、项目资料及获准团队方法；跨项目提升有来源和授权。原始文档、GitHub 对象和成果仍是证据来源，Hindsight 不替代归档或运行事实。人类反馈先持久保存，索引异步写回并记录状态；召回按权限、来源、适用范围及采纳/撤销状态处理。删除索引不等于活动上下文忘记旧内容，纠正须进入相关活动工作。

17. **成长与决策权。**

   - 自行总结先为候选；个人技巧在授权内采用并留记录，影响协作与交付的方法由负责人确认。新增成员只能提议给人；角色增减、权限、人工节点及降低验收要求由人决定。必要人工节点有期限和到期处理，只阻塞依赖它的工作；沉默不构成同意。人类答复绑定原请求、任务/效果、内容或产物身份、指定回答者、版本、有效期和预期响应结构；重复同答复返回原结果，过期或冲突答复拒绝。
   - 忽略或关闭提示不等于满足强制节点。负责人可在既有成员与授权范围内派工，不得自行增设长期成员；原生 subagent 不受此成员增设规则管控。

18. **工程协作。**

   - GitHub Issue 承载工作和验收，分支/提交/PR 承载修改和审查，Hima 保存成员上下文、交流、恢复与证据关联，无需逐条复制协作通信到 GitHub。并行写入使用独立分支/工作副本，串行交接明确写入者；测试和评审绑定具体提交，修改后复核受影响条件。默认可在契约内建分支、提交、推送、开 PR 和处理意见；合并由人或预先授权控制，发布部署另行约定。
   - 上述权限必须由实际执行边界落实，不能靠角色提示或 runtime 自动许可。资格验证须证明实际成员可操作任务分支和 PR，却不能执行未获授权的合并、受保护分支更新、远端删除、tag 或 Release；不向成员继承宿主全权凭据、SSH agent 或未受限 credential helper。
   - 细粒度 token 或 GitHub App 名称本身不是隔离证明；按目标仓库规则、身份权限和能力实测选择接法，必要时由既有 Host 暴露狭窄的获准写操作，但不预设新合并发布平台。无法落实所需边界时拒绝相应写能力并显示所缺条件，不以临时发放全权 token 过关；普通授权推送与 PR 不因此新增逐次人工审批。

19. **交付与产品研究。**

   - 程序检查可确定的文件、schema、测试和引用条件，指定成员判断业务质量，负责人汇总结果。functional spec 必须说明用户问题、价值、产品影响、范围、流程、功能细节、异常、验收与依据，区分事实、假设、分歧和未决项。Agent 声称完成、交付完成、业务目标达成和物理签核是不同事实；负结果也可形成完整交付。
   - 默认开发和规格方法明确作者与必要复核职责，并将结论绑定实际交付版本；负责人仍能在契约内作业务判断，不能用自述替代约定检查。不同 runtime/model 不是独立性的证明，也不是每项任务的额外强制要求。产品验收由独立于该次执行的评估者按明确标准判断；不把完成多成员运行直接当作比单 Agent 更有效的证据。

20. **控制与生命周期。**

   - 显式退出 HimaHarness 终止本次团队执行并保存记录，不建设退出后的常驻执行平台。原窗口隐藏与显式退出的区分不被本升级无故重写。主动退出后重新打开不自动开工，用户选择继续后核对外部状态再接续；会话可用则恢复，否则由保留材料重建。崩溃与人的停止意图分别记录。停止请求、原生 Agent 已停、外部 Job 已停和资源已释放分别核对。
   - 等待退出、保留外部作业退出、停止作业退出以及系统终止信号均须执行团队停止与恢复门；保留作业不保留 Team 成员执行，也不豁免 Campaign 委派的团队。关闭成员后才能关闭其依赖服务，停止失败或闭合未知如实显示。迟到答复、通知、结果和记忆补写不能绕过停止意图重新开工。外层 Campaign 可恢复到等待团队的状态，但不能代替人批准 Team 继续。
   - 继续请求可以触发核对；未核实的旧效果仍被阻塞，不因为用户点了继续就变成可重试。

21. **故障处理。**

   - Hindsight 不可用时，可继续不依赖新检索且能可靠保存记录的工作，经验进入待写回；依赖检索的部分等待。定向投递或成员运行时不可用时，记录 pending/unknown/rejected 和原因，暂停依赖未确认交接的新工作；无关且已授权的工作可在可保存边界推进，Hima 控制入口保持可用。核心事实库或执行控制失效时不发起新操作。
   - 恢复先核对实际状态，不增加备用调度器或未经记录的执行路径。团队专用服务按需或后台启动，不阻塞不依赖它们的 Guide、Campaign、Data Insight；真正依赖同一沙箱或记忆服务的消费者仍须等待就绪。启动与退出竞争时收束晚到的所属资源，不能留下新的常驻执行。逐成员显示恢复原会话、按保留材料重建或等待处理的实际结果，不将恢复方式另建为执行状态机。

22. **预算、网络与部署。**

   - 主要面向用户自己的本机、办公 LAN 和自部署模型；不要求外网 Agent 接入、互联网联邦、跨地域发现或云控制面。预算简单可选，保留原 Campaign 与已配置约束；上下文压缩交给运行时。安装包配齐支持平台依赖并承担初始化、就绪、停止、数据保留、升级和故障诊断。
   - macOS 按 Hindsight 服务或任务 sandbox 的独立依赖证据采用受管 Linux VM/容器运行环境，移除聊天组件不自动删除仍必要的运行环境；具体引擎依据验证确定；Linux 不能因内部试点先用服务器而从首期交付中移除。
   - 网络隔离阻止成员接触 Host 管理、服务数据库、同伴私有环境及引擎控制，同时允许受限成员接口、配置模型与获准 GitHub/研究来源；不能把仅允许模型端点的策略冒充完整工程权限。保留已有期限、容量、去重与显式收束条件来避免循环；不默认引入多种硬通信配额或新的模型端点调度器。所有成员活动沿用既有 Run 的有效绝对截止时间。
   - 独立任务首次激活前，由调用方、团队定义或操作者提供并展示期限及收束条件；已有调用期限不得扩大，缺少有效期限时不能开工。无成员执行的草稿不要求运行期限，团队长期身份也不随该期限消失。到期后平台停止接纳新工作、收束所有相关成员并显示原因，不依赖负责人下一轮回答才生效，未知外部效果仍保持待核对。
   - 当前任务显示实际获准模型与业务网络目的地及其来源；研究目的不自动授予任意互联网出站或敏感资料外传权限，不增加固定三档网络产品模式或默认全流量审计。

23. **升级与数据保持。**

   - 固定实际验证的 DSH、OAR、Pi/OpenCode、Hindsight 和必要打包依赖组合。保留旧会话、Run、Pack、Site、输入和成果的可读性；新的独立任务来源不重解释旧事实。组件数据库可有独立逻辑库、角色和迁移，不为减少数量强行合并不兼容 schema。准备备份/回退路径，避免旧版读取已被破坏性升级的数据。
   - Hima 的新团队入口和成员注册不假冒既有一次性 child 身份。备份按统一静止边界准备：阻止新工作与记忆写入，确认成员收束，在必要服务仍可导出时保存对应版本与内容校验回执，再关闭服务和存储。冷态备份不把过期或缺失的服务导出视为完整；恢复在维护隔离和人工继续门下先核对、导入，再允许消费者使用。
   - 原有完整备份的读取与恢复保障保持；不能为了减小包体直接丢弃恢复所需的冻结程序与资产。备份整体按敏感数据处理，分享配置只带凭据引用并不意味着原生会话和数据库中没有秘密。改变为需重新输入凭据的可移植备份或增加新的加密密钥恢复流程，须另行明确产品取舍，不作为本次默认决定。
   - 组件资格可比较已经有证据的原生部署与受管环境接法，但只验证实际拟采用的最小闭包，不以穷举所有候选为开工门；包可安装不等于隔离、二进制依赖、数据库扩展或双平台恢复已合格。中文材料是首期记忆验收的一部分：固定实际 embedding、reranker 与提炼模型组合，以中文事实、纠正和中英混合术语验证召回；不得以英文默认模型启动成功替代中文能力。

24. **既有体验兼容。**

   - Guide 保持独立，Campaign 的业务 owner 与运行图、节点、Evidence/Report 保留，Data Insight 标准页面和 Guide 发起的 Resident 定制分析保留各自入口。现有 Files & code、Pack & assets、当前知识、工作记忆和资产验证继续可用。
   - 原生对话附件入口能复用，但其完整文档读取与跨成员交付仍须补验证。

25. **开发归属与交付方式。**

   - 工作集中在现有 Host 的团队/独立任务接入、执行器的 OAR 适配、Desktop 任务/成员详情与 Host 定向通信接入、经验/知识模块的 Hindsight 与附件接入、安装升级和组合验收。它们是工作分工而非五个新服务。
   - 实施按现有仓库纪律拆成有明确所有者、接口、反证、测试和回退的有界增量；共享接线保持单一所有者，不以本规格一次性重写整个 Harness。先用当前可用基础冻结最小任务/身份/通信合同，组件升级与平台特有合同按消费者证据分阶段资格验证，不让可选唤醒优化或 UI 原型阻塞核心合同。共享文件可由唯一集成者顺序交接；新增测试及其登记同次落地，不拖至最终验收。
   - 计划和工单须按本次规格同步后再派工，历史评审不视为当前实现通过。

## Testing Decisions

**测试边界沿用用户已明确认可的接缝；本次没有新增主接缝。** 主测试接缝选现有 Hima Host 对产品客户端与 Agent 暴露的任务/控制接口，贯穿建队与派工、消息和附件、Resident 执行、验收、停止与恢复。优先从真实 Host 的最高可用边界观察行为，扩展现有入口承载独立团队任务，不为每个新概念增加独立测试服务或复制状态机。

真实桌面和安装行为通过既有 Electron driver 补齐；实际运行时、定向通信与记忆组合通过真实依赖检查；两条业务闭环通过真实混编团队验收。这些是同一产品的不同验证层级，不是多套执行权威；主 Host API 接缝保持，Electron 验证工作区与控制，真实 Pi/OpenCode 验证定向通信，不将 Zulip 作为任何验收前置条件。

**好测试的标准：** 断言用户或调用方能够观察的行为与持久事实，使用独立期望值和可推翻实现的反例；不测试私有函数调用次数或模型固定措辞，不把组件启动、schema 接纳、文件存在、模拟 Agent 对话或历史测试通过当作本次组合资格。

**复用的先例与模块覆盖：**

- 真实 Host 启动与 preparation、独立 Guide/owner 会话测试：覆盖建队/任务入口、来源合同、重复确认、权限和上下文边界。
- 既有 durable task adapter、任务消息、fork/join、finalization/recovery、Resident 工程与资源收束测试：覆盖委派、投递、核对、交付、停止及崩溃恢复。已有 DBOS 通信/恢复测试可复用来验证可选唤醒机制，不把它当从未使用的新技术。
- 当前 knowledge documents、experience files/report、Pack owner 与资产完整性测试：覆盖附件原件、解析引用、召回范围、纠正、复制和历史保留。
- Electron driver、Pack 安装页面、Run 控制与 trial packaging 测试：覆盖实际输入、任务/成员导航、定向追加指令、附件、用户控制、冷启动和双平台打包。
- 既有真实 Resident 工程和 LibInsight 定制分析的验收方式：借鉴真实模型/工具、明确材料身份与结果证据；既有结果不替代本功能的重新验证。

**分层执行：**

| 层级 | 本功能验证内容 | 不能由此推出 |

**两条业务验收的具体产物：**

- 开发用例采用包含已知缺陷或缺失边界测试的真实测试仓库。至少有一个 Pi 成员和一个 OpenCode 成员；观察实际分工、失败发现、修正、提交对应的独立复核、PR 和剩余问题；在过程中加入一次人类补充与一次中断/继续。不得用只生成计划或伪造测试报告通过验收。
- 产品用例采用至少两份有可核对事实或分歧的文档，由真实混编团队研究、反证和修订。产物必须能支持研发推导行为与验收，保留来源、冲突、假设和未决项；至少验证一次针对文档的追问与一次人类纠正。下一次任务要正确召回已采纳经验，不能把上次完整工作/通信记录全部灌入上下文代替记忆机制。

**自动交接专项：** 沿已有 Host 接缝提交包含团队/Resident 委派和下游消费者的任务。独立断言下游收到的成果身份与内容、实际工程提交次数和约定资源状态；成功路径不调用 owner 的机械 completion，也不以硬编码的“调用次数为零”字段证明自动性。注入“已验证但关闭未知”“已提交但下游尚未启动时 Host 崩溃”“迟到修改与已提交成果不一致”等反例：前者阻止下游，提交断点恢复继续消费原结果，迟到变更不能替换已冻结交付。该用例扩展 T20，使用真实 Host/DBOS/存储及明确的外部执行替身，不新增测试服务或要求每次重跑完整 EDA。

既有 ATCS 五任务方法可作为交接先例：准备输入、准备 baseline、Resident 修复、评估、交付。当前后两步消费已提交 Reader 值与工程报告引用，并打包脚本、ECO 和 checkpoint；它们不自动执行后续物理采用或 PrimeTime 签核。新 Team 链路须验证同样真实的交接，不能以已有单 Resident 成功代替。平台复用以本规格已定的开发、产品研究及 Campaign 调用覆盖为依据，不额外要求首期迁移所有公司业务或建立业界全面排名。

先做合同、来源、授权和脚本成员的低成本反例，再做真实运行时及 GUI 组合。投影快照只验证显示映射；伪造身份、过期答复、投递认领和停止竞态在 Host 变更接口验证。崩溃用例与正常关闭分开，数据库去重不被外推为外部效果恰好一次；真实层发现的缺陷先回落为低层回归。可选 DBOS 唤醒比较只测真实增益，不阻塞必需协作；不冻结 AG-UI/A2A 事件体系或为协议对齐更改执行状态。

每次验证记录源码/构建/组件版本、使用的模型、平台、输入与产物身份以及 pass/fail/skip/未运行范围。仅对受影响路径扩大验证；不为工作区布局变更重跑完整 EDA。所有实际外部操作使用明确获准的测试仓库、模型和 Site，产品发布不由测试结果自动授权。
