# 对话 Agent 执行节点，Fabric 提供运行约束与事实

日期：2026-09-12 更新。用户决定：Hima Harness 中与工程师对话的同一个 AI Agent 执行整个业务过程中的节点工作，依据参考路线和实际结果应变。执行主导权见 [ADR-0006](../../adr/0006-conversational-agent-owns-business-execution.md)。本轮为 [Step 4 接续](../step4-takeover/spec.md)细化接口语义、持久身份、暂停和迁移的工程约定。当前实现、实际验证和未完成范围以 [批次验收记录](../../assessment/2026-09-12/pls-next/README.md) 为准。

本文件替代此前“Fabric 自动跑图，Agent 从外部暂停/介入”的方案。下文的旧代码差异以实施前 `4d8bc8c` 自动驱动基线为准；当前生产主路径已由对话 Agent 显式执行节点。保留本文路径以维持已发布任务引用，不能把旧版控制接口方案继续当成主设计。

## 执行分工

| 主体 | 权责 |
| --- | --- |
| 工程师 | 提出研究方向、预算和约束，在同一对话中修正执行 |
| 对话中的执行 Agent | 理解 Pack、读取状态，选择可执行节点，完成节点内的研究/代码/工具工作，根据结果决定继续、调整、回溯或请求额外探索 |
| Pack / 参考运行图 | 提供方法、推荐路线、依赖、所需证据和可探索位置；保留不可被 AI 改写/删除的参考基线 |
| Fabric 及现有运行模块 | 提供上下文与可用动作；校验权限、依赖、输入版本和预算；接纳并记录执行、追踪作业、验证节点完成、支持恢复 |
| Jobs / Channel / Shell / EDA | 执行已接纳的实际命令并提供真实结果；进程执行不发生在模型本身 |
| Judge / Ledger | 保持判定与事实权威，不能由 Agent 的自然语言成功声明代替 |

业务循环应为：

工程师 ↔ 同一执行 Agent → 读取 Run/节点上下文 → 选择并执行节点工作 → 调用受控工具 → 获得真实状态/证据 → Agent 决定下一步。

节点内也由 Agent 工作。例如 Agent 在算法节点读输入、编辑脚本、测试、分析失败并调整；不能让 Agent 仅调用一个包装后的“执行整图”工具，再由旧 `drive` 自行完成其余业务。

已有确定性脚本、解析器和判断规则继续作为工具使用；一个工具可以可靠完成机械步骤，无需把每条 Shell 指令都拆成一次模型推理。普通 Coding 能力继续保留；归入某 Run/节点的工作必须带可验证的执行上下文。

## 从实施前基线改变了什么

以下五点记录 `4d8bc8c` 的起点和本任务要求，不能作为当前代码仍在自动驱动的说明。

- `fabric.ts` 的 `startRun`/`resumeRun` 目前都会调用 `drive`，由循环自行挑选和推进节点。新的主执行入口需要从该自动驱动路径拆出。
- `node-turns.ts` 的 `toolNode` 包含启动与等待，`exploreNode` 会直接执行固定 chooser。应把可复用的受控操作交给 Agent 调用；不以固定 chooser 继续垄断实际策略选择。
- `recovery.ts` 当前能在恢复时重新进入自动驱动。新模式应先重建 Job/记录事实和 Agent 上下文；不能在没有执行 Agent 的时候自动启动下一业务节点。
- `tools.ts` 的长 `hima_run`/`hima_resume` 调用会占住等待。新入口必须让追踪身份及时返回，利用已有 dsh 工具/后台工作/事件机制保持对话可响应。
- UI-02 的同屏面板已经建立，但 UI 开始按钮目前仍直接启动自动 Fabric 流程。新主路径必须连接到所属对话 Agent，而不只是换文案或增加控制按钮。

这是一项执行职责调整，会触及多个已有模块。沿用现有架构和模块不等于零适配成本。实施前必须列出真实生产者、消费者、记录兼容及重叠修改归属。

## 同一个 Agent 与明确的控制所有者

一个 Run 同时只允许一个明确的业务推进所有者。该身份与左侧对话 Agent/会话关联，并可在重启后查证；不默认新增一个隐藏的后台执行 Agent。

执行归属由 Host 从真实会话和工具调用上下文确定，不能仅信任模型在参数里自填的 Agent 身份。记录应能区分人类请求、Agent 决策与实际工具执行。

允许主 Agent 使用 dsh 已有的子任务委派，但任务范围和回执必须回到所属 Run/节点；主业务控制权不因此变成另一个未说明的自主驱动器。

在右侧选择一个 Run 不自动改变其所有者。涉及其他会话的 Run 时，需要进入所属对话或作明确交接；旧所有者的过时请求不得与新所有者并行推进。同一 Agent 可以管理多个已明确授权的 Run，但每个请求必须指向正确的 Run 和节点执行。

## 单节点执行接口的语义

接口放在现有操作层，工具、UI 和必要命令入口共享。下表不冻结最终函数名或工具名。

| 操作 | 提供给 Agent 的能力 | Fabric 必须保证 |
| --- | --- | --- |
| 打开/准备 Run | 选择 Pack、Site、Goal、预算，获得 Run 与参考方法身份 | 创建可追踪上下文，不暗中进入整图自动推进 |
| 检查执行上下文 | 当前事实、参考路线、依赖满足情况、可用动作、输入/代码/证据版本 | 未知如实返回，不把“可执行候选”偷偷选成下一项业务决定 |
| 开始节点执行 | 领取某个节点/代际/分支/尝试的明确执行上下文 | 同一尝试不被重复接纳，目标、所有者、前置证据及预算适用 |
| 节点内工具工作 | 读数据、写算法、运行脚本、提交/查询 Job、读取输出、请求 Judge 等 | 操作绑定到该节点；权限和资源检查不能绕过；异步 Job 返回身份 |
| 请求节点完成 | 提交产物与证据，要求结束当前尝试 | 根据实际输出、内容身份、Judge 及节点要求决定能否完成；模型自报成功不够 |
| 修订/回溯/附加研究 | 提出新的策略/算法版本及影响范围，选择重新执行的位置 | 保留参考图和历史，复用有效结果，重跑受影响下游；复用 PLS-10/11 |
| 暂停/继续/终止 | 响应工程师的中途指令，停止发起新工作，按授权恢复或终止 | 请求与实际效果分开，已有 Job 状态及资源不能凭空改变 |

实际命令仍通过现有工具实现、Jobs/Channel 和操作系统执行。Agent 是发出和组织这些执行动作的主体，Fabric 的单节点操作不是另一个自主跑图循环。

## 交互例子

1. Agent 按参考路线执行到 B。工程师在同一对话说“先暂停 B，检查输出，再调整算法”。
2. Agent 读取 B 的实际执行身份和 Job 状态，请求相应暂停/停止，并说明当前仍未生效的部分。
3. 在可修改状态下，Agent 自己分析输出、编辑算法和验证；修订指向明确的旧/新内容身份，不能改活动文件冒充已经更新的执行版本。
4. Agent 请求接纳修订，并依据验证后的影响范围重新执行 B 和受影响下游；先前历史和仍有效结果保留。
5. Agent 根据新结果和工程师授权继续业务，而不是把控制权交回一个自行跑完整图的循环。

这种能力不依赖 Pack 在 B 处提前插入 Human Handler 或人工等待钩子。

## 可靠性不能依赖 Agent 的记忆或自律

- 每个受控动作带准确 Run/节点/代际/Loop/branch/attempt、执行所有者以及适用的版本/去重身份，不能只发送一个模糊的 currentNode。
- Agent 可以请求动作，不能直接改 Ledger 的成功/判定字段，也不能跳过必需证据、删除参考节点或重置总预算。
- 普通 Coding 工具对同名算法文件的修改不等于已接纳的执行版本。工作区/工具范围、内容身份与 PLS-11 的有效性检查必须落实这个区别。
- 状态采集、资源约束、硬预算终止、停止结果确认等机械保障继续由基础设施承担，不要求模型为每次轮询重新推理。
- Agent 中断或模型不可用时，已经启动的 Job 可以继续被追踪并落下事实；新的业务节点等待 Agent 恢复。恢复不自动退回旧 Fabric 自主驱动。
- 长 Job、资源等待和内部研究工作不能占住唯一的前台控制通道。能继续打字不等于 Agent 能及时处理介入；必须实测。

## 本轮暂停与停止的工程约定

以下默认用于可实施规格，不追溯声称用户此前已逐条确认。普通“暂停此节点”立即阻止该节点及依赖它的后续新业务接纳；已有 Job 可完成并保存事实，界面说明仍在运行。无明确节点的暂停作用于整个 Run。无依赖的并行分支在节点范围暂停下可由 Agent 继续请求执行；Run 范围暂停则全部停止新接纳。

明确“立即停止”调用实际 Job 终止并等待退出事实；未知退出状态不能显示已停止或释放许可。暂停不使用通用 SIGSTOP 冒充安全检查点。需要 checkpoint/resume 的 EDA 工具必须声明并验证自己的语义，否则从失败节点的新尝试重跑。

暂停与启动接纳竞争时使用同一串行约束：先被接纳的 Job 如实列为在途，暂停之后的相关接纳拒绝。暂停不改写 Goal、历史和已完成证据；总 time box 继续计时，不另发预算。允许读取/分析现有材料；新实验 Job 必须先显式继续。AI 模型调用仍遵守总时间与 PLS-12 的收尾约定。

恢复推进须由合法所有者显式请求；不因 Job 自行结束或 UI 重连解除暂停。需要修改正在使用的脚本时先进入明确无在途使用的节点边界，或创建新内容版本，不能就地改活动文件再声称当前 Job 使用了新算法。

## 身份、幂等与回执

下面是所需语义字段，具体序列化名称在现有 Ledger schema 中实现；不引入第二状态存储。

| 身份/字段 | 写入者 | 消费者与约束 |
| --- | --- | --- |
| 执行方式与 owner session/Agent、owner epoch | Host 接受首次绑定或明确交接后写 Ledger | 工具、命令、HTTP、恢复、UI 共用；身份来自真实会话上下文，epoch 变化使旧所有者的请求失效 |
| control revision | 现有执行/控制操作，在接纳、暂停、交接、修订等突变时递增 | Agent 提交 expected revision；过时请求返回当前事实与可用动作，不隐式重放。日志追加和只读轮询不无故改变控制版本 |
| node execution identity | Fabric 接纳写入 | Run、node、generation、Loop/branch、attempt 及方法/输入/代码版本一起确定一次执行，不能只传 currentNode |
| request identity 与参数摘要 | 操作入口在副作用前持久记录 | 相同请求返回已有回执，内容不同时拒绝；restart 后仍不能重复启动。Ledger 写入失败不允许绕过记录直接 launch |
| Job 与产物回执 | 现有 Jobs/Channel/Workspace/reader/Judge | 返回真实 Job ID、running/waiting/exit/unknown、结果位置和内容身份；Job 完成不代表节点必需证据已齐全 |

owner epoch 和 control revision 适用于本轮所有改变运行行为的入口。旧工具名若仍保留，必须路由到同一约束，不能成为绕过路径。模型无法直接写 Ledger 的成功或 verdict；请求完成必须查验本次输入/代码身份、真实输出、必要 reader/Judge 与依赖。

同一 UI 选中别的 Run 仅改变查看对象。接管必须是明确操作，记录原 owner、目标会话及交接时的执行事实；先停止新接纳并处理在途状态再交接。紧急取消可由已授权的人类入口发起并记录其身份，不要求原 Agent 在线，也不因此更换业务所有者。

## 非阻塞与重启

节点开始与 Job launch 返回可追踪回执，不等待整个 Job 或整张图。用已有 dsh 事件/后台能力通知同一会话有新事实，Ledger 保留未读状态以便恢复；可靠性不依赖一次易失通知。通知本身不决定下一节点，也不另开隐藏业务 Agent。真实模型 L4 必须证明长 Job 期间同一 Agent 能处理用户介入，不能只检查输入框可打字。

新模式恢复先重建在途 Job、未闭合 code/session 与控制状态，保留已用预算、owner 和历史。只有得到属于该所有者的下一项业务请求后才再开节点；模型不可用时保持可读、可取消、可追踪。旧 `drive` 的 start/resume/reconcile 和循环内部入口都要做执行方式校验，不能由后台恢复路径绕过。

旧格式 Run 不批量补成新模式。在本轮默认升级中：历史只读继续可用；在途 Job 先观察/收束，阻止新业务自动开始；原始记录未丢失且到达安全节点边界后，由明确操作绑定对话 owner，再继续。无法重建旧方法/输入/产物身份的 Run 不允许直接声称安全迁移，应保留旧历史并说明缺口。旧自动路径只在隔离回归环境对照，不作为永久第二产品引擎。

L2 必须覆盖进程重启落在“请求已登记、Job 已发起但回执未送达”等边界，复用现有 Job/session 发现与去重逻辑；无法确定是否已 launch 时先查询/阻塞，不能直接重复发起。

## 实施顺序与验收

1. 接口盘点与迁移设计：固定 polishing/原型快照，列出旧 `drive` 全部入口，明确每个 Run 的所有者和旧在途任务的处理。
2. 完成一个 Agent 执行的纵向切片：读上下文 → 开始节点 → 调用工具/获得 Job → 观察 → 请求完成 → Agent 选择下一步。先复用普通 act/observe/judge 能力，不能隐藏地调用旧整图循环。
3. 接入研究节点内的 Coding、算法修订与回溯、附加探索；复用 PLS-09～12，不再默认采用“Fabric 在指定点调用另一个 AI”的集成方式。
4. 验证实际对话介入、模型恢复和 DTCO 研究价值。

### 分级验证

- **L0/L1**：接口、身份、状态与合法动作、去重及兼容检查。
- **L2 主力**：真实 Host/Job/文件，由确定性的工具调用序列或明确标注的 replay 驱动新节点接口。证明“没有下一次 Agent 业务动作就没有下一节点启动”、伪造完成被拒绝、预算硬限制、旧请求失效、Agent 离线时只收集在途 Job 事实、重启不回旧自动循环。旧自动驱动测试可保留兼容价值，但不算新执行模式通过。
- **L3**：同一对话 Agent 与运行图关联，节点工作/输出可见，长 Job 期间介入有效，草稿与上下文不丢失。
- **L4 模型**：真实 DeepSeek V4 Flash 发出节点执行动作、根据输出调整、处理工程师中途指令；查验同一 Agent 的实际工具链。机械 replay 不能证明模型已经掌握研究。
- **L4 Site / L5**：实际作业/停止或检查点变化做最小 Site 检查；复杂 DTCO 中验证 AI 主导执行与知识交付的价值。

本文件初次发布时只修正规格。此后 PLS-19 已在 polishing 实施节点协议，并完成真实 Host、原生桌面关键路径和同一 DeepSeek Agent 的两代反馈实测；详细身份、失败记录及范围见批次验收记录。增长、完整修订、正式 DTCO 与真人使用验收仍按各后续任务交付，不由该小样本代替。
