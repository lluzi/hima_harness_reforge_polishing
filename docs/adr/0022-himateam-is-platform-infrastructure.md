# HimaTeam 是可独立承接任务的平台协作基础设施

2026-10-09 HimaTeam 设计访谈 Q1 中，用户明确区分业务定义与执行工具：HimaPack 继续面向具体、
复杂的芯片设计领域任务；HimaTeam 属于 HimaHarness 基础设施，既可被 Pack 调用，也可直接
接受不由任何 Pack 定义的任务，包括开发测试和 Estack 知识研究与产品孵化。

不要求为每项团队工作制作 Pack，也不将 HimaPack 泛化为所有团队任务的容器。这样保留 Pack
的领域含义，同时允许 HimaHarness 从执行 Pack 的产品扩展为多 Agent 协作平台。代价是必须为
独立团队任务澄清业务身份、成果归属和生命周期，不能直接将其视为现有芯片设计 Campaign。

本决定仅接受上述产品边界。它扩展了 ADR-0017 当时限定的产品范围，但不改变驻场工程 Agent
承接完整工程任务的职责；ADR-0018 的 DBOS 执行权威继续成立。团队契约、成员经验与方法改进的
后续确认记录在产品定义和领域词汇中；具体实施仍在访谈中，本记录不代表完整设计已确认或已有
实现通过验收。

Q29 补充确认：团队作为可管理的基础设施，可由 Campaign/Fabric、普通 session、聊天或
讨论项目使用。调用方可提供固定的成员上下文、任务与协作要求，也可由人通过对话定义成员
运行时、角色和配合关系；固定 Fabric 流程的节点可委派团队工作。团队同级入口提供管理与
可见协作，但不成为唯一调用路径。这样让不同业务复用同一能力，代价是须明确调用任务与
团队工作的身份、输入、交付和控制关系，不能把几种入口分别实现成独立调度系统。

## 当前范围修订（用户批准，2026-10-13 UTC）

当前首期采用可信用户本机/办公 LAN 上的受信任 Pi/OpenCode 与插件。默认成员执行在
既有 OAR/Resident adapter 内使用原生受管子进程，不以 Podman/VM、网络命名空间、
逐 IP/端口期限策略或 Python/Landlock/seccomp 加固为启动、测试和功能关单前置。
既有实现与失败证据保留为延期能力；强隔离不作当前承诺，App/Linux 分发在 #110 HOLD。
本文较早的冲突安装/隔离前置由本段覆盖，双平台完整分发目标保留。

DBOS 唯一调度、Host/Fabric 任务事实与成果验收、任务/成员身份及代次、grant/工具 API
权限、独立 cwd/config、密钥脱敏与最小环境、实际进程观察/取消/退出/收束仍保留。
目录/进程分离是协作和配置分离，不能宣称安全沙箱。Host 收集原生事件并核对真实成果，
不将模型自述或可编辑完成文件作为唯一成功依据；普通原子写与丢 ACK 恢复继续验证。

这一取舍缩小当前恶意本地进程威胁范围，优先交付真实混编任务与可靠协作。没有新 broker、
运行平台、产品运行模式或第二调度器。功能票按当前完整范围验证后同步提交并独立关单，
不据此宣称延期加固、分发或完整发布已经接受；main 合并和产品发布仍未授权。
