## 第一轮已确认

### Q1 服务谁及核心价值

- 不按芯片设计者、DTCO 工程师等职业划分产品重心。两类人分别是只关心 Library、同时关心 Library
  和 Design；两者依靠同一基础。
- 两类入口是 Library 与 Design。前者包括 Library 及相关 PDK 的库信息；后者包括具体设计的 DEF、
  Liberty、Netlist、Timing Report 等。文件格式本身不能决定归属。
- Library 本身的数据洞察不可或缺，要研究库值得做什么、需要做什么，以及哪些东西可转化为设计收益。
- 有 Design 后结合两侧信息，对设计形成具体指导。

### Q2 原型价值与交互改进

要保留：

1. Overall 风险地图，以矩阵/表格显示整套库中风险的位置与类型。
2. 看到问题即可直觉式点击，获得新信息。
3. input transition × output load Heatmap，配合标线区分可靠/不可靠区域。
4. 每个 cell 的 Sensitivity 呈现。
5. Overall rule configuration，允许用户表达规则或偏好。

要改善：

1. 每类分析尽量在一个标签页内完成，细节原地展开；减少下钻与回退。
2. 表达实际影响，使用户能感知某个 rule 的问题到底有多严重。
3. 数据与结论并排对照。
4. 用浅层逻辑与直接交互缩短信息 → 洞察 → 行动的距离，做到一目了然。

## 第二轮已确认

### Q3 同一套库内部洞察

- 多数场景分析一套完整库，包含多个分支、PVT、corner；本次 demo 聚焦这套库内部。
- 跨版本、跨 PDK、跨供应商比较是少数场景，暂不考虑；同一套库内不同分支/条件的分析仍在范围内。
- 默认输入完整；不完整时开展局部分析，不阻止有依据的局部结论。

### Q4 Design 的简单增量

- Timing paths：聚焦 critical timing path 用到的 cell，把这些 cell 分析清楚。
- Verilog netlist：统计 cell 使用数量，识别哪些 cell 使用较多。
- DEF：未来用相对物理位置寻找频繁出现、位置邻近的 pattern。
- 本轮没有选择此前建议中的替换/库组合/约束优化引擎；不得从“具体指导”推导出此类 demo 承诺。
  DEF 的 pattern 定义和具体交付阶段留待后续细化。

### Q5 影响与排序

- 用户同意问题、幅度、影响对象和可能后果的直接表达，并指定按风险等级排序。
- 尚未冻结等级名称、分级阈值或规则配置如何影响等级；不另造未确认的综合质量分。

### Q6 两层导航

- 左侧是大类，顶部是该大类下各具体工程问题的 tab。
- 最多两次点击定位目标分析；数据、结论和细节按第一轮要求在当前页对照呈现。
- 这取代上一轮助手建议的单一层级导航；大类与具体问题同时保留，避免多级下钻回退。
