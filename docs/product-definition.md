# HimaHarness Polishing 产品定义与验收目标

状态：用户于 2026-09-11 确认初始共同理解，并于 2026-09-14 确认真人试用后的升级设计树，作为后续 polishing 的产品依据。本文描述产品要求，不是已实现能力或已通过验收的声明。原始问题、建议、回答与代码核查见[初始产品访谈](/Users/lluzi/code/hima_harness_reforge_polishing/docs/product-interview.md)和[产品升级访谈](/Users/lluzi/code/hima_harness_reforge_polishing/docs/product-upgrade-interview.md)。

## HimaTeam 平台扩展（2026-10-09，产品定义已确认）

以下整理自 [HimaTeam 产品访谈](himateam-interview.md)的逐项确认，描述首期目标，不是已有能力
或验收完成的声明。原讨论经 to-spec 形成[升级规格](specs/himateam/spec.zh-CN.md)，已发布为
[Issue #97](https://github.com/lluzi/hima_harness_reforge_polishing/issues/97)。随后用户明确收缩
首期展示范围，取消群聊/IM 和 Zulip 依赖，保留团队通信与人类介入，见 ADR-0024。
2026-10-10 按评审收口同步规格、实施计划和工单草稿，并更新 #97。具体版本、接入与安装
组合仍待验证，尚未进入产品实现。

同日进一步明确公司级承载协议：HimaHarness 是不同产品和芯片设计业务共同使用的能力承载体，
通过 Pack、Skills、工具与领域验收交付业务，并可用 HimaTeam 组织多专业协作。新增业务优先
复用既有合同与执行能力，有实际通用缺口时再演进内核。该定位不自动要求中央共享服务、集群或
多租户，也不承诺首期迁移所有业务。用户描述约 3–4 类业务已初步跑通，不据此推导全部独立验收完成。
本次将该定位及真实交接澄清同步至 #97；此前实施计划与工单草稿需对齐本次增量后再派工。

### 定位与首期交付

HimaTeam 是 HimaHarness 的可定义、复用并持续改进的 Agent 团队基础设施。HimaPack 继续定义
具体、复杂的芯片设计业务，可调用团队执行；用户也可直接交付不属于任何 Pack 的任务。
边界见 [ADR-0022](adr/0022-himateam-is-platform-infrastructure.md)。首期同时支持：

- **GitHub 软件开发协作：** 从 Issue 出发，由团队承担开发、测试、审查等职责，自动推进到约定
  的交付状态。Issue 保存工作与验收要求，PR 承载修改、测试证据和审查；HimaHarness 保存成员
  上下文、团队交流及恢复记录并关联 GitHub 对象。无需将每段对话复制为评论。
- **产品定义：** 用户配置阵型，团队从信息和 idea 出发，经研究、反证与修订形成可信的
  functional spec，承接 Estack（以知识研究推动产品创新的方法）的知识研究与产品孵化需求。规格讲清特性价值、产品影响、用户
  与问题、目标与范围、主要流程、功能行为、异常边界及验收条件；关键判断有依据，事实、假设、
  分歧和待决定事项明确。它应持续指导研发拆解、实现和判断细节，不能以篇幅或模板完整代替质量。

### HimaTeam、HimaFabric 与 Resident Agent（2026-10-09 边界澄清）

用户明确确认：OpenCode 与 Pi 都归入 Resident Agent，可在 HimaFabric 和 HimaTeam 两种
使用场景发挥作用。它们是同类执行能力的不同运行时实现，不按调用方拆成两套 Agent 产品。
驻场工程 Agent 是 Resident Agent 承担完整工程任务的角色用法；产品研究、测试与评审也可
使用这类执行能力。“驻场”不要求进程永久在线，成员身份与经验可以跨执行会话保留。

以下分工结合 Q24、Q27、Q29 的确认描述目标关系，不是独立团队任务已经实现的声明：

- **HimaTeam 承担协作组织。** 保存团队目标、角色和成员、负责人及决策权、工作空间与协作
  契约。负责人和成员作出调查、分工、交接、复核与修订的业务决定；不另建机械执行引擎。
- **HimaFabric 承担任务运行的产品约束与事实。** 将目标、输入、权限、环境、验收和产物关系
  落实为受控任务，接回实际执行与验证记录；机械推进和恢复仍由 DBOS 承担。现有实现主要
  面向 Pack/Campaign，团队直接任务需扩展来源合同，而非伪造 Pack 或创建第二套执行账本。
- **Resident Agent 承担具体工作的自主执行。** 在给定目标与边界内理解问题、使用工具、
  编写代码、研究、测试并组织原生 subagent，返回真实进展与成果。它不能凭自述改写 Fabric
  的完成事实，也不能自行扩大团队成员、权限或验收范围。

不需要团队的工作，可以由 Fabric 直接委派 Resident Agent；需要成员职责、交接复核和持续
经验等团队协作关系的工作，由 HimaTeam 组织，成员执行复用同一 Fabric/DBOS 与 Resident
Agent 接入。Pack 也可以委托
团队，团队将符合调用合同的成果交回原任务；外层 Campaign owner 不因委派自动转移。
HimaTeam 的讨论和成员关系不强制落为固定工作流节点，每条聊天也不自动创建执行任务。

Q24 确认：Fabric 管理可独立委派、交接和验收的成员工作，例如“修复 Issue 并提交 PR”或
“独立测试并提交报告”，并保存团队整体任务与成员委派的关联。成员内部的搜索、编辑、测试
循环和原生 subagent 由运行时自主组织，继续遵守既有权限与证据要求，不逐一编排为 Fabric
业务节点。串行或并行只是执行顺序；多个 Resident Agent 步骤不自动构成 Team，具备团队
协作关系的工作即使串行也可以属于 Team。

角色定义职责；成员保存长期身份与经验；Resident Agent 执行实例使用所选运行时完成成员
当前工作；session 保存一段工作上下文。更换 OpenCode/Pi 不更换成员身份。两种场景共用
执行能力，不意味着同一活动实例同时接受互不相关任务的双重指挥；同一任务保留一个明确
业务负责人，Fabric 实施控制不会使其成为第二业务负责人。

Q27 确认：团队负责人是成员承担的角色，可以使用 Pi 或 OpenCode；DSH 继续承载 Guide
与既有产品能力，不为每个团队额外安排隐含的 DSH 业务负责人。Campaign 委托团队时，外层
owner 负责整体业务，团队负责人负责被委托的工作。当前 owner 入口与 DSH 会话绑定的
实现需要适配，不能以更换角色配置代替身份与授权接入。

Q29 进一步明确 HimaTeam 是可被不同入口调用的基础设施，而非独立页面限定的功能：

- Campaign/Fabric 可为成员提供明确上下文、任务与协作要求，并调用团队完成业务工作。
- 普通 session 或聊天、讨论项目可通过对话创建团队，指定成员的 coding CLI、角色与配合
  关系，开展交流及后续工作；不要求先构造芯片设计 Campaign。
- 固定任务可继续按 Fabric 节点运行，其中某个节点可以委派一项完整的团队工作；外层
  流程与团队内部协作分别表达，成员内部工具步骤仍遵守 Q24 的自主执行边界。

这些用法复用同一套团队能力，不按入口分别建设执行系统。

Fabric 是 Hima 自有的业务执行基础设施，DBOS 是它使用的持久执行内核。Pack 方法及获准动态
任务定义工作内容和依赖，Fabric 落实合同、环境、权限、验证与结果事实，Hima 的流程解释器在
DBOS 中推进、等待与恢复。DSH 承载会话、模型/工具、插件宿主及既有 Guide/owner；Team 组织
成员的业务分工，Resident 自主完成工作。这些职责不要求各自部署为独立服务。

团队委派与节点交接沿用“实际产物收取、合同验证、已验证交付持久保留、必要资源收束、结果提交”
的边界，下游消费已提交值与产物引用并自动接续，无需 owner 逐次机械 complete。消息收到、
原生回合结束、交付完成、Goal 达成分别表达；DBOS 不能代替外部效果和资源核对。现有 ATCS
Resident 交付之后是评估和打包，脚本/ECO/checkpoint 可交付不代表已完成后续物理采用或签核。

长期积累的业务资产包括 Pack/Skills、团队方法、获准经验、来源与工程成果。新模型、Agent 或
知识组件通过经过验证的适配合同加入，原生会话与后端细节不成为业务调用者的必要知识；能力
不足时限制用途，不承诺任意组件无条件兼容。主要新增 OAR、Pi、Hindsight，升级 DSH；已有
OpenCode、Fabric、DBOS、Host 与数据库继续复用，取消 Zulip/IM 的决定保持。

### 组队与工作空间

用户主要通过对话创建、修改可查看和保存的团队定义，明确职责、知识、工具、工作范围与交付
要求。角色定义职责；成员承担角色并保留自身经验、特长和反馈。执行会话可在任务结束后释放，
成员身份和经验继续保留，更换模型或运行时不要求丢失培养结果。

Q31 确认：对话创建或修改的团队形成明确、可查看、可保存与版本管理的配置资产，包含成员
选择的 CLI/模型、角色、Skills、协作关系与交付约定，支持导出或纳入项目 Git，用户不必
手写文件。API key、机器路径等本地绑定分开保存。Campaign 与会话入口复用团队定义，
Pack 可携带建议定义或引用已有定义；每次执行记录实际使用的版本。聊天历史不是唯一
配置来源。

Q32 确认：新定义默认用于新任务，活动任务继续使用已记录版本；人类可明确要求当前任务
采用修改，系统记录变更，在合适的工作边界交接后继续。暂停、停止、权限撤销和事实纠正
及时处理，不受定义版本固定的阻碍。CLI/模型切换等需要重建上下文的修改先交接再接续。

Q33 确认区分两种复用：“交给现有团队”沿用成员身份及有权使用的经验，每件工作仍有独立
任务上下文；“按定义创建新团队”复制角色、Skills 和协作配置，建立新成员身份与工作空间，
不默认复制原成员私人记忆和项目历史。已批准的通用方法可明确携带，跨项目材料遵守既定
引用和授权规则，不建设跨项目成员排班池。

角色的做事方法以 Skills 为主要载体，可按职责选择、组合和调整。Matt Pocock 的 Skills、
Compound Engineering、BMAD 等均可作为方法来源，不绑定某一家方法学或把其完整流程固化为
平台架构。引用方法与引入运行依赖分开处理。

可定义、可编排的角色是产品核心。成员在任务中以该角色承担责任，拥有独立上下文，参与多轮
交流、交接和复核，并保留可用于后续工作的经验；不能将团队能力缩减为临时 spawn 后收取一段
回答。是否使用原生 sub-agent 是运行时的实现选择，不能替代成员身份、职责和协作契约。

每个团队拥有随团队保留的工作空间，首期以任务和成员工作视图承载协作，不建设群聊、频道、
话题线程、@、在线状态或独立 IM 系统。用户可以查看目标、分工、依赖、阻塞、交接和成果，
打开成员详情查看运行时实际提供的输入、输出、工具调用及产物，并选择成员追加要求与附件。
未观测到的内部行为不补写，不要求暴露模型内部推理；持久记录与实时临时输出分别表达。
Guide 仍是独立的对话入口，可以创建或调用团队；团队交互不强制由 Guide 转述。

成员间仍必须能直接提问、传递发现、请求复核与交接成果。Host 在现有数据库内保存带真实
发送者、收件成员、任务和材料引用的协作消息；复用 Fabric/DBOS 和 OAR 送入获授权的成员
执行上下文。消息不是新的执行内核，模型说“已发送”必须对应持久接收回执；无法确认运行时
是否收到时保留未知并核对，不能盲目重发工程动作。具体接口在实施计划中冻结。

Q29 确认“团队”与 Campaign、Data Insight 作为同级产品入口，用于管理团队和进入工作空间。
会话与 Campaign 也可直接创建或调用团队；从 Campaign 可进入被委托的团队工作并返回原
业务。用户不必为了使用团队而先离开当前业务、另到团队入口重复建任务。

团队定义与工作空间跨任务保留，成员执行会话按工作需要启动和释放。每件完整工作在团队空间内
有自己的任务空间，保存目标、契约、材料、交流和交付；各成员拥有独立工作上下文并承担具体
任务。不设计跨项目共享成员的排班池。需要独立判断时先分别形成意见，再交换复核信息；共享
工作空间不等于将全部记录灌入每个成员上下文，也不自动扩大项目材料访问范围。

团队空间显示真实成员输入输出、工作进展、阻塞、交接、复核和成果引用，保留发送者与相关任务身份。
不能由一个模型拟写其他成员的对话来制造协作感。用户可以从消息进入实际工作记录、工具轨迹
和产物，直接补充要求、暂停或停止相关工作；消息保存、运行时接收与请求实际执行分别表达。协作记录不自动
成为已采纳经验，执行与成果仍按团队契约判断。

Q25 确认：给团队的新目标默认由负责人整理为可见任务；首期用户在已有任务中选择成员追加要求时，
成员可在既定职责与授权内处理，请求和结果关联当前任务、对负责人可见，不要求每次经负责人
转述。改变整体目标、验收或超出当前范围时，明确记录任务变更；普通交流不自动派工。

Q35 的按事件唤醒语义保留：定向要求、明确派工、交接和所等待的结果到达触发相关成员；普通
讨论与进度作为可读取的上下文，不默认使全员调用模型。已接任务的成员自主推进，不需人
逐轮催促；忙时普通消息排队，暂停、停止、撤权和重要纠正及时处理。自身发言、已读和
普通状态通知不形成自动回复循环；集体讨论明确参与者和收束条件。

### 对话附件与文档讨论（用户补充）

用户明确要求对话窗口能直接附加文件，尤其支持产品讨论中提供文档。该要求适用于 Guide、
团队任务与定向追加要求等入口；工程可依托 GitHub，产品讨论不能要求用户先准备代码仓库或
只填写本机文件路径。附件是交付给对话参与者的材料入口，不要求用户先操作独立知识库。

拟议交互包括选择/拖入文件、发送前查看附件、与消息一起提交，以及打开原件和查看读取
状态。文件已保存、内容已解析、Agent 已实际读取和已纳入长期知识须分别表达；不支持或
仅部分可读时明确说明，不能以文件名推断内容。这些交互细节、格式清单和大小限制待验证
并纳入后续规格，不表示现有聊天壳已经实现完整的文档讨论闭环。

### 运行时与部署

首期必须支持 **Pi 与 OpenCode 在同一团队混编**。成员可配置不同模型和 API key，独立于
HimaHarness 自身的 DeepSeek 配置。OAR 已由用户选定为接入组件；不能以接口存在代替实际混编
资格，运行时、模型兼容性与上下文压缩能力仍需验证。

用户在本轮开源调研后确认：必要时可以升级 DeepSeek Harness。当前固定版本是现状，不是
HimaTeam 的设计上限；若升级能够承接所需原生能力或减少兼容补丁，可选择升级路径。具体版本
依据源码差异、插件兼容组合及现有 Hima 功能回归确定，同时核对历史会话与运行数据的兼容和恢复。

用户在有使用权限的本机或办公局域网服务器运行 HimaHarness，在平台内配置并启动团队。
Q26 明确首期安装交付：macOS 与 Linux 都必须能在本机运行完整 HimaTeam 环境，Hima Harness
安装包配齐所选组件、运行依赖以及 OpenCode、Pi，不要求先部署 Linux 服务器，也不把 Mac
限制为远程客户端。模型服务地址、API key 和具体工作所需授权由用户配置，不意味着安装包
包含外部模型服务或商业 EDA 工具。具体打包机制、资源需求与平台兼容性仍须验证；不以人工
预装依赖的开发环境代替安装交付验收。

Q34 接受的受管 Linux 环境仍是必要时可用的方案；取消聊天服务后，不再因群聊默认引入 VM。
Hindsight 或执行隔离确有需要时，macOS 安装包可携带由 Hima 管理的 Linux 虚拟运行环境，承载对应的
服务组件。用户不另装 Docker、不另备服务器，Hima 管理启动、退出和数据生命周期。
接受随之增加的包体、资源和维护成本，但具体 VM/容器引擎、资源需求和组合安装资格尚未
验证；该环境不用于退出后持续执行任务，也不替代现有 Fabric/DBOS 执行权威。

首期不要求外网 Agent 接入、跨局域网协作或复杂互联网通信体系。主要场景使用用户自行部署
的模型，预算配置保持简单、可选，不建设复杂额度分配和计费系统；各 Agent 应具备基本上下文
压缩能力。压缩工作上下文与长期经验沉淀分别处理，既有 Campaign 预算和已配置约束继续有效。

当前首期组件为 **OAR + Pi/OpenCode + 必要的 DeepSeek Harness 升级 + Hindsight**，沿用
现有 Host/Cordis、Fabric、DBOS、数据库与资产能力。此前 ADR-0023 的 Zulip 必选决定由

## 驻场工程 Agent（2026-10-02，当前产品验证）

## 诚实性与知识资产

库分析本身必须独立成立：从质量、能力与机会出发，说明这套库值得做什么、需要做什么、哪些改进
可能转化为设计收益；具体 Design 未提供时，潜在收益仍是带条件的研究判断。Design 加入后，把库
信息与具体设计结合，给出设计指导；不能预先将其作用限制为原型 Usage Lens 的问题重排。
芯片设计者与 DTCO 方法学工程师不作为互斥产品路线。

第二轮访谈明确本次 demo 的边界：以**同一套完整库内部的洞察**为主体，覆盖其分支、PVT 与 corner；
输入不全时开展局部分析并说明覆盖。跨版本、跨 PDK、跨供应商比较暂不纳入本次 demo。
Design 侧先保持简单：由 timing paths 聚焦 critical path 上的 cell，由 Verilog netlist 统计 cell
使用数量；未来结合 DEF 分析相对物理位置、频繁出现及相邻的 pattern。当前范围不因“设计指导”
自动扩展为 cell 替换优化、约束优化或执行完整 P&R 的功能。

Library 侧的电气/物理评估与跨视图关联要求如下：

- **Liberty 评估**：逻辑功能、pin/arc/model 完整性，PVT、时序、功耗、约束、变化和版本比较。
- **LEF 评估**：cell/pin/PORT/OBS 的几何、层与位置，以及结合声明的技术规则、via、routing grid
  和环境分布计算的 pin access 概率、联合冲突、逃逸瓶颈和敏感性。可先计算参考环境下的模型概率，
  未来用实际 placement/routing 分别校准规则覆盖、环境分布与算法成功率。
- **统一关联**：在同一库版本、cell/pin 分析中呈现逻辑、电气和物理结果。跨视图映射须有版本、
  来源与映射依据，不能只凭同名自动确认；多 PVT 电气视图可以关联同一物理 master，但须证明对应关系。
  不把 Liberty area 与 LEF 宽高乘积未经单位/语义核对就判为一致或不一致。

仅有 `.lib` 或仅有 `.lef` 时可完成相应评估，另一侧和跨视图结论显示缺失/未知；缺失不替换为零或
默认通过。两侧具备且身份明确时提供联合比较，例如“电气表现更好，但 pin access 风险更高”的 cell
候选及其条件。测量、文件声明、模型概率与未验证推断分别标注，不合成无条件的库质量总分。

面向用户只呈现三类分析，不把 Catalog、图表、Finding、Rule Studio、报告和 Action Center 分别包装成
多个产品功能：

1. **库健康与发布风险分析——这套库可靠吗？** 检查版本与 corner/view 身份、结构和单位完整性、
   Cell/pin/arc/constraint/model coverage、跨 PVT 一致性、数值趋势异常和 revision regression，帮助
   用户判断能否交付、哪些问题需要阻塞或复查；包括 LEF 几何/映射缺项和有证据的接入风险。
2. **库性能与竞争力分析——这套库强在哪里、弱在哪里？** 分析 Cell family、drive/VT/PVT、delay、
   transition、constraint、area、leakage、internal power、variation 和工作域，帮助用户比较版本/方案、
   识别优势、短板和 Library 开发优先级，并比较相同物理评价条件下的 pin access 概率与敏感性。
3. **设计影响与行动分析——它对我的芯片意味着什么？** 将 Library finding 与当前设计实际使用的
   Cell/instance、path/endpoint、slew/load、mode 和商业工具结果连接，帮助用户决定先处理什么、下一项
   最便宜验证是什么，以及是否需要 candidate、STA/SPICE 或 matched implementation。

自定义规则、数据探索、可视化、证据追溯、报告和后续动作是三类分析的共同能力，不作为一级产品导航。
用户可以在分析过程中用自然语言增加组织规则或保存分析方法；产品把它们编译为受控、可测试、可版本化
资产，不让自由模型代码直接成为结果权威。Liberty API 承担其已验证的电气视图读取能力；LEF 评估需
独立验证物理解析与规则计算，但结果归入同一 LibInsight。设计采用、真实 PPA、相关性和芯片结果
仍须由 HimaHarness 的设计证据与实际 EDA 验证补充，不能由 Liberty 或 LEF 模型概率单独推导。

2026-09-29 原型体验确认：保留 Overall 风险矩阵、直觉式点击展开、input transition × output load
Heatmap 及可靠性标示、每个 cell 的 Sensitivity 呈现，以及 Overall rule configuration。
用户要求降低交互深度：每类分析尽量收敛在一个标签页内，细节在当前标签内展开，避免多级下钻后
逐层回退；数据与由其得出的结论并排展示，并直接表达问题实际影响，缩短信息、洞察到后续行动的距离。
第二轮确认以风险等级排序，同时保留问题、幅度、影响对象和后果的解释。导航采用**左侧大类标签
与顶部具体工程问题 tab**；以最多两次导航点击定位目标分析，具体内容和细节尽量在当前页呈现。
第三轮进一步确认：Overall 风险地图沿用分析标签，随标签切换/filter 展示对应的库风险矩阵；
点击某个库的风险，直接进入该库对应的分析标签页。它是全局问题总览与直达入口，不增加另一套操作逻辑。

**Design-specific 分析独立呈现**，容纳 critical-path cell、使用统计等带 Design 信息、可能较定制化
的分析；复用 Library 基础，但不采用上一轮建议的全局 Design 叠加作为默认交互。
规则配置先提供少量参考模板/预设，允许调整范围、阈值和检查项；具体数量、值和新增规则能力按后续
需求细化，不因配置入口而扩展为本次 demo 的任意算法开发平台。

Heatmap 保留数据覆盖、数值可信程度和使用适宜性三层信息，并在 input transition × output load
平面圈定可靠与不可靠区域。每个区域必须注明含义及判定依据，帮助识别 cell 的建议工作范围，并用于
针对性的 max transition / max load 约束。第四轮确认具体要求：

- 默认以数据覆盖、数值质量和已有使用限制圈定建议工作范围；用户性能目标可进一步收窄。数据不可靠
  与数据可靠但不符合当前目标分别解释。
- 图上先展示当前 pin/arc、corner 等条件，cell 级建议再汇总选定相关条件的共同范围，标明限制范围的
  corner、pin 或 arc。共同范围只适用于实际纳入的条件，不隐含全 corner 覆盖。
- 保留真实二维轮廓，另给一组成对成立的保守 max transition / max load 上限；必要下界或中间可疑
  区域同时标示，不能分别取两轴最大值后声称其任意组合均可用。
- 本次 demo 提供图内说明及可导出的建议清单，包含建议值、对象、corner、依据和适用条件。具体工具
  约束文件生成、写回原始库/设计及实际应用留作后续能力。

模型或规则给出的区域不能直接宣称为经过物理验证的保证。

第五轮确认使用流程：选定库后按默认模板自动开展基础分析，结果逐步呈现；配置变化只更新受影响的
结果，并尽量保留当前 cell、corner、图表位置等浏览上下文。尚未完成的分析显示进度与覆盖；长时间
计算单独显示状态，用户可继续浏览已有结果。旧结果与更新中的条件必须可区分。

AI 同时承担三项职责：主动解释重点发现；结合当前 cell/图表区域、数据、规则与条件回答追问；根据
自然语言调用已有分析能力并呈现结果。优先做好后两项，回答能指回图表和证据；新增检查算法的自主
研究留待后续。自动分析、规则计算及 AI 回答都沿用现有受控执行和事实归属，不建立另一套分析权威。

一线 AE 的竞品观察进一步明确共同能力：trend 分析允许切换 output load；用户可过滤不关注的 Cell；
同一视图可用类别、数值与 corner 等三个维度联合表达；客户可以增加自己的 Python 分析算法。HimaHarness
应在三类分析内部提供这些能力，但 Python 算法须使用受控输入/输出 schema、fixture、版本和执行边界，
不能成为无审计的自由代码。Milkyway、NDM 等第三方数据库不属于 Liberty API 的直接读取范围；只有在
Site 具备合法工具、许可和只读访问时，才通过独立格式 adapter 投影到相同语义身份，并保留原数据库为
权威。本要求不扩展为“任意格式天然支持”的产品承诺。
见 [LibInsight 三类用户分析与统一视图决定](adr/0012-library-intelligence-has-three-user-analysis-surfaces.md)
和 [pin access 概率模型](package-development/library-intelligence-platform/research/pin-access-probability-model.zh-CN.md)。
以上是现行产品要求；已有 Liberty 有界切片的通过证据不代表 LEF 或联合评估已经实现。

### 产品任务与外部评估的职责纠正（Issue #83）

用户明确：“Hima Harness只知道ATCS，用ATCS去fix timing；忠实完成这件事。对比由我们做，不是Hima Harness；任务不是对比，而是用ATCS fix timing。”新生产 Pack 因此不执行独立 Serial AutoFix 对照，不要求对照材料，也不以超过对照作为 Goal。产品负责真实修复、保留最佳状态、报告实测 Timing/残余/限制并交付可用产物。AutoFix 可以继续作为修复手段。外部评估者在运行后比较分别保留的实际证据；比较不进入 Harness、Campaign Agent 或 FL 的用户任务。历史已冻结方法和记录保留原语义，不热改活动 Run。
