# HimaHarness Product Decisions

The record of decisions made while grilling [the product idea](product-idea.md), in the order they were made. Each entry says what was decided and why, so a future reader does not reopen it without a reason. Terms are defined in [CONTEXT.md](../CONTEXT.md). Engineering decisions that are hard to reverse get an ADR under `docs/adr/`; this file is for product decisions.

Date of the grill: 2026-09-08. Decisions made before the grill, while brainstorming the idea, are listed first.

## Before the grill

- **B1. Host and ecosystem.** HimaHarness is built on DeepSeek Harness and is part of its ecosystem, from day one, so it can use dsh's agent loop, tools, sessions, storage, web UI, skills, and any plugin including AI coding plugins. Chosen over Claude Code, opencode, and an own harness. The reforge's failure is read as a mid-project switch, not as dsh being unusable.
- **B2. Thesis.** Campaigns that end in facts. Outcome first; packs are the method, the harness the runner, evidence the guarantee.
- **B3. First path.** A DTCO or back-end engineer runs an exploration pack. Chosen over the simpler flow-execution path because it is what the first customer buys.
- **B4. Business.** A vendor product for many customers. Pack authoring and a pack source are core, not later.
- **B5. Capacity.** One builder plus AI agents, first customer-visible result in about three months.
- **B6. Coding capability.** HimaHarness is not sold as a coding tool, but it codes: on-the-fly scripts and tools inside exploration nodes are a first-class ability.
- **B7. Build order.** Reuse the dsh plugin ecosystem for everything that is not Hima's own semantics; custom code only for the fabric's graph language, the ledger semantics, the judge, and the pack contract. Reuse is verified on a running host.

## Round 1

- **D1. Terms.** Campaign, Run, Job are three distinct words. "Task" is retired for these meanings.
- **D2. A campaign holds several loops.** Loops appear at different stages as the pack defines. The fabric is built from a few basic elements with finite states and attributes; the connections carry the business logic. Rejected: splitting the first campaign into one loop.
- **D3. Goal shape.** One primary target plus declared constraints, all typed, all checked by the judge, stated without ambiguity, immutable for the campaign. A new goal is a new campaign.
- **D4. Budget meters.** Time, EDA resources, parallel job count, licences, and a retry allowance per node. Tokens and money are not budgeted because customers run their own models. Rejected: token and money caps.
- **D5. Where the harness runs.** On the engineer's own machine. EDA jobs run on the site through HimaChannel and HimaShell, because that is how chip design works. Rejected: running the harness inside the site's LAN.
- **D6. How the judge decides.** Every pass or fail verdict comes from deterministic rules over typed ledger values. A model may add only qualitative findings the pack explicitly declared as judgment calls. A model never overrides a computed verdict.
- **D7. Judge isolation.** A separate agent session with its own instructions, no access to the executor's conversation, read-only on the ledger. Every verdict cites the ledger record IDs it used. The executor cannot write verdict records. Same model is fine in phase one.
- **D8. Blockers and retries.** A node retries within its retry allowance, three by default, set per campaign. EDA tool and site infrastructure failures become hard blockers when the allowance is spent. Failures in Hima's own tools are Hima's to fix by self-repair first. A blocked node keeps its state and resumes when cleared. Phase one notifies in the workbench only.
- **D9. Model.** deepseek-v4-flash through the DeepSeek API. No local model for now. Credentials are set by the owner out of band and never written by the agent.
- **D10. Second person.** A real chip-design engineer who has used this EDA server, named before month two.
- **D11. Segment.** Fabless and IP teams on commercial Synopsys and Cadence flows. The open-source stack is a demo path, never the proof path.
- **D12. Prior repositories.** Studied, never imported or quoted, so the development context stays aligned and carries no integration debt.
- **D13. Legacy package.** Reference at most. The pack is redesigned from scratch to be simple enough to build quickly under HimaGuide.
- **D14. dsh version.** Track the newest published version. dsh-facing code is arranged so a breaking upgrade costs days, not a rewrite; the arrangement is ADR-0001.
- **D15. Enforcement.** Local git hooks plus a scripted real-host suite. No GitHub Actions.
- **D16. Experience.** A technical report per campaign: facts and reasoning, S.M.A.R.T., readable by machine and by people.

## Round 2

- **D17. First campaign's design and technology.** AES on TSMC28 with the celluzi and bool2cmos toolchain, the only combination on the site where every loop can run. The site's toolchain moved to the 2025 releases after the reference runs, so a small command-level bring-up is part of the first campaign.
- **D18. Job survival.** tmux, one named session per job, session name and pid recorded as the job ID.
- **D19. Permit and workspace.** The permit is a plain editable file encoding the site owner's operating rules. Campaign workspaces live under `/data/eda/project/hima_harness/<campaign-id>/` on the reference site.
- **D20. Self-repair in phase one.** In scope for Hima's own tools, with a record of every change. Risk mode in its broad sense, touching site infrastructure or pack delivery, stays out.
- **D21. Authoring is Guide-led.** The author describes the business in plain language and points at the Golden Flow. HimaGuide carries the work through a skill pipeline, one skill per stage: grill, spec, fabric, test, release. In scope for phase one; the builder is the first author.
- **D22. "Latest" means newest published.** Not the npm `latest` tag.
- **D23. Host coupling.** Not host-independent. dsh is used directly on the seams that are documented-public and were stable across tracked versions; only the seams that moved are wrapped behind one Hima interface each, with a booted-host contract test per seam. Recorded as [ADR-0001](adr/0001-dsh-seam-coupling.md), grounded in `docs/research/2026-09-08-dsh-architecture-and-integration.md`.
- **D24. Enforcement without CI service.** Pre-commit runs lint and unit tests, pre-push runs the contract-on-fixture suite, a scripted real-host suite runs before any merge with its record committed.
- **D25. Capacity and defaults.** The site config declares capacity: cores, memory, parallel job cap, licence counts. A campaign inherits the site's allowance unless lowered at start. The fabric's logical parallelism is capped by the site.
- **D26. Reference set.** Demo transcripts and final runtime snapshots, legacy package specs, and the untracked flow tree, preserved as one content-hashed archive outside the product repo, read during authoring, never imported.

## Round 3

- **D27. Authoring artifacts.** Grill ends in a pack intent record. Spec ends in one human-readable pack spec. Fabric ends in the compiled graph plus its tool list, missing tools flagged. Test ends in a test record from a real site run against the Golden Flow. Release ends in a versioned pack with its check results. Test means a real site run; fixture-only packs are not releasable.
- **D28. Pack anatomy.** A folder of plain files the author can read: a Markdown spec, a semantics file, a graph file, a tools folder of small scripts, a knowledge folder, a version file.
- **D29. Fabric elements.** Four node kinds: act, judge, explore, wait. Fork and join are edge patterns: edges branch out so nodes run in parallel, and converge back into a judge node. End is the absence of outgoing edges. Node state is a small fixed set; business meaning lives in the ledger.
- **D30. HimaGuide in phase one.** The dsh web profile with a Hima client module: dsh's chat is the conversation, Hima adds the campaign and fabric views.
- **D31. The reference campaign.** The archive is built around `gr_20260821_020514_327246`, the finalized autonomous-Fmax run whose graph is a superset of the cell campaign, paired with `gr_20260816_060117_938542`, the finalized cell run with an exportable validation package, and `gr_20260818_200934_153405` labelled as a mechanism reference for a multi-generation loop that ended not met. Plus the four demo transcripts and snapshots, exported JSON of those runs' rows from the legacy runtime store on the Mac, the legacy package specs, the untracked flow tree, and the reforge's staging directory. One tarball, one SHA-256, on the site under `hima_harness/archive/` with a copy on the Mac. The archive README states first that no run in history demonstrates a converging multi-generation loop. Built 2026-09-08: `hima-reference-2026-09-08.tar`, 1,641,953,280 bytes, 7,477 entries, SHA-256 `c96cbc970898c3ca68ae8abe458bbeb3a3abc31a72c63cd1df9f349983fd4e84`, at `/data/eda/project/hima_harness/archive/` on the site and `/Users/lluzi/code/hima-reference-archive-2026-09-08/` on the Mac.

- **D33. Parallel job cap.** Stays at one on the reference site until the first campaign has produced peak-memory measurements for DC and Innovus on the 2025 tools.

## Step 1 delivered

- **D34. Step 1 of the acceptance ladder is done, 2026-09-08.** Evidence: [docs/validation/2026-09-08-step1-acceptance.md](validation/2026-09-08-step1-acceptance.md), re-run clean after the final-review fixes as [docs/validation/2026-09-09-step1-acceptance.md](validation/2026-09-09-step1-acceptance.md), which is the record of the shipped code (setup and hold now judged in one run). On a booted DeepSeek Harness host, the three real opene902 reports on the reference site were read over SSH into the ledger by typed readers, judged by the three shipped rules (setup all-paths FAIL, setup reg2reg PASS, hold PASS, each citing its observation), every typed value matched the site's handoff metrics exactly, records survived a host restart, and the same chain ran through the workbench's Hima namespace with the browser module served. Every remote command was read-only. Tickets #2–#8 are closed with their evidence on GitHub.
- **D35. The host-to-browser interface is HTTP routes on dsh's web server, not a Typert remote service.** Recorded as [ADR-0002](adr/0002-hima-remote-over-webserver-routes.md); a deviation from ticket #7's wording, taken because dsh's remote generator has no out-of-tree path.
- **D36. Two facts learned on the way that later steps must carry.** Each observe creates its own run, so a run spanning several observations needs a run-id option before step 2 (fabric). And the Innovus post-route summary carries no clock period; the reader reports it unknown.
- **D37. Pack anatomy in step 2 is four files.** `PACK.md`, `contract.yml`, `graph.yml`, and `tools/`. Of D28's list, the semantics file, the knowledge folder, and the version file are deferred until a pack needs them: the semantics a pack produces are the readers' declared outputs and the contract names the reader per output, knowledge has no consumer before HimaMind, and a version waits for the first released pack. D28 remains the target shape; this records the narrowing so nobody reads the four-file pack as the whole plan. The contract's `argv` is what runs and what the Permit decides on; the script under `tools/` is its human-readable twin.
- **D38. A chooser is data, like a judge rule.** One YAML file per chooser id under `packages/harness/choosers/`, beside `rules/` and shipped with the bundle, referenced from an Explore node by `<id>` or `<id>@<version>`. The file states what it reads out of an observation, the one parameter the pack binds, and an ordered list of clauses over the constraint and goal verdicts, whose arithmetic is `sum`, `neg`, `abs` and the names it declared — evaluated by the harness, checkable rather than programmable, exactly as a rule's predicate is. The pack binds the chooser's parameter in `graph.yml` (`bind: { guardBandNs: 0.05 }`), because a guard band is the pack author's judgement and not the chooser's, and `/hima pack check` resolves every chooser id and holds that binding against what the chooser declares. Reason: the spec (#9, user story 22, #13's AC3) says the chooser is pack data so that the choice is inspectable, and judge rules already set what "data referenced by id" means here — a chooser in TypeScript sends a pack author looking for `choosers/timing-push.yml` beside `rules/clock-period-at-most.yml` and finding nothing. This reverses the shipped-as-code deviation the first cut of #13 took and wrote into CONTEXT.md. A general expression language is out of scope until a pack needs a form these cannot state; widening the clause language is then a deliberate change to one file, not an escape hatch.

- **D39. HimaGuide is a desktop window around the hima profile, never a browser tab.** The workbench is delivered as one native window that starts `dsh --profile hima` itself and loads that host's own page; the harness never hands a URL to a browser (`--no-open` is not optional). `packages/desktop` is that window and nothing more: an Electron main process, a native menu, a remembered size, a starting page and a page that shows the host's stderr when it fails to boot. It contributes no plugin, patches no dsh package, and gives the loaded page no IPC surface at all — the host-to-window interface stays the `/hima/api/` routes of [ADR-0002](adr/0002-hima-remote-over-webserver-routes.md), and dsh's chat stays inside the page (D30). Closing the window stops the host. Reason: a campaign runs for hours, holds an EDA licence, and can be cancelled or resumed; a browser tab is somebody else's window — it is closed by accident, restored into a session the harness knows nothing about, shares a cookie jar with everything else on `127.0.0.1`, and gives a person no place to look when the host does not start. A window whose lifetime is the host's lifetime makes "the workbench is open" and "a host is running" one fact instead of two. Two alternatives set aside. *A separate renderer UI over the routes*: it would mean building and keeping a second front end for what dsh's own web app already renders, and would put the campaign views somewhere dsh's chat is not — the opposite of D30, which says HimaGuide is the dsh web profile with a Hima client module in it. *The browser tab*: rejected for the reasons above; it is also what `--no-open` exists to prevent, and every launch of it leaves another thirty-day `dsh-auth-*` cookie on `127.0.0.1`, which a shell with its own cookie jar can sweep and a browser cannot. Recorded as [ADR-0003](adr/0003-desktop-window-around-the-hima-profile.md), grounded in `docs/research/2026-09-09-dsh-desktop-shells.md`: neither existing community shell (`fendouai/deepseek-harness-desktop`, `dataelement/dsh-desktop`) can be depended on or forked, so their patterns are borrowed under MIT with attribution in `packages/desktop/THIRD-PARTY-NOTICES.md` and nothing else is taken.
- **D40. Step 2 of the acceptance ladder is done, 2026-09-09.** One real generation of the opene902 timing probe ran on the reference site from a booted host: the flow copied into a campaign workspace (six pieces, 56 MB), synthesized there through `make` in tmux under the campaign's own container, the qor report read at the requested 2.07 ns, the setup rule failing on a measured slack of −0.16 ns, the goal rule passing, and the chooser relaxing the period to 2.28 ns by period + |slack| + guard, citing both verdicts and the observation; the run view carried the path over the real web profile and the same Run read back unchanged after a host restart; every remote command the harness sent is in the record, and every write it asked HimaChannel to make landed inside the campaign workspace — which is what the record's own check claims and no more: "This is about the commands this harness sent, which are the ones it is answerable for. What `make` and the tools it starts write once the Job is running is not covered by this check." What the Job itself wrote is bounded by where the flow copy is (D19) and spot-checked by the record's `site-flow-root-untouched`, not proved here. Evidence: [docs/validation/2026-09-09-step2-acceptance.md](validation/2026-09-09-step2-acceptance.md), every one of its 17 checks passed. The first attempt the same day failed because the pack's copy list lacked the flow's `tools/`; the harness handled it exactly as designed (three attempts, a Hard blocker with the log tail, a record saying what failed) and that record is kept as [2026-09-09-step2-acceptance-attempt1-failed.md](validation/2026-09-09-step2-acceptance-attempt1-failed.md). The campaign workspace and its container are left on the site as evidence; removing them is the owner's call.

- **D41. Step-2 deviations from the #9 spec, accepted.** The final review of step 2 held the shipped code against the #9 spec and found seven places where they differ. Each is accepted as it stands, recorded here so nobody reads step 2 as the spec and nobody reopens one of them without a new reason.
  - **The reference Permit lists `eda` and `make`, not `eda`, `make`, `tmux` and `cp`.** The spec named four wrappers; the shipped `sites/linglong/permit.yml` names two. `cp` and `tmux` are not a pack's wrappers at all — the copy that prepares a workspace and the plumbing that launches and watches a Job are HimaChannel's own verbs, decided by HimaShell against the Permit's write roots before they are sent, and a Site owner who struck them from a wrapper list would not thereby stop them. A wrapper listed there, by contrast, runs with whatever arguments a Job names it with, so `cp` in that list would hand a Job an unconstrained copy to anywhere this login can reach — which is not what agreeing to workspace preparation means. The file stays a statement about the Site owner's own tools. Stricter than the spec: nothing a Site allows grew.
  - **Node states gained `waiting-for-slot` and `reconciled`.** The spec fixed six. `waiting-for-slot` is #15's own acceptance criterion in a word ("the run view says it was waiting for a slot"): a node held by the Site's parallel job cap has not failed and is not running, and a state is how a person is told which. `reconciled` is the transition a second process writes when it picks up a node's interrupted attempt after a restart, carrying what it found of that attempt's Job — still running, finished with the exit the launch wrote, or gone. It settles nothing; without it, that a different process took the node over is nowhere in the record.
  - **The record union gained `workspace`, `cancel` and `resumed`.** The spec listed four kinds and said the union grows. `cancel` and `resumed` are the spec's own cancel and resume text made into records, because a person's action on a Run is exactly the kind of thing HimaLedger exists to hold. `workspace` is the one the spec does not imply: a Campaign's workspace and its container name are written nowhere else, and without a record of them a later cleanup could not know what to remove and a restart could not know where a Run runs.
  - **`/hima run` takes `--period`.** The spec's run command takes pack, site, goal, time box and retries. The first Strategy is a sixth, defaulting to the goal's own target period, because a Run whose first generation must be the goal cannot probe a Site at a period a person chose — which is what the acceptance script needs to ask for a period tighter than the Site's last result without changing the Goal.
  - **`/hima pack check` and `/hima pack prepare` are two verbs.** The spec had one verb that validates and then prepares. Split because they differ in the one way that matters on a customer's machine: `check` reads a pack and a site file and touches nothing on a Site at all, so a person can ask whether a Site can host a pack without anything being created there. Preparing is the verb that writes.
  - **The time box does not run while a person is asked.** The spec puts a time box on the Run. A Hard blocker is by definition a wait on a person, and a Budget meters the design and the EDA environment (CONTEXT.md, *Budget*) — charging a person's response time to the Run's time box would end Runs for a reason that is not the Run's. `waitedMs` is metered separately and is on the record.
  - **Licences are declared on the Site but not metered or recorded.** The spec has EDA resources and licences recorded against the Run; `capacity.licences` is parsed from the site file and read nowhere else. Nothing in step 2 ran long enough or wide enough for a licence count to bind — the reference Site's cap is one Job (D33) — and no sub-issue carried it, so it fell between #13 and #15 rather than being decided. It is step 3's, and until then a Budget's licence line is a declaration, not a meter. **Closed by #21**: a pack's contract now declares what a Job of each tool holds, a launch is counted against the Site's declared seats in the same step and by the same rule as its parallel job count, and `meters.licenceMs` is what a Run held.

- **D42. The desktop driver is the test seam for the product's window, 2026-09-09.** Every step-3 contract test drives the product through the desktop shell in a driver mode: the same Electron main process a person runs, started with `--driver`, which prepares the home, launches the real dsh host, exchanges the token in its own window's session, loads the page, and then answers a small set of requests as JSON lines on its standard input and output — report the host and the session, open a page under the host's origin, read a marked region's rendered text and state, wait for a region to show a text, click a marked control, take a screenshot, quit. A test asserts on what the window renders and on what the routes answer with the session the shell established, and on nothing a person could not see. Reason: the user's direction that the harness looks and acts like a desktop app and is tested as one — what the tests prove has to be what the engineer sees, and step 2 exercised the product a person uses with one smoke test while everything else went through a booted host and a test-only web boot. One seam for the whole of step 3, containing the same booted host the step-1 and step-2 tests use one level up, so #25–#31 all test through it and the acceptance starts the Campaign from the window. The driver is the shell's own code and patches nothing in dsh; reads and clicks run from the main process through `executeJavaScript` and `sendInputEvent`; the page keeps zero IPC (D39); the navigation fence stands in driver mode and every URL outside the host's origin is refused in its words. `pnpm run desktop --site local` seeds a developer's home with the same stand-in flow and local site the suite proves things on, so a Loop is watched converging in the product before it touches the reference site. Two alternatives set aside. *WebDriver or Playwright against the page*: a dependency on a browser-automation framework and a second way of reaching the window that is not the window's own, with its own driver binary to keep in step with Electron's Chromium — and the shell already owns the window it would be automating. *Route-only tests that never open the window*: what they prove is the routes, which step 2 already proves; the card, the page, the fence and the session a person actually gets would stay untested, which is the gap this decision closes. Recorded as [ADR-0004](adr/0004-desktop-driver-as-the-test-seam.md). The `--smoke` flag and the smoke test are replaced by the driver: one mechanism.

- **D43. The Loop is the pack's data and the harness's arithmetic, and the generation limit is a Budget meter, 2026-09-09.** A `graph.yml` edge may say `revisit: true`. It leaves an Explore node, leads to an act node, and is the only kind of edge a graph may close a cycle with — a graph is refused at load if anything else does. Following one is what opens the next Generation, in one write of the run row: the target node, the generation, and the Strategy the decision chose, together. An Explore node's edge is taken only when its decision chose a next Strategy; a decision of goal met or converged has no edge to take and the Run ends where it stands, `ended-goal-met` or the new `ended-converged`. What convergence means is declared on the Explore node, in its chooser's own vocabulary: `converge: { read, band, generations, generationLimit }`, where `read` names one of the chooser's `reads` (held against them by `/hima pack check`), `band` is a distance in that read's unit, and `generations` is how many successive generations must each have moved that *measured* value by less than the band. The harness evaluates it, inside `choose()`, over the values the ledger holds, and weighs three outcomes in one order: the chooser's own goal-met clause, then converged, then the next Strategy. The decision record's `chosen` carries the whole rule — the read, the band, the generations counted and the values compared — so the ending is re-derivable from one record. The generation limit is not part of that: `converge.generationLimit` is the pack's default for a Budget meter, overridable at start by `/hima run --generations <n>`, the form's field and `StartRunRequest.generationLimit`, copied to `budget.generationLimit` when the Run opens; a revisit that would open one generation past it does not, and the Run ends `ended-budget-exhausted` with `meters.endedBy: 'generation-limit'`, the decision it was not allowed to act on still on record. Every record carries the Generation it was written in, stamped by HimaLedger from the run row at append time, and the Retry allowance is counted per node per generation. Reason: the spec's own words — the Loop declared as data so the exploration is inspectable and changeable without code (user story 16), and convergence stated in the chooser's vocabulary so that "converged" is a rule over ledger values and never a feeling (17). Three alternatives set aside. *Convergence as a chooser clause that reads history*: a clause sees one generation, and "successive generations stopped moving" is a statement about several — the chooser file would have had to grow a way of naming earlier generations, which is a query language inside pack data, and D38 was explicit that widening the clause language is a deliberate change and not an escape hatch. *A loop counter in the engine*: the Loop would then be something the code does rather than something `graph.yml` says, and a pack author could not see where their Campaign goes back to, let alone change it. *The generation limit as a third convergence condition*: convergence is what the exploration learned and the limit is what the Campaign was allowed to spend learning it; folding them together would have a Run that ran out of allowance say it had stopped learning, which is the one thing a person reading `ended-converged` must be able to trust.

- **D44. The Campaign's experience is two files beside the results and two hashes on the ledger, 2026-09-10.** When a Run ends for any reason — the Goal met, the exploration converged, a Budget meter spent, a person's cancel, a graph out of edges — HimaFabric writes the Campaign's technical report into the Campaign workspace on the Site, beside the results: `<workspace>/hima-experience/<runId>.md` for the people who read it and `<runId>.json` for the programs that do. What the ledger keeps is neither file but an `experience` record holding both paths, both `sha256` hashes and both sizes, and the instant both files state as their own. It is written once, after both files are on the Site and never again — that record *is* the claim that the report is there, so a Run carrying it is a Run whose report is written, and a Run whose ending landed without one is finished by the next host's reconciliation from records that cannot have moved. The report is composed from the run view, which is the ledger folded, so every number in it is a number the card showed; the JSON is `hima-experience/1` and the Markdown is the same facts as headings, tables and one paragraph of reasoning per generation. Both are served read-only from the Site, through the channel's read-only `cat` with the hashes verified, by two routes behind the same session fence as everything else (ADR-0002); a file that no longer hashes to what the Campaign wrote is refused with both hashes named and never served as the report. Reason: the Site owner keeps the evidence with the results (D19 — the workspace, its container and now its report are left in place, and removing them is the Site owner's call), and D16 asks for a technical report per Campaign that is both machine- and people-readable, owned by the organisation and linked to the pack that produced it — a file an engineer can hand to a colleague, not a view that exists only while this harness is running (user stories 10, 11, 12, 35). One alternative set aside: *the report kept in the ledger alone*, composed on demand by the routes. It is less code and it is what the run view already does — but the ledger is this harness's own storage in an engineer's own home directory, and a Campaign's experience is the customer's: a report that lives only there is gone when the home is, cannot be read beside the results it is about by anyone who was not running the harness, and cannot be handed to a colleague without this harness to render it. HimaExperience is the organisation's archive (CONTEXT.md), and an archive that only one process can open is not one. What the ledger keeps instead is the hash, which is what makes the file evidence: a reader that fetches it back knows whether it is what the Campaign wrote.
- **D45. Step 3 of the acceptance ladder is done, 2026-09-10, on the infrastructure's evidence and not on a convergence.** The step-3 acceptance ran once on the reference site, started from the workbench window through the driver: the read-only gate cleared the Site, the form filled and the Campaign started by a click, six real generations of the opene902 timing probe at about 150 s each in one Campaign workspace under the Campaign's own container, one Design Compiler Job at a time, every generation's verdicts and decision following from the measured values, the technical report written beside the results with its hashes on the ledger and shown in the window, the same Run read back unchanged by a second shell, every command the host sent audited through the new audit route, nothing written outside the workspace. Thirty of thirty-one checks passed; the record is [docs/validation/2026-09-10-step3-acceptance-attempt1-failed.md](validation/2026-09-10-step3-acceptance-attempt1-failed.md), kept under the name its own outcome gave it. The one failed check, `ended-goal-met-or-converged`: the Campaign ended on its generation limit. Design Compiler reports a setup slack of exactly 0.00 whenever it meets the period asked, and the reference pack's chooser, `period − slack + guard` on a pass, loosened the period by the guard band every generation (2.28 → 2.53), each move equal to the band. The owner's ruling: the fault is the pack's, not the harness's. The first generation's violation (2.07 ns, −0.16 ns) already states the achievable period, 2.23 ns; a timing push that knows its business over-constrains and reads the violation, and the reference pack carries no such knowledge — it was a stand-in for a method, never the method. - **D46. Pack first: the boundary and the order of repair, 2026-09-10.** HimaPack and HimaHarness together decide whether a Campaign succeeds, and their relationship is collaborative, but the priority is fixed: changes go into the pack first, and the harness changes only for a gap no pack can fill. The order of repair when a Golden Flow fails in this harness is the pack (its graph, contract, tools, readers, rules, choosers, knowledge and words), then the pack's tools written or replaced through the workshop at run time or by the fabric and test stages at authoring time, then the harness — only when a test record or an acceptance record shows that no pack can state what is needed, and then as a generic element recorded here with the evidence it rests on. - **D47. The Strategy is the pack's, 2026-09-10.** A pack's contract declares its Strategy: named knobs, each a number with a unit, bounds and a default, or a choice from a declared list with a default, each with its words in the contract's `words:` block; a knob without words, or words for a knob no contract declares, is refused at pack check, which every start runs first, because a Strategy the window cannot say in the pack's words is one the person cannot read.
