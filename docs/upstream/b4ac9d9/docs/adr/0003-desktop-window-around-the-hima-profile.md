# Deliver HimaGuide as an Electron window around `dsh --profile hima`, borrowing the community shells' patterns and depending on neither

HimaGuide is the dsh web profile with a Hima client module in it (D30), and until now the only way to reach it was a URL — the host printed one and a browser opened it. A campaign runs for hours, holds an EDA licence, and can be cancelled or resumed from that page, which makes a browser tab the wrong container for it: it is closed by accident, restored into a session the harness knows nothing about, shares a cookie jar with everything else on `127.0.0.1`, and leaves a person with no place at all to look when the host fails to start, because the only explanation is stderr in a console nobody opened. We decided that HimaGuide's only delivery form is a desktop window (D39): `packages/desktop` is an Electron main process that starts `dsh --profile hima --host 127.0.0.1 --port <free> --no-open` as its own child, waits until it answers, follows the tokened URL inside the window's own session, and loads the page in one `BrowserWindow` titled HimaHarness. Closing the window stops the host. The harness never opens a browser tab.

The shell adds nothing else. It contributes no plugin and patches no dsh package; the page it loads gets no preload bridge and no IPC channel; the host-to-window interface stays the `/hima/api/` routes of [ADR-0002](0002-hima-remote-over-webserver-routes.md) and dsh's chat stays inside the page. Two pieces of logic it shares with the rest of the repository: `src/host-launch.ts` — the argument vector, the launch-token parser, the readiness probe and the graceful stop — which `test/contract/support/boot-host.ts` boots every route test's host with, so the window starts a host exactly the way the contract suite starts one; and `src/hima-home.ts`, the four operations that make a hima home, which `createHimaHome` makes every test's throwaway home with, so the window prepares a home exactly the way the suite prepares one. That second module is why `pnpm run desktop` needs nothing installed first: it makes the profile in whatever `$DSH_HOME` names (`~/.dsh` by default, as dsh resolves it) and prints what it did.

Electron rather than Tauri, on one deciding fact: dsh names its session cookie after the request authority, which includes the port; cookies are not port-scoped; the cookie lasts thirty days. A fresh port per launch therefore accumulates one `dsh-auth-*` cookie per launch on `127.0.0.1` until the request header exceeds what Node accepts and the workbench answers HTTP 431 for ever. Sweeping them needs programmatic access to the window's cookie jar, which Electron's `session.cookies` gives directly and Tauri's WebView does not expose. The cost is a larger runtime, which for a developer-run window is not a cost we are paying yet — packaging is out of scope for this ticket.

## Considered options

- **Depend on, or fork, `fendouai/deepseek-harness-desktop` or `dataelement/dsh-desktop`.** Rejected on the evidence in `docs/research/2026-09-09-dsh-desktop-shells.md`: both are `private: true` and publish only installers, neither builds outside its own repository, A is a fork of the whole harness monorepo frozen at dsh 0.1.0-rc.5 (and omits `--no-open`), and B is a 2,900-line product hard-pinned to 0.1.2-rc.1 by 226 `file:` dependencies and 20 version-keyed patches into dsh's own packages. Forking either would mean owning a harness rebase or a patch set for ever, which is the opposite of "HimaHarness is a plugin bundle" (ADR-0001). Their patterns are borrowed instead, under MIT, with both copyright lines carried in `packages/desktop/THIRD-PARTY-NOTICES.md`; the stale-cookie finding above is B's, and is worth the reading on its own.
- **A separate renderer UI of our own over the `/hima/api/` routes.** Rejected: it is a second front end for what dsh's web app already renders, and it would put the campaign views somewhere dsh's chat is not — the reverse of D30.
- **Keep the browser tab.** Rejected for the reasons in the first paragraph. It is also what `--no-open` exists to prevent.
- **Tauri.** Rejected for the cookie access above, and because A — the Tauri shell — has no cookie handling at all to learn from.

## Consequences

- The dsh CLI is now a seam this repository faces at run time as well as in tests: `// @hima-seam cli direct` marks the two files that spawn it. If the `dsh web: <url>?token=…` line, the `--no-open`/`--host`/`--port` flags, or the `GET /?token=` exchange change shape, `packages/desktop/src/host-launch.ts` is where it lands, and every contract test in the suite fails with it — which is the point of the two callers being one module. The home's layout is a second such seam, `// @hima-seam profile-home direct` in `src/hima-home.ts`: `$DSH_HOME/profiles/<name>`, the `~/.dsh` default, the profile manifest and `cordis.patch.yml`. Both restate dsh's rules rather than importing them, so neither file carries a compile-time dependency on a dsh package.
- The window needs a Node 24 to run dsh with, and Electron's bundled Node is older. In development it uses `HIMA_NODE`, else the Node that ran the package manager, else `node` on the PATH. A packaged app would carry its own; packaging is out of scope, so this is stated rather than solved.
- Electron tracks the newest supported major, `^44.2.0`. Electron supports the latest three majors, so a window that renders model-authored content has to be inside that window or it stops receiving Chromium security fixes. The package dropped its own `postinstall` in **42.0.0** (41.10.7 still has one) and exposes an `install-electron` bin instead, so `packages/desktop`'s own `"postinstall": "install-electron"` is what fetches the binary — a workspace project's scripts are not gated by `allowBuilds`, which keeps its `electron: true` entry for the case of a dependency that brings a postinstall back. Moving up a major is a version bump and nothing else. The range is `^44.2.0` and not `^44.3.0` so that the newest release still sits under pnpm's release-age quarantine rather than being carved out of it: the caret takes 44.3.0 on its own once it has aged, and `minimumReleaseAgeExclude` keeps naming only `@deepseek-ai/*`.
- The shell's automated check is one contract test (`test/contract/desktop.test.ts`) driving the main process's `--smoke` flag: it starts from an **empty** `$DSH_HOME`, so the profile can only be there because the shell made it; then it opens a real window, loads the host's page, asserts the page carries dsh's own client-module boot graph and the window is titled HimaHarness, and asserts the port is dead afterwards. `HIMA_USER_DATA` puts the window's state and cookie jar inside that throwaway home, so a suite run writes nothing into the developer's application-data directory. It skips, with the reason, where Electron cannot open a window — a headless login, a launchd session with no window server, a machine with no display, an install with no binary. There is no Playwright and no renderer test: the renderer is dsh's page, which the rest of the suite already asserts on over HTTP.
- **Superseded (2026-09-09).** `--smoke` is gone: the shell's automated check is the driver mode of [ADR-0004](0004-desktop-driver-as-the-test-seam.md), which `test/contract/desktop.test.ts` drives from the same empty home and asserts the same facts through. The bullet above stands as the record of what was decided here.
- `pnpm run desktop` builds the shell and starts it, and prepares the home it is going to boot. There is no prerequisite left: `pnpm install && pnpm run build && pnpm run desktop` opens the workbench on a machine that has never run it.
- A host that dies after the window is up is shown in the window, with its exit code or signal and the end of its own stderr, on the same page a host that never booted gets. Without that, D39's claim — that the window makes "the workbench is open" and "a host is running" one fact — would hold in one direction only: the card's fetches would start failing as `hima/unreachable` with nowhere saying why. In the other direction the child is stopped from the moment it is spawned, so quitting mid-boot leaves no host behind either.
- The window's navigation fence compares parsed origins, never string prefixes: `http://127.0.0.1:<port>@evil.example/` begins with the host's origin and is a request to another machine, and a page that reached it would still be titled HimaHarness because the title is pinned. There is no test at the one seam for a window event, so this one is held by reading.
