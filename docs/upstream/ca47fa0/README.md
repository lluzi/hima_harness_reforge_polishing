# HimaHarness

Bounded exploration campaigns for chip design, shipped as a DeepSeek Harness bundle. Read [docs/product-idea.md](docs/product-idea.md) first, then [docs/product-decisions.md](docs/product-decisions.md) and [CONTEXT.md](CONTEXT.md) for the vocabulary. Engineering decisions live in [docs/adr/](docs/adr/).

## Setup

DeepSeek Harness needs Node 24. On this machine it is installed under `~/.local/node24`:

```bash
export PATH="$HOME/.local/node24/bin:$PATH"
pnpm install
pnpm run hooks:install
pnpm run build
```

`pnpm run hooks:install` points git at `.githooks/`: pre-commit runs the seam check, the typecheck, and the unit tests when any exist — today none do, and the runner says so rather than printing a pass; pre-push builds and runs the booted-host contract suite. There is no lint step, because this repository ships no lint tool. The hooks are the enforcement, not a reminder.

## Layout

- `packages/harness/`: the `@hima/harness` bundle. Its `cordis.patch.yml` inserts the Hima rows beside `dsh-base`. It is dual-face: `pnpm run build` produces the host half (`lib/index.js`, tsc) and the HimaGuide browser half (`lib/client.js`, esbuild), which the web profile discovers through the package's `dsh.client` declaration and serves under `/plugins`. The two halves talk over one Hima-owned namespace, `/hima/api/`, behind the web app's session cookie; the contract is `src/remote.ts` and `src/client/api.ts`. Each module under `src/` changes for one reason and says which in its first lines: `index.ts` is the plugin entry and the bundle's surface, `commands.ts` and `tools.ts` the two faces, `fabric.ts` the driver that carries a Run through its graph, `node-turns.ts` what one node's turn does, `budget.ts` what a Run may spend and the ending spending it all causes, `job-cap.ts` what holds a slot on a Site and how one is taken, `recovery.ts` picking a Run up after a restart and stopping one, `moments.ts` the one file that reaches dsh's agent seam and so the whole of what a Model moment is, `skills.ts` the pack authoring pipeline's five stages and the one provider that carries them, `words.ts` the one pluralizer every sentence uses, `remote.ts` and `workbench.ts` the two browser-facing surfaces with `card-labels.ts` the words they share, and `ledger.ts`, `jobs.ts`, `channel.ts`, `shell.ts`, `packs.ts` with `pack-folder.ts` (the one reading of a pack folder every answer about that folder is made from) and `release.ts` (the seal a tested folder is versioned with), `sites.ts`, `readers.ts`, `judge.ts` and `choosers.ts` the pieces those stand on. No module is much over 800 lines, which is the size at which one file starts holding two reasons.
- `packages/desktop/`: the HimaHarness window — one Electron main process around `dsh --profile hima`, and nothing else (D39, [ADR-0003](docs/adr/0003-desktop-window-around-the-hima-profile.md)). `src/host-launch.ts` is the launching itself, `src/hima-home.ts` is the making of the home it boots from — including the `hima-moment` agent preset and, in driver mode only, the keyless model stand-in overlay — and `src/local-site.ts` is the local Site and the stand-in flow `--site local` seeds; all three are shared with the contract suite, whose `bootHimaHost`, `createHimaHome`, `writeStandinFlow` and `writeLocalSite` are views over them. `src/main.ts` is the window; `src/driver.ts` is its driver mode, the one seam every step-3 contract test drives the product through (D42, [ADR-0004](docs/adr/0004-desktop-driver-as-the-test-seam.md)). It contributes no plugin, patches no dsh package, and gives the loaded page no IPC surface. Electron is a devDependency here and nowhere else, on the newest supported major; this package's own `postinstall` runs Electron's `install-electron` bin, which is what fetches the binary. `THIRD-PARTY-NOTICES.md` carries the MIT attribution for the two community shells whose patterns it borrows.
- `profiles/hima/`: the profile template a host boots with: `dsh-base`, the web app, the Hima bundle, under the privacy overlay that turns plugin-inventory reporting and telemetry off.
- `sites/`: site file and Permit templates, one directory per reference Site. `sites/linglong/` is the owner's EDA workstation; a customer's CAD copies a pair into the harness home's `hima/sites/` as `<name>.yml` and the permit it names. A site file also carries `bindings:`, what this Site binds for the inputs a HimaPack's run contract names, and `capacity:`, what the Site will hold at once — cores, memory, `parallelJobs`, and `licences:`, the seats of each licence it reserves for the harness (a count of `0` is a licence the owner reserves nothing of, as the reference site's node-locked Innovus line says; a licence not listed is one the Site does not declare). A Site's identity is the `name:` its own file states and nothing else — `loadSite` refuses, naming both, when that differs from the name asked for, which is what keeps a caller typing `LOCAL` from being answered by `local.yml` on a case-insensitive filesystem.
- `packs/`: the HimaPacks this repository ships, one directory per pack id. `packs/opene902-timing-probe/` is the first. A pack is installed by copying its directory into the harness home's `hima/packs/`, which is where the bundle's `packsDir` config points, exactly as a site file is installed into `hima/sites/`.
- `test/contract/`: tests at the one agreed seam, the booted Host. They boot the real `dsh` from an isolated home and assert only on what the host prints or answers. `pnpm run test:contract` builds the bundle before it runs a single test: the suite exercises `lib/`, not `src/`, so a bare run against a stale build would report on code that is no longer there — green or red, it would be reporting on the wrong thing. The tests that read real opene902 reports resolve them through `test/fixtures/opene902.manifest.json`, verifying each local copy's SHA-256 first; a missing or stale copy fails the test that needed it. On a machine that has never held the copies, set `HIMA_FIXTURES_OPTIONAL=1` to skip those tests instead. The local Site binds its flow root to a stand-in flow the suite generates into the isolated home: the same five pieces the run contract copies, driven by a makefile with the same `synth` target and the same command-line variables, which sleeps, can be told to fail its first N attempts, and writes a qor report into the results path the contract names — computed from the period it was asked for, so a Loop on it converges the way a Loop on Design Compiler does. A tool that passes `RESULT_TAG=<tag>` gets a results path and a failure counter of its own (`results/<design>/syn/report-<tag>/qor.rpt`, `build/<design>/fail-remaining-<tag>`), which is what lets two branches of one fork synthesize at the same moment without overwriting one another's report or spending one another's failures; unset — every generation of the shipped pack — nothing about the flow changes. The pack does not know the difference; only the site file's binding does. Beside `synth` the same makefile answers eight more stages, which is what lets a cell-mining and Fmax-push pack be driven here before a Site is reached (see "The stand-in's stages" below); `test/contract/standin-stages.test.ts` runs the whole sequence by hand, as Jobs on the local Site, and reads every report. The generator is `packages/desktop/src/local-site.ts`, the same one `pnpm run desktop --site local` seeds a developer's home with. Tests of the window, and every step-3 test, boot the harness through the desktop shell's driver mode with `support/driver.ts` (see "Driving the window" below), and skip with the reason where Electron cannot open a window.
- `scripts/check-seams.mjs`: every file under `packages/`, `test/`, and `scripts/` that imports a DeepSeek Harness package carries `// @hima-seam <name> direct|wrapped`, per ADR-0001 — the bundle, the test support, the contract tests, and the acceptance script alike.
- `scripts/check-boundary.mjs`: the pack-first boundary (D46) as a check rather than a reminder. Nothing under `packages/*/src`, the rules and choosers the bundle ships, or the skill bodies and authoring knowledge beside them names a design, a technology, a vendor's tool, a mining route or a report of one; those belong to a HimaPack, whose author owns them. The noun list and the exemption list are at the top of the one file, each exemption naming the file, the nouns it may use and the ticket that removes it — `readers.ts` for the bundled readers that really do read a vendor's reports, which goes when a pack ships scripts for those report kinds, `local-site.ts` for the stand-in flow that imitates the shapes of the three reports the bundled readers read, which is the carve-out D46 names and is permanent, and `target_period_ns` in the eight files of product text that still spell it (#72). Markdown is read as well as source, because a skill body is the one kind of prose in this package a model acts on: a vendor's flow named in one would be in the harness more surely than a line of code would put it there. An exemption whose file no longer holds its noun fails too, so the list says what is actually there. `pnpm run check:boundary`, and the pre-commit hook runs it beside the seams check.

## Records, rules, routes

**A Run** is what records belong to: `id`, `campaignId`, `siteId`, `createdAt`, and the next sequence number the ledger will hand out. An observation taken outside any fabric Run belongs to the Probe campaign of the day, `probe-<date>`. One Run can hold several observations: `/hima observe --run <runId>` appends to a Run already open instead of starting one.

A Run that **HimaFabric** started carries its whole fabric state on the same row, and that row plus the Run's records is the only place that state lives — the engine holds nothing besides. `packId` is the pack it runs and `goal` the Goal as bound parameters (`{ "target_period_ns": 2.3 }`), both written once and never again, because a Run runs one pack and a Goal is immutable for the life of a Campaign, a new Goal being a new Campaign (D3). `budget` is `timeBoxMs`, `retryAllowance`, `generationLimit`, the `jobCap` copied from the Site's declared parallel job count, and `licences`, the seats of each licence the Site declared, copied beside the job cap at the same moment and for the same reason: a Run is held to what the Site declared when it started, and a licence absent there is one the Site declares none of. All five are likewise written once. So is `firstStrategy`, the Strategy this Campaign was started with — the pack's own knobs by name (`{ "periodNs": 2.3 }`) — put on the row in the same write that opens it and never written again: `strategy` below moves with the Loop, so this is the only place what generation one asked the flow for stays readable once a decision has been acted on, and it is what the generations table reads that generation's own measurement against. `RunProgress` — what HimaFabric may change about a Run as it moves — does not name it, so no advance can write it. What moves is `status` (`running`, `waiting`, `cancelled`, `ended-goal-met`, `ended-goal-not-met`, `ended-converged`, `ended-budget-exhausted`), `currentNode`, `strategy` (the knobs this Run is set to now, by the names its pack declares them under — a revisit overwrites it with the Strategy the decision chose, and a Run that ends without meeting its Goal ends carrying the Strategy it would have tried next), `generation` (which turn of its Loop it is in, counted from one, and what every record it writes is stamped with), `loop` (the drill-down Loop it is standing inside while it is inside one — the Loop's id, the Explore node that opened it, its name, and which Generation *of that Loop* the Run is in; absent while the Run is in its pack's own graph, and it is that Loop's generation the ledger then stamps records with), `fork` (the fork it is standing inside while it is inside one — the node whose unlabelled edges branched, the judge node they converge into, and where each branch stands, by branch id: `currentNode` and one of `running`, `waiting-for-slot`, `done`, `blocked`; absent while the Run is not inside one, and `currentNode` above is the join for as long as it is there), and `meters` (`elapsedMs`, `jobsLaunched`, `attempts`, `waitedMs` — how much of the elapsed time was a person being asked, on a Run that was — `licenceMs`, what this Run has spent of each licence in licence-milliseconds, the seats a Job held times how long it held them summed over every Job of this Run that has settled, read from the records like every other meter and absent on a Run whose Jobs held none — `generationMs`, how long each Generation of the Loop has taken, oldest first, index 0 being generation one, which is where a Campaign's time box actually went — and `endedBy` naming what ended the Run where the graph did not: `time-box`, `generation-limit`, or a person's `cancel`, said to a person in words and never as that key). The meters only ever move forward, `waitedMs` and every entry of `generationMs` among them: two faces can be writing one Run at once — a `/hima cancel` composing its ending while the loop it interrupted is still counting the Job it had just launched — so each meter is taken from the further of the two answers rather than from the later of the two writes, and a counter never goes back. `endedBy` is not a counter and follows the status: a write that is only counting states no status and cannot unsay it, but a Run moved back to `running` or `waiting` has not ended and loses it — a cancel whose kill did not take ends nothing, and a Run left waiting for a person must not say a cancel ended it. All ten are absent on a Run no fabric started, which is how the ledger says "this is a Probe-campaign Run" without a word invented for it. `packId` is on the row rather than only on the workspace record because a reconciliation after a restart must be able to say what a Run was for even when it never got as far as a workspace, which is exactly the Run that needs saying.

**Every record** carries `id` (`<runId>#<seq>`), `runId`, `siteId`, `seq`, `at`, `writer` (`executor`, `shell`, `judge`, or `person`), `generation` (which turn of the Run's Loop it was written in, stamped by the ledger out of the run row as it appends, and absent on a Run no fabric started), `loopId` (the drill-down Loop it was written inside, stamped from the same row and absent on a record written outside every Loop — what nests a sub-question's records under the Run without a second ledger), and `type`. Five of them also carry `branchId`, the branch of a fork they were written inside — the observation, verdict, job, node and blocker records, which is everything a fork produces. It is a field the fabric passes and **not** a stamp the ledger takes off the run row, unlike `generation` and `loopId`: branches append in the same instant, so the row says where all of them stand at once and never which of them a given write belongs to. There are fourteen types:

- **observation** — `path` as the caller named it, `contentSha256` and `bytes` of what was actually read, `reader` (`id`, `version`, `reportKind`, `emits`), and `values`. Each value is a `type`, the `unit` that type is bound to, `mode` and `scope` where those apply, `group` naming the tool's own path group the value was read out of when one group is its source, and either a number or `null` with an `unknownReason`. A reader never substitutes a zero for a value it could not find. Two readers ship today: `innovus-timing-summary@1` (`innovus-optdesign-summary` reports) and `innovus-verify-drc@1` (`innovus-verify-drc` reports); a third, `dc-qor-report@1`, reads a Design Compiler qor report (`Report : qor` header) and emits `setup_wns` (setup, all) as the minimum critical-path slack over every one of the report's path groups, naming the group that holds it; `setup_tns` (setup, all) as their total negative slack summed, naming no group because no one group is its source; `clock_period` as the critical-path clock period of the report's **clock** group, naming it; `hold_wns` (hold, all) as the hold slack the worst hold violation stands for (DC prints the violation as a positive magnitude; `hold_wns` is a slack, so 0.02 ns of violation is −0.02 ns and no violation is 0), naming the group that stated it; and `cell_area`, stated outside every group, bound to the `um2` unit like every other value type is bound to its own unit.

The clock group is the one DC did *not* name in double asterisks: `**default**`, `**async_default**` and `**clock_gating_default**` are DC's built-in groups for paths that belong to no clock, and every other group is named after the clock that launches it. The distinction is load-bearing because a built-in group routinely holds the report's worst slack while stating a `Critical Path Clk Period` the design was never synthesized at, so `setup_wns` and `clock_period` come from different groups on a real report. When a report states no clock group at all, or more than one, `clock_period` is `null` with an `unknownReason` naming the groups that were found — a period is never guessed from the groups on offer.
- **refusal** — `path` and `reason`. The shell writes it when the Permit refused the read; the executor writes it when the reader does not accept that report kind. A refused observe is a record, never a silent empty answer.
- **verdict** — `outcome` (`PASS`, `FAIL`, `UNDETERMINED`), `ruleId` and `ruleVersion`, `cites` (the observation record ids the values were read from), `valuesAsRead` (those values copied exactly as read), `boundParameters` (the value bound to each parameter the rule declared, absent for a rule with none), and `reason`, which is required whenever the outcome is `UNDETERMINED`. HimaJudge is the only writer of verdicts. At a **join** it writes one per rule per branch, each citing that branch's own reading and carrying its `branchId`.
- **job** — `event` (`launched`, `finished`, `killed`), `job` (the identity: the tmux `session` and its pane `pid`, the `workspace`, the `name`, `startedAt`, and `wire`, the shell line the site was given to run), and `exitCode` on a finished job. On the `launched` record alone, three more, each written where it is true and read by a host that never launched the Job: `licences`, the seats it holds; `reading`, what a pack reader's Job was launched to read (#61); `workshop`, what a workshop's Job was launched to *run* — `{ id, entry: { path, sha256 } }`, the entry and the hash it was verified to have against its `code` record immediately before the launch (#62); and `attempt`, which attempt at its node the Job is, so recovery after a restart numbers its own records from the launch rather than from a node record the launch may have outlived. Written by the executor. The exit code is read from the exit file the launch itself wrote, never inferred from a session being gone; a job whose session is gone and whose exit file is absent is `gone`, and no exit code is invented for it.
- **node** — `nodeId`, `kind` (`act`, `judge`, `explore`, `wait`), `state` (`pending`, `running`, `done`, `retrying`, `blocked`, `cancelled`, `waiting-for-slot`, `reconciled`), `attempt` counted from one, `outcome` where a node concludes one (a judge node's verdict outcome, which is also the label of the edge the Run then took), `jobSession` naming the tmux session an act node's attempt is waiting on, and `reason`, why the node is in the state it is in — the first thing a person reads on a `blocked` node. Written by the executor, one per transition, so the Run's whole path is readable from its records. `pending` is never written: it is what a node the Run has not reached is in, and a record says what happened. `reconciled` is written by a host that picked a node's interrupted attempt up again after a restart, carrying in `reason` what it found of that attempt's Job — still running, finished with the exit the launch wrote, or gone. It settles nothing: the node goes on to `done`, `blocked` or `cancelled` from there, under the same attempt number, because it is the same attempt.
- **blocker** — `nodeId`, `attempts` (how many attempts that node had made when it gave up), `lastExitCode` (absent when the failed Job wrote none), `logTail` (the last 40 lines of that Job's own log, and at most the last 16 KB of them, copied into the ledger rather than left on the Site, and absent when there was no Job to tail — a bound in lines alone is no bound, since one megabyte-long line would otherwise land on every blocker), and `reason`. Written by the executor when a node's Retry allowance is spent: the whole of a Hard blocker in one record, so the person who has to clear it need not reconstruct it from a one-line node reason and a log file on a machine they may not be logged into.
- **resumed** — `nodeId` (the node the Run re-enters), `who` (the session's agent id, or `workbench` for the route), and `clears` (the blocker record id, when the Run held one). The one record type written by `person` rather than by the executor: a Hard blocker is by definition a failure the harness could not clear on its own, so the record that clears it says a person did.
- **decision** — `nodeId`, `chooser`, `chosen` (exactly one of `{ strategy: { <knob>: <value>, … } }`, the whole Strategy chosen and not the knobs that moved, `{ goalMet: true }` and `{ converged: { read, band, generations, values } }`, never two and never none), `rationale` (the named numbers the chooser used, enough to re-derive the choice from this record alone), and `cites` (the verdict record ids it weighed, then the observation record id it read). Written by the executor: an Explore node's chooser is not a judge, and D7's guarantee that only HimaJudge writes verdicts is untouched by it.
- **workspace** — `event` (`prepared`, `reused`), the `campaignId` the workspace belongs to, the `packId` and `packVersion` it was prepared for, the `workspace` path as the Site resolved it, the `flowRoot` it was copied from, the `design`, the `containerName` the pack's tools bind that copy into, `copied` (what the run contract named, in the order it was copied), and `preparedAt`. Written by the executor. It is a record of its own rather than a job event because preparing a workspace launches nothing: there is no session, no pid, and no exit code, and a `job` record shaped to hold it would have to invent all three. `containerName` is recorded because nothing else on the Site says it, and only a name could remove that container later.
- **cancel** — that a person asked this Run to stop, with the `nodeId` it stood at and `jobSessions`, every Job it found open, both absent where it had neither. Written by the executor the moment the request arrives, before anything is sent to the Site. The request only: what actually stopped is the `killed` job record and the `cancelled` node record that follow, and a Run is not cancelled until those exist. One record however many Jobs were stopped — a cancel stops every Job the Run has open, and a Run inside a fork has one per branch — so the record names them all, and `jobSession` is the head of that list, kept because every face names one Job. Naming them all is what lets a loop still holding a Job of its own ask whether *its* session is one this cancel is stopping, rather than guessing from the order two writes landed in. Written first for a second reason as well — it is what tells a waiting loop still driving that Run that the Job about to disappear was stopped on purpose, so the disappearance is not recorded as a fault.
- **loop** — that a drill-down Loop `opened`, and that it `closed` (#28): the `loopId` this pair mints and names, the `nodeId` of the Explore node whose `opens:` it is, the `name` the pack declares it under, the `event`, and — on `closed` alone — the `outcome` it came to (`goal-met`, `converged`, `generation-limit`) and how many `generations` it ran. Written by the executor, the `opened` one before the Run moves into the Loop and the `closed` one before it moves out, so the pair brackets every record the Loop wrote and each of those carries its `loopId`. `loopId` is required here where it is optional everywhere else, because on this record it is not the header's stamp but the record's subject. A Run cancelled inside a Loop has an `opened` with no `closed`, and that is the record: the Loop really was left open, and the Run's own `cancelled` is the last word on it.

- **session** — that a Model moment `opened`, and that it `closed` (#59): the `preset` the session was composed from, dsh's own `sessionId`, the `model` that answered, the `nodeId` and `attempt` it belongs to (with the Generation on the header, as on every record), and — on `opened` alone — `tools`, every tool the session could reach, and `workshop` (`{ id, entry }`) when the moment was opened for one (#62), and on `closed` alone the `outcome` (`completed`, `failed`, `interrupted`). Written by the executor, the `opened` one once the session exists and before the model is asked anything, the `closed` one once the session is disposed. `tools` is dsh's own answer about that session's scope and not a list the caller handed in: a record of what we meant to give a model would not be evidence of what it could reach. An `opened` with no `closed` is a host that went away mid-moment, and the next boot's reconciliation writes the one close it is missing, `interrupted` — exactly one per open, never two. See "Model moments" below.

- **code** — that a Model moment wrote one file inside its workshop (#62): the `nodeId` and `attempt` it was written at, the `sessionId` of the moment that wrote it, the `workshop` the contract declares, the absolute `path` on the Site, the `sha256` of the bytes that landed, their `bytes`, and the `language` the pack says every file of that workshop is in. Written by the executor **after** the bytes are on the Site and never before, because the record is the claim that the file is there. A write the grammar, the Permit or the containment rule refused writes no record of this kind at all — and neither does one whose bytes could not be read back and held against what was sent: both write a `refusal` naming the path, like everything else this harness was not allowed to do or could not verify. Nothing here says what the file *contains*: that is on the Site, where a person and the Job both read it, and the hash is what says the file there is still the file that was written. See "Workshops" below.

- **experience** — that this Run's Campaign report was written on its Site, and where: `writtenAt`, the instant both files state as their own, and `markdown` and `json`, each the `path` the Permit resolved, the `sha256` of what was written there and its `bytes`. Written by the executor when a Run ends, once and never again, **after** both files are on the Site — the record is the claim that they are there, so a host that died between the two files leaves a Run without one and the next boot's reconciliation writes the report again. A Run that carries this record is a Run whose report is written, which is what makes writing it idempotent.

**The Campaign's technical report** is two files under the Campaign workspace, beside the results the Site owner keeps: `<workspace>/hima-experience/<runId>.md` for the people who read it and `<runId>.json` for the programs that do (D44, D16, D19). It is written when a Run ends for any reason — the goal met, the exploration converged, a Budget meter spent, a person's cancel, a graph that ran out of edges — from the same run view the card is rendered from, so every number in it is a number the card showed. The JSON is the machine's (`schema: hima-experience/2`, the run and campaign ids, the pack and its version, what the Run was for, the Site, the Goal, the Budget, the ending with the meter that ended it and the reason in words, one entry per Generation with its drill-down Loops and its branches nested, the meters, the path, the blockers, the cancels, and `writtenAt`); the Markdown is the person's — the same facts as headings and tables, with one paragraph of reasoning per generation, and every Strategy in it said in the pack's own words, as the card says it. A **test run** says so in the report's head, where the card says it: a report filed beside a Site's results outlives the ledger that wrote it, and a later reader with nothing but the file has no other way to tell a pack author exercising their own work from a result. Every write is decided by the Permit first and sent with the workspace plumbing's own verbs, `mkdir` and `tee`, exactly as preparing a workspace is; a Site that will not take the report leaves the Run's ending standing and the report owed, and the next host writes it. Nothing rewrites a report that is there.

**A rule** is data, not code: one YAML file per rule id under `packages/harness/rules/`, so a person can review a rule without reading TypeScript. It names every value it requires and applies one comparison to one of them, which must itself be listed in `requires`:

```yaml
id: setup-wns-all-nonnegative
version: '1'
title: Setup WNS over all paths is not negative
requires:
  - type: setup_wns
    mode: setup
    scope: all
subject:
  type: setup_wns
  mode: setup
  scope: all
predicate:
  op: gte          # gte, lte, gt, lt, eq
  threshold: 0
  unit: ns
```

A rule is referenced as `<id>` or `<id>@<version>`. An unknown id, or a version that does not match the file, is an error — never a silent pass. A required value that the Run never observed, or that the reader marked unknown, is `UNDETERMINED` with the reason naming it.

A rule may also declare one **parameter**, a value its caller binds at judge time instead of fixing it in the file: a top-level `parameter: { name: <id>, unit: <unit> }`, and a predicate whose `threshold` is `{ parameter: <name> }` in place of a number. `clock-period-at-most` is the shipped example, the goal rule: the run's clock period must be at most a target chosen when the run starts.

```yaml
id: clock-period-at-most
version: '1'
title: Clock period is at most the bound target period
parameter:
  name: target_period_ns
  unit: ns
requires:
  - type: clock_period
subject:
  type: clock_period
predicate:
  op: lte
  threshold:
    parameter: target_period_ns
  unit: ns
```

A value is bound with `--param <name>=<value>`, repeatable for a batch of rules that each declare a different one. Judging a rule whose declared parameter has no bound value is `UNDETERMINED`, naming the parameter — never a default and never a silent pass; a rule with no `parameter` ignores every `--param` it is given. The bound value lands on the verdict's `boundParameters`.

**A chooser** is data too, and for the same reason (D38): one YAML file per chooser id, referenced by `<id>` or `<id>@<version>` from an Explore node, resolved in the pack's own `choosers/` folder first and the bundle's `packages/harness/choosers/` second (below, "Pack-local data"). It states what it reads out of the Run's latest observation, the one parameter the pack binds, and an ordered list of clauses over the two verdicts — the first whose `when` matches wins:

```yaml
id: timing-push
version: '1'
title: Push the clock period against the measured setup margin
parameter:
  name: guardBandNs   # bound by the explore node, in ns, zero or more
  unit: ns
reads:
  period: { type: clock_period, unit: ns }
  slack: { type: setup_wns, unit: ns }
decide:
  - when: { constraint: PASS, goal: PASS }
    goalMet: true
  - when: { constraint: PASS }
    next:
      periodNs: { sum: [period, { neg: slack }, guardBandNs] }
  - when: { constraint: FAIL }
    next:
      periodNs: { sum: [period, { abs: slack }, guardBandNs] }
```

`constraint` is the verdict of the judge node's first rule and `goal` the verdict of its goal rule. `next` sets the pack's own Strategy knobs by name, and a knob a clause does not name carries over from the Strategy the Run is on: a number knob takes an expression, a choice knob takes one of its own declared words. The arithmetic a clause may state is `sum`, `neg`, `abs`, a name it `reads`, and the parameter's name, and nothing else: a chooser is checkable, not programmable, exactly as a rule's predicate is. Which of the two a bare string is — a read, or a word out of a knob's list — is the *pack's* declaration to say, so `/hima pack check` holds every knob a clause sets against the contract's `strategy:` block: the name declared, and the kind matching. Nothing here says when to stop exploring: a clause sees one generation, and that is the pack's `converge:` and the harness's arithmetic over what the ledger holds (below). A value the observation does not state, an unbound parameter, and a pair of verdicts no clause matches all answer with the reason, which lands on the Explore node's blocked record — never a period computed from a substituted zero.

One chooser ships with the bundle — `timing-push` above — and the rule that is *not* in it is the point (D45). `timing-push` pushes by the margin a met period reports; **a synthesis tool reports none**, because it stops optimizing once the constraint is met and prints a setup slack of exactly `0.00` for every period it meets, so on the real tool that clause reads `period − 0 + guardBandNs` and loosens by the guard band every generation, which is what the step-3 acceptance recorded. `over-constraining-push` (`parameter: stepNs`, the same two `reads`) never asks a met period what it had to spare: `{ constraint: PASS }` sets `periodNs: { sum: [period, { neg: stepNs }] }` — one step tighter, asked again — and `{ constraint: FAIL }` sets `periodNs: { sum: [period, { abs: slack }, { neg: stepNs }] }`, one step below the period the violation says the design actually closes at, so the next generation reads the same violation, asks for the same period, and the pack's `converge:` sees a Loop that has stopped learning with the fact it was run to find on record. That rule is **pack data** and the bundle ships no file for it (#57): a push rule is the method a pack sells, so the pack that uses it carries it in its own `choosers/` — the converging variant `pnpm run desktop --site local` seeds, the drill-down variant, and whatever the step-4 pack authors write. The reference pack keeps `timing-push` and `PACK.md` says what that costs.

**A HimaPack** is a folder of plain files a person can read and diff (D28), never code. One directory per pack under `packs/<id>/`, installed into the harness home's `hima/packs/`:

| File | What it is |
| --- | --- |
| `PACK.md` | the human-readable spec: what the pack does, its goal template, its strategy knobs, its guard band |
| `contract.yml` | the run contract: the `inputs` a Site must bind, the `outputs` a generation leaves in its workspace, the `environment.wrappers` the Site must allow, what `workspace.copy` takes from the flow, the `tools` — each with the `licences` a Job of it holds — the `rules` the pack references, the `strategy` knobs a Run of it is set to, and the `words` it calls its own numbers by |
| `graph.yml` | the fabric graph: `nodes` with an `id`, a `kind` (`act`, `judge`, `explore`, `wait`) and that kind's `parameters`, `edges` of `{ from, to, outcome?, revisit? }` — `revisit: true` being the one edge that closes a Loop, and several unlabelled edges out of one act node being a fork — and `loops`, the drill-down Loops an explore node may open, each a graph of its own |
| `tools/` | the small scripts, one per tool the contract declares |
| `rules/` | the pack's own judge rules, `<id>.yml`, resolved ahead of the bundle's |
| `choosers/` | the pack's own choosers, `<id>.yml`, resolved ahead of the bundle's |
| `readers/` | the pack's own readers, `<id>.yml` — the script under `tools/` that reads one of the contract's outputs, and the command line that runs it |
| `semantics.yml` | what the value types this pack's readers emit mean: the unit each is measured in, and the qualifiers a value of it carries |
| `knowledge/` | the plain Markdown files the contract's `knowledge:` names, which a Model moment may read and the harness never reads as data |

The skeleton of every one of those files — the smallest each can be and a note per field — is `packages/harness/skills/knowledge/pack-anatomy.md`, which is what the pipeline's fabric stage compiles to.

An **input** is bound by the Site, in the site file's `bindings:` map — `flowRoot`, `design`, `workspaceRoot` for the first pack — so the same pack runs on another Site by editing that file and nothing else. `${input}` in an output path or a workspace copy entry is substituted from those bindings. A **tool** declares the `argv` HimaFabric launches, with `${NAME}` bound from the tool's own declared `inputs` (the environment variables its script reads); `argv[0]` is the first word the Permit decides on, and the script beside it is that same command line written for a person to run by hand. It also declares its `licences:`, how many seats of each a Job of it holds while it runs, held against the Site's own `capacity.licences` by `/hima pack check`; a tool that holds none declares none. A **node parameter** is a number or a word the pack fixes, or `{ from: strategy | goal, name: <n> }` for a value the Run supplies — the clock period for this generation, the target period the goal was started with. A judge node names its rules by id and binds their declared parameters under `bind:`; an explore node either names its chooser by id, binds its declared parameter under `bind:` the same way, and may declare `converge: { read, band, generations, generationLimit }` — when its Loop has stopped learning and how many generations it may take at most — or names `opens: <loop>` instead and drills down into that Loop. Exactly one of the two: a node that named both, or neither, is refused when the pack is loaded. A graph with several explore nodes may declare `converge` on each of them, and every one of those declarations states the same `generationLimit`: one Campaign has one Budget, so a graph naming two of them is refused when the pack is loaded, and the number the Run is held to is read off the explore node whose edge revisits.

A contract declares **`strategy`**, the knobs a Run of it is set to for one generation — what an Explore node chooses anew (CONTEXT.md), and the whole of what a Strategy is for that pack. One entry per knob, keyed by the name every face carries it under, and at least one, because a pack with nothing to choose has no Loop to run:

```yaml
strategy:
  periodNs: { type: number, unit: ns, min: 0.5, max: 10, default: 2.30 }
  profile: { type: choice, options: [plain, balanced, dense], default: plain }
```

Two kinds, and the harness knows no others: a `number` in a `unit` between a `min` and a `max`, and a `choice` out of a list of `options`. Every field is required, so a knob says all of itself in one place, and each carries the `default` a Run of that pack starts at. The harness owns no knob: the start form renders one field per knob of the pack a person selected, `/hima run` takes `--set <knob>=<value>` (repeatable), `POST /hima/api/runs` takes `strategy: { "<knob>": <value> }`, and every one of those is held against this block — a knob the pack does not declare, a number outside its bounds, a word outside its list — in one sentence all three faces refuse in, before a Run exists. A knob nobody set takes the default.

A contract also declares **`words`**, what the pack calls the numbers a Run of it is stated in — one entry per goal parameter its graph binds and one per knob it declares above, keyed by that very name, each with a `label` and a `unit`:

```yaml
words:
  target_period_ns: { label: clock period at most, unit: ns }
  periodNs: { label: clock period, unit: ns }
```

The pack is what knows: `target_period_ns` is a name the harness carries and "the clock period at most, in ns" is what it means. The card's four questions, its other mount in the chat, and `/hima status` all say `goal: clock period at most 2.3 ns` and `strategy: clock period 2.25 ns` from this block, through one words table, at whatever precision the number itself has. A goal parameter the pack says nothing about is shown under its own name — `target_period_ns=2.3` — which is what every pack read before this block existed. A **knob** is not that: a knob is the pack's own invention, so there is nothing else a person could read it as, and `/hima pack check` refuses a pack that declares one and says no words for it. A knob declared as a `choice` states no `unit`, because a choice is measured in nothing, and it is the only entry here that may omit one; a face renders `mining profile dense` where a number reads `clock period 2.25 ns`. Nothing changes on the wire either way: `run.goal` and `run.strategy` keep the names, so a caller that reads numbers reads exactly what it read before. A `words` entry keyed by anything else — a name the pack's graph never takes from the Goal, and no knob of a Strategy — is a label no face could ever look up, and `/hima pack check` refuses it, naming the ones it could have used.

A contract may also declare **`knowledge`**, the domain knowledge the pack carries — one entry per plain Markdown file under its own `knowledge/`, with what that file is for in the author's own words:

```yaml
knowledge:
  - file: push-method.md
    purpose: why this pack pushes the clock period the way it does
```

The purpose is what makes this a declaration rather than a directory listing: a Model moment is opened for one purpose with the instructions and tools of that purpose only, so what a file is for is what decides whether that moment may read it. A **workshop** is what reads one (below), through `hima_workshop_knowledge`, and only the files its own declaration lists; the harness never reads a knowledge file as data at all. `/hima pack check` lists each one and refuses a pack whose folder does not hold a file its contract promises.

### Pack-local data

A pack folder is the **first** place an id it names resolves from, and the bundle is the second (D46, #57). `loadPack` computes the ordered list once — `<pack>/rules/` then `packages/harness/rules/`, `<pack>/choosers/` then `packages/harness/choosers/` — and every caller that resolves one for a Run takes it off the pack: the judge node of a Campaign through the run row's pack, the explore node through the pack it is driving, `/hima pack check` through the pack it is holding. An id neither place holds is refused naming **both** paths, because a person told only about the bundle goes on editing the wrong folder. Absence is the *only* thing that moves a lookup on: a file that is there and will not open — permissions, a `rules` that is a file rather than a directory — is an error naming it, never a quiet fall back to the bundle's copy of that id, and a Run whose pack this machine cannot load at all is refused by `/hima judge` naming the pack and why, rather than judged on a rule that pack never selected.

**Which instant the pack's own copy is read at is stated at every call** (#64): `/hima pack check` reads every pack-local file — a rule, a chooser, a reader declaration, `semantics.yml`, a knowledge file, a reader's script — out of the **one reading** the pack was parsed from (`pack.folder`), because a check is one statement about one folder at one instant and a check that read the folder again would describe a folder the pack did not come from; a **running node** reads the same files as the folder stands, because a pack edited between two generations means the correction (D46). The bundle's own files are read where they lie either way. Both answers fail closed in the same words: a `readers` that is a plain file, or a directory standing where `semantics.yml` or `rules/<id>.yml` goes, is refused naming the path in the reading exactly as `ENOTDIR` and `EISDIR` are refused off the disk — never read as a pack that declares none, which would run a bundled rule under a pack's own id and call it a pass.

Knowledge is one-sided: the bundle ships no knowledge directory, so the refusal says so rather than naming one path and reading like a list that was cut — and what must be there is a plain file, not merely something of that name, since nothing reads a directory as Markdown.

**A reader is a script of the pack's** (#61). `readers/<id>.yml` declares it, and the file beside it is what runs:

```yaml
id: count-candidates
version: '1'
file: tools/count-candidates.sh          # under the pack's own tools/; a plain file, resolved inside it
argv: [sh, '${READER}', '${REPORT}', '${OUT}']
reportKind: standin-candidates           # a word for the record; never sniffed
emits: [candidate_count]                 # every value type it writes, each declared in the semantics
```

`argv` is held to a grammar at load, because it is the one string a pack author writes that becomes a command line on somebody else's machine: **a word is a literal carrying no `$` and no whitespace, or it is exactly one of four placeholders** — `${READER}` (the shipped script's absolute path on the Site), `${REPORT}` (the report the contract's output names, as the Permit resolved it), `${OUT}` (the file the script must write), `${WORKSPACE}`. Any other `${…}`, a `$` in a literal, or whitespace in a word is refused naming the word. Every one of the four is computed by the harness from a path the Permit already decided, so nothing a pack wrote is ever substituted into an argv beyond the literal words its own declaration holds. `argv[0]` is the wrapper the Site's Permit decides on, exactly as a tool's is, and the contract's `environment.wrappers` must declare it; it must be a **literal** word, because pack check reads it as it stands in the file and the launch runs it after substitution, and a placeholder there would be a pack that checked fit against one word and launched another. `file` must begin `tools/`: a reader is a pack tool, and the file, that folder and the pack folder are each resolved for real and held inside the next, so neither a `..` in a name nor a `tools` that is a link out of the pack reaches a script the pack does not hold.

**The output contract**: the script writes one JSON document to `${OUT}` and exits 0.

```json
{ "values": [ { "type": "candidate_count", "unit": "count", "value": 8 } ] }
```

Each value is the same shape an observation carries — `type`, `unit`, `value`, and optionally `mode`, `scope`, `group`, `unknownReason`. The document itself is strict, and each value in it is parsed by that strict value schema **at the one gate**, which is also where a reader this bundle ships has its values parsed: one place decides what a value is, so an unknown key or a number written as a string is the same refusal whichever reader produced it — and never a record the next host cannot open the ledger over.

**How it runs**, and every step is a mechanism this harness already had: the report is resolved by `decideRead` and read; the script's bytes are read from the pack folder on this machine and hashed *from those bytes*; the script is shipped to `<workspace>/hima-readers/<id>/<file name>` with the `mkdir -p` and `tee` pair a prepared workspace's own `workspace.json` is written with, on every observation, so the audit shows the bytes as well as the launch; `${OUT}` is `<workspace>/hima-readers/<id>/<nodeId>-g<generation>-a<attempt>.json`; and the reader is launched as a **Job** through the same claim-slot-and-launch a tool node makes — `name` is `reader-<id>`, and it holds no licence, because a Job that reserved a synthesis seat to count a number would make a Campaign wait for one. A reader Job that exits non-zero or vanishes is a failed attempt of the observing node, retried within the Retry allowance exactly as a tool's Job is and then a Hard blocker, so a broken script is something a person repairs in the pack folder. A Job that exits 0 and whose output cannot be read, does not parse, or does not validate is a **refusal record** and the node blocked with that sentence — a pack fault, as an observe refusal is, and not a retry, because running it again would produce the same JSON.

**A reader's Job outlives its host, and what reads it back is what its launch said.** A Job survives the host that launched it (#14), and a pack folder is plain files a person edits while a Run is between hosts — so everything the read-back needs is settled at the launch and written onto that Job's own `launched` record as one strict block, `reading`: the reader as the observation will carry it (its version, its emitted set, its file and the hash of the very bytes that were shipped), the file the script was told to write, and the report as it stood when it was read. A host that picks the Run up reads that record and nothing else of the pack folder: whether that one block is there is what says the Job was a reader's at all, which is why it is one nested member rather than three loose ones and why every schema around it refuses a key it does not declare, so a declaration deleted in between cannot make a reader's Job look like a tool's and settle an observe node `done` with no reading in it. The one thing read again is the pack's `semantics.yml`, for the reason a rule and a chooser are read again at every node — it is the vocabulary a Campaign currently speaks, not evidence about this reading. A reading is also read back before its node is settled when a cancel and the Job's own ending cross: **a node is never `done` without its observation.**

The observation record then carries `reader: { id, version, reportKind, emits, file, sha256 }`, and the four faces that name a reader — the workbench page's observation row, the chat card's, `/hima observe`'s own answer, and the `latest reading:` line of `/hima run` and `/hima status` — all say `read by count-candidates@1 · pack script tools/count-candidates.sh sha256 a1b2c3d4e5f6`, through one spelling. The file and the hash are present exactly for a pack script, and a record carries both or neither: a pack folder is plain files a person edits, so the id and the version alone do not say what ran.

A reader id is a file name like a rule id and a chooser id, so it is held to the same shape (lowercase letters, digits and dashes): a pack naming `../something` is refused when the pack is loaded, before any of it is joined to a path. The declaration resolves ahead of the bundle's registry, and only `ENOENT` moves a lookup on — a silent fall-through would run the bundle's reader under the pack's name and call that a pass.

### What a value means: `semantics.yml`

A value type is **declared**, not built in. `semantics.yml` sits beside `contract.yml` in a pack folder, and `packages/harness/semantics.yml` declares the eight the bundle's own readers emit; the pack's file resolves first, exactly as its `rules/` does, and a type declared in both is the pack's.

```yaml
values:
  setup_wns:        { unit: ns, mode: [setup], scope: [all, reg2reg] }
  clock_period:     { unit: ns }
  candidate_count:  { unit: count, description: how many cell candidates a mining stage yielded }
```

A value type name and a unit are slugs (`^[a-z][a-z0-9_]*$`). `mode` and `scope`, when present, list the words a value of this type must carry, drawn from the harness's two fixed qualifier vocabularies (`setup|hold`, `all|reg2reg`); when absent, a value of this type carries none. `description` is optional.

**One validator** holds every reader's output — a pack script's and a bundled reader's alike — before anything is appended, against the semantics **that Run resolved**, so a reading taken at a node of a pack is held to the pack's vocabulary whichever code took it (`/hima observe`, the tool and the observe route take a reading outside any pack and are held to the bundle's): each value's type is declared in the resolved semantics, its unit is the declared unit, its `mode` is present exactly when the declaration lists modes and is one of them, likewise its `scope`, and a `value` of `null` carries an `unknownReason`. Then the output is held against the reader's own declaration: **the set of types produced is the set `emits` names**. A type emitted and not declared is a reader doing something its record does not say; a type declared and not produced is a report that did not hold what the pack promised, and reading it as an absent value would put a Campaign's conclusion on a rule that quietly went UNDETERMINED for want of a number nobody noticed was missing. So a bundled reader emits every type it declares on every report — the Innovus summary reader reports the *other* analysis pass unknown, saying which pass the report states, rather than leaving it out. Every failure is one sentence naming the reader, the value type and what disagreed.

Rules and choosers speak the same vocabulary and are held to it by `/hima pack check`: every rule's requirements name a declared type and its predicate's unit is that type's unit, and every chooser's `reads` name a declared type in the unit it is measured in. The Judge and the chooser compare literally at run time as they always have, and nothing is fabricated for an undeclared type — a requirement the observation does not state is UNDETERMINED with its reason, as before.

`/hima pack check <pack> --site <site>` holds a pack against a Site and answers `fit` or `unfit`: every input bound, every tool's first word a wrapper the Permit allows (asked with the same function that decides a live launch), every rule, reader and chooser resolvable, every chooser's declared parameter bound by the node that names it, to a number that is zero or more, every knob a chooser's clause sets declared by the contract and of the kind that clause sets it as, every knowledge file the contract names there in the pack's folder, and every `words` entry keyed by a name the pack actually takes from the Goal or declares as a Strategy knob — and one entry for every knob it does declare. For a reader the pack declares itself it holds three more (#61): the script is a plain file inside the pack's own `tools/`, `argv[0]` is a literal wrapper the contract declares and the Permit allows, and every type it `emits` is declared in the resolved semantics. For a workshop it holds the three that need a Site and a folder (#62): `argv[0]` is a wrapper the Permit allows, in the same words a tool's refusal uses; every knowledge file it may read is a plain file in the pack's own `knowledge/`; and every licence seat it holds is one the Site declares at least that many of, exactly as a tool's is and printed in the same list (`workshop mine holds 1 of "Design-Compiler": site local declares 1`) — a workshop whose seat the Site has none of would otherwise sit in `waiting-for-slot` until its time box ran out. Everything else about a workshop is in `contract.yml` alone and is refused when the pack is loaded. And the same rule from the other side: **every value type the pack's own `semantics.yml` declares is emitted by at least one of its own readers**, because a vocabulary nothing produces is a rule nothing can ever rule on. Rules and choosers alike are collected from **every** graph the pack holds, its drill-down loops included, so a rule only a Loop's judge node names is resolved here rather than at that judge node an hour in. **Every resolved id says where it came from**, which is what a pack folder resolving first makes worth printing — and an id that resolved and then failed on something else says both, because which of the two files answered is exactly what a person about to edit one of them needs to know:

```
pack carries-its-own@1 on site local: fit — 3 of 3 inputs bound, 1 tool, 1 workshop, 2 rules, 1 reader, 1 chooser, 1 knowledge file, 1 licence
stage: none; next: intent — INTENT.md, written by /hima-grill
rules:
  clock-period-at-most@2: found in the pack
  setup-wns-all-nonnegative@1: found in the bundle
workshops:
  mine — sh, writes hima-workshop/mine/miner.sh, produces candidates (read by count-candidates)
readers:
  dc-qor-report@1 reads qorReport: found in the bundle
semantics:
  8 value types come from the bundle
choosers:
  timing-push@2 chooses at next-period: found in the pack
knowledge:
  push-method.md (why this pack pushes the clock period the way it does): found in the pack
```

The `stage:` line is how far up the pack authoring pipeline that folder has come and what the next rung wants ("Pack authoring pipeline" below). It is reported and never judged: the packs this repository ships were written by hand, stand at `none`, and are as fit as anything the pipeline will author.

It touches no Site — every one of those answers is in files this machine already holds — so it can be run before a Site is even reachable.

`/hima pack prepare <pack> --site <site> [--campaign <id>]` gives a Campaign the workspace its generations run in: `<workspaceRoot>/<campaign>/`, with what the contract's `workspace.copy` names copied out of the bound `flowRoot` into `<workspace>/flow/` (about 56 MB for `opene902`), and a `workspace.json` saying what was prepared. The flow derives its project root from its own location, so a copy builds into the copy and the Site's own results are never written (D19); the one thing that does not follow from the copy's location is the container the flow's wrapper creates by name, so every tool line carries `EDA_CONTAINER_NAME=hima-<campaign>` and the workspace records that name. Preparing twice for one Campaign is a no-op that says so — the 56 MB is not paid twice, and a generation's results would not survive it being. Twice for *that* Campaign, though: the `workspace.json` already there is held against what this preparation is for, and a workspace belonging to another campaign, pack, design, Site or flow root is named as such and prepared into by nothing. So is a directory carrying no `workspace.json`, and one whose `workspace.json` cannot be read as one — all three are the same answer, because this harness removes nothing on a Site and a person decides what becomes of what is there.

**HimaFabric** executes a pack's graph. `/hima run <pack> --site <site> --goal <name>=<value>` creates the Campaign (its id is the pack, the time, and four hex digits drawn at random, so two runs of one pack started in the same second are two campaigns in two workspaces rather than one workspace synthesized into twice), opens the Run with its Goal and its Budget, prepares the Campaign workspace if it is not already there, and then advances the Run one node at a time until it stops. Four node kinds and no more (D29):

- **act** with a `tool` — launch that tool as a Job in the Campaign workspace and wait for it. The command line is the contract's `argv` with `WORKSPACE`, `FLOW_ROOT`, `DESIGN` and `CAMPAIGN` bound from the Run and the Site's bindings, and the node's own arguments bound from the Run's current strategy or its Goal. Those four names are the harness's own: a node's `arguments` may not bind one, and a graph that does is refused when the pack loads, naming the node and the name. `argv[0]` is what the Permit decides on. The wait polls the Job's status at a bounded interval; the first look that sees it end writes the `finished` record with the exit code the launch wrote.
- **act** with an `observes` — read that output of the contract, at its path inside the Campaign workspace, through the reader the contract names, into this Run.
- **act** with a `workshop` — open a Model moment at this node, let it write a script inside the directory that workshop declares, and then launch what it wrote as a Job exactly as a tool's is ("Workshops" below).
- **judge** — ask HimaJudge for a verdict per rule, in the order the node lists them, with each rule's declared parameter bound from the Run (`target_period_ns` from the Goal). The outgoing edge is the one labelled with the outcome of the **first** rule — the constraint the pack chose to branch on. An `UNDETERMINED` the pack labelled no edge for leads to the graph's wait node instead of ending the Run: a rule that could not be applied is not a result to end on.
- **explore** — apply the chooser the node names, by id, resolved in the pack's own `choosers/` before the bundle's, and write the decision — which carries `chooserOrigin`, which of the two places that id answered to, because two packs may name one chooser and mean two different clauses. Every chooser is deterministic and model-free. The bundle's `timing-push`: on a constraint PASS the next period is the period the report stated minus the measured slack plus the guard band the node bound; on a FAIL it is that period plus the violation plus the guard band; when the goal rule passed as well there is no next strategy and the decision is that the Goal is met. `over-constraining-push`: on a PASS the next period is the period stated minus the step the node bound, the margin never read; on a FAIL it is that period plus the violation minus the step; the goal-met clause is the same. All of them are clauses of `choosers/<id>.yml`, not code. Periods are rounded to three decimals, a picosecond, past any tool's resolution. A fourth outcome is weighed between the goal-met clause and the next period, and it is not a clause: **converged**, when the node's own `converge:` says the exploration has stopped learning (below). An explore node that names `opens:` instead of a chooser applies none: it drills down into the loop it names, and what it decides is that loop's to say (below).
- **wait** — the Run stops for a person; its status becomes `waiting`. Nothing has to draw an edge here: a Hard blocker and an `UNDETERMINED` the pack labelled no edge for are both routed to the graph's wait node by the fabric itself. A graph declares at most one of them, each drill-down loop counting as a graph of its own; two would leave which of them a person is sent to to the order the nodes happen to be written in, so a graph declaring two is refused when the pack is loaded.

A node with no outgoing edge ends the Run: `ended-goal-met` when the decision says the Goal is met, otherwise `ended-goal-not-met` with the next strategy on the run row.

**Fork and join** are edges and not node kinds (D29, CONTEXT.md). An act node with **two or more unlabelled edges out** forks: each branch is the chain of act nodes from that edge's target on, following the one edge out of each, until the first node with two or more incoming edges — the **join**, which must be a judge node, because judging all of them together is the only thing that can be done with several answers at once. Every branch of one fork reaches the same join, a branch holds act nodes only, no fork holds a fork, and no drill-down loop's graph holds one: fork and drill-down each go one level in step 3 and neither nests in the other. All of that is refused when the pack is loaded, in the words a person reads their own file in. Only an act node forks, and that is the whole of the widening: an act node's edge out was always the unlabelled "and then", and now there may be several of them; a judge node is left along the edge its first rule's outcome labels, an explore node along the one its decision allows, and a wait node when a person clears it.

```yaml
edges:
  - { from: start, to: synthesize }     # a fork: two unlabelled edges out of one act node
  - { from: start, to: synth-b }
  - { from: read-qor, to: judge }       # the join: two edges in, so the run waits for both
  - { from: read-qor-b, to: judge }
```

HimaFabric opens the fork in **one write** — the branches and the join together — and the run row then stands at the join with `fork` saying which branches it is waiting for. The branches are driven at the same moment, each branch's node turns being exactly the turns any other act node takes, with that branch's id on every record they write. How many really run at once is the Site's answer and not the graph's: every launch goes through the same claim step, so a Site declaring one job slot runs the branches one after the other with a `waiting-for-slot` record on whichever is queued (which is what the reference site, whose cap is one, does — D33), and a Site declaring two runs both. A branch that spends its Retry allowance blocks **itself**: the others go on, and only when every branch has settled and one is blocked does the Run wait for a person, with the fork left exactly as it stands — a resume re-enters that branch alone, with a fresh allowance, and the branches that reached the join stay there. One resume clears one blocker, so a Run with two blocked branches takes two: the branch nobody has cleared is not re-entered by another branch's resume, and the Run waits again for its own. A cancel stops every branch's Job and records each stop. A host taken away inside a fork is replaced by one that picks up each branch's Job by its session and re-runs the nodes of the branches that had none, so nothing is launched twice. A Site that stops answering inside a fork is read over the branches and not over the join: the rule is that a fault which cannot be recorded without leaving a Job of ours unattended is raised and nothing is written, and inside a fork the Run stands at the join — a judge node that launches nothing — while the Jobs are in the branches, so one branch with a Job still open is enough to leave the row exactly as it was for the next poll, the next boot or a person.

When every branch has reached it, the fork closes in one write and the **join** is judged: one verdict per rule per branch, each over that branch's latest reading and carrying its branch id. The outcome the join's own edge is labelled with is taken over the **first** rule of each branch, exactly as an ordinary judge node's is over its own first rule: PASS only when every branch's is PASS, UNDETERMINED when any is, else FAIL. Whether a judge node is a join is read off the graph and never off the run row, so a host that died between the close and the judging judges it the same way.

**The Loop** is the pack's own data (D43). An edge in `graph.yml` may say `revisit: true`: it leaves an Explore node, leads to an act node, and is the only kind of edge a graph may close a cycle with — anything else that goes back is refused when the pack is loaded, naming the cycle it walked, because a loop a reader cannot see in the file is one the engine would be running behind it. What the Run does when an Explore node settles is the **decision's** to say and not the graph's: goal met ends the Run `ended-goal-met`, converged ends it `ended-converged`, and only a next Strategy has anywhere to go. Following the revisit edge is **one write** of the run row — the target node, the **generation**, and the Strategy the decision chose, together — so no host can die between two of the three and leave a Run running last generation's Strategy under this generation's number. An Explore node whose graph draws no edge out of it ends the Run as it always did.

**Drill-down** is that Loop one level down (#28). A pack may declare `loops:` beside its graph, each a graph of its own — the same four node kinds, its own `entry`, its own Explore node with its own `converge`, its own revisit edge, and at most its own wait node:

```yaml
loops:
  push:
    entry: synthesize
    nodes: [...]
    edges: [...]
```

An Explore node opens one with `opens: <loop>` in place of a chooser, and HimaFabric then drives the Run through that graph until it reaches one of the three endings a Loop can reach: `goal-met` and `converged` are its own Explore node's decision, and `generation-limit` is its own `converge.generationLimit` spent. Node ids are unique across the whole pack, and no edge crosses between a graph and a loop: the only way in is an Explore node that opens it, and the only way out is that loop closing. A loop's Explore node applies a chooser and may not open a second loop — drill-down goes one level in step 3. **Every** edge out of an opening Explore node carries one of those three outcomes, and none of them revisits — that node is left along the edge its loop closed with and along no other, so an unlabelled edge there is a route the file shows and the Run could never take — and no node draws two edges carrying the same label, a judge node's outcomes included, because the engine takes the first edge that matches and a fork the line order decides is a route nobody can read off the file. Both are refused when the pack is loaded.

What a Run carries while it is down there is the run row's `loop` and nothing else, which is why a restart in the middle of a nested loop carries on inside it: the row says which loop is open, which Explore node opened it, and which generation of it the Run is in, and `currentNode` says which of its nodes the Run stands at. Every record written inside it carries that loop's id and that loop's generation, bracketed by the `loop` pair. The loop's own `converge.generationLimit` bounds *its* generations, the Run's `budget.generationLimit` bounds the outer ones, the time box spans everything, and the retry allowance is per node per generation — the loop's generation, inside it. A Hard blocker inside a loop is routed to the loop's own wait node where it declares one, and otherwise to the graph's, where the Run waits with the loop still open; the resume re-enters the node inside the loop that failed. A cancel inside a loop ends the whole Run, and the loop is left `opened` on record with no `closed`, because that is what happened.

When a loop closes, the Run stands back on the Explore node that opened it and the outer graph goes on along the edge that outcome labels: `- { from: probe, to: final-read, outcome: converged }`. Where no edge labels it, the Run ends as if the outer graph itself had reached that ending — `goal-met` ends it `ended-goal-met`, `converged` ends it `ended-converged`, and `generation-limit` ends it `ended-budget-exhausted` with `meters.endedBy: generation-limit` — because a pack that asked a sub-question and drew nowhere for the answer to go has said the answer is the Campaign's. An edge out of an opening Explore node carries one of those three outcomes, an edge out of a judge node carries a verdict outcome, and no other edge carries a label at all.

**Convergence** is declared on the Explore node, in its chooser's own vocabulary:

```yaml
converge: { read: period, band: 0.05, generations: 1, generationLimit: 6 }
```

`read` names one of the chooser's own `reads` — `/hima pack check` holds it against them and says so before a Campaign exists — `band` is a distance in that read's unit, and `generations` is how many successive generations must each have moved that **measured** value by less than the band, from the generation before it, before the decision is `converged`. The move is compared as the record states it, rounded to the three decimals every period on the ledger is rounded to, so a decision and the rationale beside it are one arithmetic and never disagree at the band itself. The reference pack's band is its own guard band, 0.05 ns — the margin it asks a closed design to keep — and not one tick of Design Compiler's two-decimal period, which is the resolution of the instrument rather than a statement about convergence. It takes `generations + 1` values to make that many moves, so a Loop cannot converge before it has run that many. The harness evaluates it, over the values the ledger holds: a chooser clause sees one generation, and "successive generations stopped moving" is a statement about several. The decision record carries the whole rule — the read, the band, the generations counted and the values compared — so a person re-derives the ending from one record, and both mounts of the card and `/hima status` say it in words: `converged: period moved by less than 0.05 over 1 generation, at 2.15 then 2.15` — the sentence the over-constraining push settles on against the stand-in flow that closes at 2.20 ns, which is the trace `test/contract/honest-standin.test.ts` asserts.

**A generation** is one turn of the Loop (CONTEXT.md): the act nodes run once with one Strategy, judged, and decided. The run row carries the one it is in, counted from one, and HimaLedger stamps every record's header with it as it appends, so no caller passes one and the ledger reads as the exploration ran. The Retry allowance is per node **per generation**: a node that failed twice under one Strategy starts afresh under the next, because that is a new attempt at a new question and not a third go at the old one.

**The Budget** is a time box (60 minutes by default, `--time-box <minutes>`, fractional allowed), a retry allowance per node per generation (three by default, `--retries <n>`), a **generation limit** (`--generations <n>`, else the pack's own `converge.generationLimit`, else six), and the Site's own slots copied at start: the job cap from `capacity.parallelJobs` and the licence seats from `capacity.licences`. The generation limit is a meter and not a convergence — convergence is what the exploration learned, the limit is what the Campaign was allowed to spend learning it — and a revisit that would open one generation past it does not: the Run ends `ended-budget-exhausted` with `meters.endedBy: generation-limit`, the decision it was not allowed to act on still on record. A spent time box kills the running Job through the same kill the `/hima job kill` face uses, waits for the session to be observed gone, records the `killed` Job event and the node as `cancelled`, and ends the Run `ended-budget-exhausted` with `meters.endedBy: time-box`. The box is measured from when the Run was opened, plus however long the Run has spent waiting on a person — the deadline is `createdAt + timeBoxMs + meters.waitedMs`, where `waitedMs` is the time from each Hard blocker to the resume that cleared it. The Budget meters the design and the EDA environment and never the person, and a Hard blocker is by definition something only a person can clear: a node that blocks at minute five of an hour's box and is cleared the next morning has five minutes of that box spent, not a night. Both terms come out of the records, so a Run picked up by a later process computes the same deadline.

**The Budget is the Campaign's, and only two of its five meters can end a Run.** The time box spans every generation, and the generation limit counts them; either running out is `ended-budget-exhausted`, with `meters.endedBy` saying which. The other three only ever make a Run *wait*: a spent retry allowance is a Hard blocker a person clears — the allowance is per node per generation, so the same node in the next generation starts afresh, and so does a resume — and a full Site, full of Jobs or of one of the licences it declares, is a slot the node queues for, still on the attempt it was on. Every meter is shown against its bound, in one wording wherever it is read (`card-labels.ts`, `meterLines`): elapsed against the time box, with each generation's own time beside the generation against its limit; jobs launched beside the job cap, which bounds how many may run at once rather than how many there may be; the node the Run is spending its allowance at against that allowance, and the Campaign's own count of turns taken beside it; each licence's seats held against the seats the Site declared, with what it has cost in licence-milliseconds; and, on a Run something ended, that meter in words. Both mounts of the card show them as their own section — `run-meters`, one row per meter in three columns: what the meter is called, the meter drawn as a bar against its bound, and the rest of the sentence that says it. Three meters carry a bar, the three whose bound accumulates in the same kind (elapsed against the box, the generation against the limit, the attempts at the node spending the allowance against that allowance); the other two leave the bar column empty, because their own pair of numbers is not a quantity against a bound of its kind, and carry both numbers in the sentence. `/hima status` prints the same sentences whole, one to a line — the name is split off the front of a sentence only where the sentence opens with it, so the words are one wording however they are read. The Retry allowance's line names the node the Run is actually spending it at, which at the pack's wait node is the node that blocked and not the wait node itself — the same pairing a resume makes when it re-enters a waiting Run, because "attempt 1 of 3" about a wait node would say the allowance is untouched at the moment it is spent.

**The meters** are what the Run has spent, all of them computed from its records and never from a driving process's memory: `elapsedMs`, how much of it was `waitedMs` on a person, `generationMs`, how long each generation took — the span of that generation's own records, and of the current generation of a running Run to now, one entry per generation the Loop has opened — `jobsLaunched`, `attempts`, `endedBy` on a Run a meter or a person ended, and `licenceMs` — for each licence, the seats a Job held times how long it held them, summed over every Job of the Run that has settled. A Job holds its seats for exactly as long as its launch is open, which is the rule below read in time rather than in the present tense: from its `launched` record to the first record that settled it, its own `finished` or `killed`, or the node record by which the Run gave up on it. Milliseconds and not minutes, so one unit spans the row beside `elapsedMs` and `timeBoxMs`; `/hima status` and the Run card spell it however a person reads. `generationMs` is wall time and counts a wait on a person exactly as `elapsedMs` does, `waitedMs` beside it being what says how much of the Campaign was one — it is the number the run view's generations table shows per row, kept on the row as a meter so a face showing no table can still say where the box went. Its entries are the **outer** Loop's generations, the ones the row's own `generation` counts, and each of them spans everything that happened while it was the outer generation, the records a drill-down Loop wrote inside it included — those carry that Loop's own generation in their headers, and it is the Loop's `opened` record that says which outer generation the whole block belongs to. So a Campaign's time is accounted for once at the depth a person reads it at, and the table's nested rows are where the same time is broken down further; the table's outer row spans the outer graph's own records, which comes to the same number for every Loop that closed and stops earlier on a Run somebody stopped inside one.

**An attempt** is one try at a node, numbered from one and counted out of the Run's own records — one past the highest attempt number any record of that node carries, never out of a counter a restart would lose. A Job that exits non-zero, or that vanishes without writing an exit status, is a failed attempt. Within the Run's **retry allowance** the node writes `retrying` and takes another turn: a fresh Job, in a fresh tmux session, with its own log and its own exit file, so no attempt can read another's exit code or write over the log it left. The generation that succeeds is the one that counts.

When the allowance is spent the failure becomes a **Hard blocker**: a `blocker` record carrying the attempts, the last exit code and the tail of that Job's log; the node `blocked` carrying the same sentence; and the Run routed to the pack's wait node with status `waiting`. Nothing retries a pack's own faults — a tool the contract does not declare, an argument the Run cannot bind, a launch the Permit refused — because a second identical attempt cannot come out differently; those block at once, as they always did.

`/hima resume <runId>` is the person clearing it. Only a run that is `waiting` can be resumed; a running or ended run is answered clearly and nothing is written. A resume records who acted, re-enters the node the blocker names — the node that failed, never the wait node the Run was routed to — with a **fresh allowance**, and drives the Run on. The blocker it clears is the latest one no resume has cleared already, read off the `clears` those resumes name, so a Run holding two uncleared blockers at once (which only a fork's branches produce) takes one resume each and neither is left standing for ever. Everything it needs it reads back out of the ledger, so a Run blocked before a restart is resumed by a later host exactly as by the one that blocked it, and its next attempt is numbered from the records the first one wrote. A Run whose box was already spent at the moment it stopped is refused instead, naming the box and when it stopped: resuming it could only end it `ended-budget-exhausted` on its first turn, and it must not do that with a person's record in the ledger claiming they cleared something.

**The cap** is over all of one Site's slots at once: its `capacity.parallelJobs`, **and each licence its `capacity.licences` declares**, both as the Run copied them at start. Before a node launches, the Jobs that Site is holding are counted — every Job with a `launched` record and neither a `finished` nor a `killed` one, across every Run of that Site, because a machine and a licence are the Site's and not a Campaign's — and the launch is held against every slot: the count of those Jobs against the job cap, and, for each licence the tool being launched holds, what those Jobs' own `launched` records say they hold against what the Site declares. Full on any of them, the node records `waiting-for-slot`, once, naming what was full, and looks again on the Job poll's own interval until it frees; the time box bounds the wait, as it bounds every other. Waiting for a slot is not a failed attempt and spends no allowance: the node is still on the attempt it was on. One rule and one step for both scarcities, never a second chain — a count taken outside the step that serializes launches on a Site is a count another Run can launch in between, which is the very window that step exists to close.

**A licence** is declared in two places and matched by name. A Site says how many seats it reserves for the harness (`capacity.licences`, `Design-Compiler: 99` on `linglong`); a pack's contract says how many a Job of each tool holds (`tools[].licences`, one `Design-Compiler` seat for the timing probe's synthesis). A **count of 0** is a licence the Site owner reserves nothing of — the reference site's node-locked `Innovus_Impl_System: 0`, which has no seats to budget — and a licence **absent** from the map is one the Site does not declare at all. Either way a tool that holds one can never launch there, so `/hima pack check` says the pack is unfit and names it, and `/hima run` answers the same before a Campaign exists: the alternative is a Run that waits for a seat that will never come free until its time box runs out. A Job launched by hand with `/hima job launch` runs a command line a person typed, which no contract describes, so it reserves nothing and is counted against the Site's job slots alone.

Two rules make that count mean something. **The count and the launch are one step per Site**: every launch on a Site — a fabric node's and a `/hima job launch`'s alike — is chained behind the one before it, so the `launched` record of one is written before the next count is taken. Without that, two Runs started in the same instant both pass a check that neither has yet moved, and a Site that declares one slot runs two Jobs. One host process owns a home's ledger, which is what makes chaining inside that process enough. **And every open Job is asked about before it is counted**: the same look `/hima job status` does, which writes the `finished` record the first time it sees a Job end. That is what releases the slot of a Job nobody asked about — one launched by hand and never followed up — without a person having to ask. What is left is a Job the Site says is running, which holds its slot, or one the Site says is gone: no session and no exit status. A gone Job is still counted, because nothing has recorded that it ended — unless the Run that launched it has already settled a node against it (`retrying`, `blocked` or `cancelled` naming its session), in which case that Run has given up on it and nothing will ever write its end. Counting it then would queue that Run's own retry behind its own corpse, and on a Site with one slot the retry would never be launched at all.

`/hima job launch` is under the same cap, counted and taken in the same step, and refuses at it — naming the Site's slot count and the Jobs holding it, so a person can decide whether to wait or to stop one.

**Cancel** is `/hima cancel <runId>`, the `hima_cancel` tool, and `POST /hima/api/runs/<runId>/cancel`. The request is recorded first — a `cancel` record naming the node the Run stood at and the session of the Job it had open — and then the Job is killed through the same kill the time box and the `/hima job kill` face use, which waits for the session to be observed gone. Only then is the stop recorded: the `killed` Job event, the node `cancelled`, and the Run `cancelled` with `meters.endedBy: cancel`. The Job it looks for is **any** fabric node's open launch and not only the node the Run stands at: a Run whose retry allowance is spent stands at the pack's wait node while the Job it gave up on may still be running on the Site, and a cancel that asked about the wait node alone would find nothing, end the Run `cancelled` with the licence still held, and leave it in the one state reconciliation passes over for ever. So the record's fields can name different nodes, and each says only its own thing: `nodeId` is where the Run stood when the request was read, `jobSessions` are the Jobs that were stopped, and the node each stop is settled on is the one that launched it. A `/hima job launch` a person made by hand is never one of them — those belong to no node, and stopping one is `/hima job kill`. The request and the observed stop are two records, in that order, because a cancel is a fact and not a wish: a kill that does not take within its bounded wait cancels nothing, and says so — the node is blocked naming the session a person must go and look at, and the Run waits. That blocker says `the kill did not take`, in those words wherever the kill came from, because it is the one blocker on a Run that means the Job is still running rather than over; the next cancel of that Run asks the Site about the session and finds the Job open again, rather than reading the Run's own blocker as the end of the story. A Job that ended by itself between the request and the kill is not claimed as a stop either; its node settles from the exit the launch wrote, and the Run still ends cancelled, because a person asked it to. Cancelling a Run that has already reached a final state answers with that status and writes nothing at all, and cancelling one HimaFabric never started says so. A cancel that arrives in the moment between the Permit deciding a launch and that launch getting its own record finds no Job open, and ends the Run without one: the loop that made that launch reads the ending a moment later, and stops the Job it has just made — the `killed` event and the node `cancelled` — before it returns, because nothing else ever will (reconciliation passes over a Run in a final state). Which loop owes that stop is read off the `cancel` record, **by name**: a request that names this loop's session is stopping that Job itself and the loop writes nothing, while a request that named other sessions and not this one never saw this launch, so the loop stops it. Read by name and not by which record came first, because a cancel reads what a Run has open before it appends its own record — so a launch can be on record ahead of a cancel that never saw it, which inside a fork would be a whole branch's Job left running with the Run already final.

**A Run has a Job open** while nothing has settled that launch, and only the Site can settle one for good. The Job's own `finished` or `killed` event settles it outright: both are written from something that was observed on a Site. Nothing else in the ledger is — a `retrying`, `blocked` or `cancelled` node record naming the session is the Run's own account of that launch, and a Run can be wrong about a Job it asked to stop and could not. So the rule is both halves together: **a launch with no `finished` or `killed` event is open unless the Run has accounted for it on a node *and* the Site says its session is gone**, and a Site that cannot be asked settles nothing: the cancel and the reconciliation leave the launch open and go and ask about it, while the cap's own asker stops the launch it was counting for outright. Neither reads an unanswered Site as a Job that ended. The Run's half is needed because a Job can end with no record of its own — a Job that vanished wrote no exit status and none is invented for it, so nothing will ever be appended to that Job's history again, and what the Run knows is on the node that blocked on it. The Site's half is needed because a person told "this run was NOT cancelled, its session is still there" asks again, and must not then be told the Run is cancelled and had nothing to stop while the Job runs on — a Run final at `cancelled` is one reconciliation passes over for ever. One rule, read the same way by the cancel that asks what to stop and by the job cap that counts what a Run is holding.

**Reconciliation** happens once, when a host starts, before it serves anything. HimaFabric asks the ledger which Runs still say `running`, and for each one whether its current node has a Job that was launched and that nothing has yet said finished or killed. That Job is found through its own `launched` record — the tmux session name, the workspace, the exact wire — so it is found without any handle the dead host held, and it is asked after through the same `status` operation the waiting loop uses. Still running: the Run waits for it again, where it stands. Finished while the host was down: the exit file the launch itself wrote is read, the `finished` record written, and the graph carries on. Gone with no exit file: a failed attempt, never a silent success — no exit code is invented, and what becomes of that attempt is the Retry allowance's to say, exactly as it is for an attempt that failed while a host was watching. What reconciliation found is itself a record before anything acts on it: a `reconciled` node record under the interrupted attempt's own number, carrying in `reason` what was found. Every one of those decisions is made from the run row as it stands at that moment, never from the list of Runs the reconciliation started with: Runs are picked up one at a time and each is waited for, and the routes answer throughout, so a Run a person cancels while an earlier one is being carried on is left exactly as that cancel left it and reported as untouched.

**Nothing is relaunched.** Exactly one `launched` record exists per attempt however many hosts a Run outlives, which is what makes a restart cost nothing on a Site where one generation is two and a half minutes of licensed Design Compiler. A Run left `running` with no Job of its current node open — a host that went away between nodes, or at a node that launches nothing — is not re-run either: re-reading a report or judging one a second time is nobody's call to make at boot, so the node is blocked saying so and the Run waits. Neither is a Run left claiming to be running while nothing advances it. A Run HimaFabric opened and never started, because a host went away in the middle of preparing the Campaign workspace, is reported the same way: blocked at the node it would have started at, with the reason on the record. That is the only way into that shape, because a preparation that *answers* is blocked at the entry node the moment it answers, carrying the words it used — the path the Permit refused and why, or what is occupying the workspace — so `/hima status` says which path and why rather than waiting for the next boot to re-stamp the Run with something more general. A fault preparation itself throws is recorded the same way, by the same route a node's turn records one.

Every one of those steps is a record, and the run row carries only what the records could not: which node is current, and what the Run is set to. Nothing else is held anywhere. That is what makes a Run readable from the ledger alone.

**The `/hima` command**, every form:

```
/hima version
/hima observe <site> <path> [--reader <id>] [--run <runId>] [--judge <id,id,...>] [--param <name>=<value>]...
/hima judge <runId> --rules <id,id,...> [--param <name>=<value>]...
/hima job launch <site> <workspace> [--run <runId>] [--name <n>] -- <command...>
/hima job status <runId> <session>
/hima job tail <runId> <session> [--lines <n>]
/hima job kill <runId> <session>
/hima pack check <pack> --site <site>
/hima pack prepare <pack> --site <site> [--campaign <id>]
/hima pack release <pack>
/hima run <pack> --site <site> --goal <name>=<value>... [--set <knob>=<value>]... [--test] [--time-box <minutes>] [--retries <n>] [--generations <n>]
/hima resume <runId>
/hima status <runId>
/hima cancel <runId>
```

`/hima run` answers when the Run stops, with the Run exactly as `/hima status` shows it — where it stands, which generation of how many it reached, which drill-down loop it is inside if it is inside one and which fork it is inside if it is inside one (the node that branched, the join it waits at, and how many branches), what it is for, what it was allowed, its meters one line each against the bound each is held to (the same lines the card's meters show, in the same words), the state each node it touched is in, each branch of a fork it ran beside what that branch is doing and how many Jobs it launched, any request to stop it beside the stop that request was answered with, and its decision. A Run that reached a final state is a success whichever one: `ended-goal-not-met` and `ended-converged` are real results, so is a spent meter, and so is a Run a person cancelled from another face while the command waited for it. A Run that could not start, or one that stopped needing a person, is an error. `/hima resume` answers the same way and by the same rule: the Run when it stops again, a success when it reached a final state — including one a person cancelled from another face while the resume was still waiting, which is a cancel that did exactly what was asked — and an error when the Run could not be resumed or stopped needing a person again. `/hima cancel` answers with what it stopped and then the Run, again as `/hima status` shows it; a Run that already ended is a success saying so, and a Run that was NOT stopped — a kill that did not take, a Run HimaFabric never started — is an error. `--goal` is repeatable, one per parameter the pack's goal template names; `--set` is repeatable too, one per Strategy knob the pack declares — a knob it does not name takes that pack's own declared default, and a value read as the knob's kind: a number parsed for a number knob, the word as typed for a choice knob. `--generations` defaults to the pack's own `converge.generationLimit`, else six. `--test` is a bare flag and marks the Run as the **test run** of its pack whatever stage that folder stands at; left out, the folder decides — a pack the authoring pipeline is still carrying an author through is a test run, a released or hand-written pack an ordinary Campaign. `/hima run` refuses any word of its flag list it did not consume, which is what makes a bare flag safe to have beside five that take values: `--test false` is `unexpected argument "false"` and `--test=false` is `unknown option "--test=false"`, and neither starts a Campaign.

`/hima pack release <pack>` seals a tested folder: it names no Site and takes no other flag, because every fact it uses is on this machine. It writes `VERSION.yml` with the version the contract declares and one sha256 per file the harness computed, and answers with what was sealed and the Run its test record rests on. It refuses a folder below `tested` naming the rung it stands on, a folder whose test record this ledger cannot vouch for, and a folder holding anything that is not a plain file. Releasing again over the same version rewrites the seal and says so.

A flag typed with no value is a usage error, not "not given": nothing is read and no Run is created; the same holds for a `--param` with no `=`, an empty name, or a non-numeric value. `--param` is repeatable, one per parameter a rule in the batch declares. The `hima_observe` tool takes the same arguments (`site`, `path`, `reader`, `run`, `judge`, `params: { name: value }`) and answers with the run and record ids. The `hima_run` tool takes `pack`, `site`, `goal: { name: value }`, `strategy: { "<knob>": <value> }` (the pack's own knobs, by the names its contract declares), `test` (a boolean, as `--test` is a flag), `timeBox` (minutes), `retries` and `generations`, and answers with the run it started and where it got to; `hima_pack_check` takes `pack` and `site` and answers the ladder as data beside the words the command prints; `hima_status` takes `run` and answers the run view the route serves, so a stage can write a record from a Run's own records without a browser; a run this ledger does not hold is `unknown` in words and a Run whose pack will not load is `unreadable` naming the pack; `hima_pack_release` takes `pack` and answers what was sealed or why nothing was; `hima_resume` takes `run` and answers with the node it re-entered, the record it wrote, and where the run then got to — or, on a run that is not waiting, why it did neither. The `hima_cancel` tool takes `run` and answers with what it stopped: the kind, the run's status now, the session it stopped and the record the stop was written as. Every word of a command line, the job command after `--` included, is separated by whitespace and is not shell-quoted; a job whose command needs a space inside one word runs it from a script in its workspace.

**A Job** is launched detached in its own tmux session inside a workspace on the Site, with its output in `<workspace>/<session>.log` and its exit status written to `<workspace>/<session>.exit` before the session ends. The session is `hima-<run>-<name>-<random>`, one per launch and drawn afresh rather than counted, so a relaunch under the same `--name` — or a restarted harness — never reads an earlier attempt's exit code as its own or writes over the log it left. `status`, `tail`, and `kill` name the Run and the session, which is what the launch's own record holds: a Job is found again through HimaLedger, never through a handle a restart would lose. The first status that sees a Job end records `finished`; a kill records `killed` only once the session is observed gone, and a second kill answers that it was already gone. A launch is under the Site's job cap wherever it comes from, and every open Job on the Site is asked about on the way in, so a Job that ended without anyone asking still releases its slot.

**What became of a Job is asked in one order, and only tmux's own words are read as an answer.** The exit file is read first: a Job that wrote one finished with that code, whatever a session probe would say, so a Job that ended and whose socket a `/tmp` cleaner removed afterwards still settles. With no exit file, `tmux has-session` decides — and it exits 1 for four different facts, only two of which are about a session. `can't find session: <name>` (older tmux: `session not found: <name>`) is a running server with no such session, and `no server running on <socket>` is the server having exited, which it does when its last session ends, leaving its socket file behind — the ordinary state of a quiet Site. Both mean the session is over, and with no exit file the Job is `gone`: it vanished, and no exit code is invented for it. `error connecting to <socket> (No such file or directory)` is a socket path that is not there at all, and `error connecting to <socket> (Permission denied)` a socket that cannot be reached — and neither says anything about a session. Those two, an exit 1 with no words at all, and every other exit code (an ssh that could not connect exits 255) are **cannot tell**, and a cannot-tell raises and writes nothing: no `finished`, no `killed`, no `gone`, no `blocked` node behind a Job that is still open, and no move of the run row. A Job may be running under a server nobody can reach, and blocking a node on that guess would spend the Retry allowance and leave a licence-holding Job running unattended on the Site. So the poll asks again at its next interval — one line to the host log when a stretch of unreadable looks begins and one when it clears — a restarted host reports the Run `site-unreadable` and leaves it exactly as it was, and every face says which Site could not be asked, in the Site's own words. The job cap launches nothing it cannot count slots for, and asks again the same way: a Run whose Site will not say how many Jobs it is running waits where it stands, writing nothing and holding nothing, until the Site answers or its own time box runs out — which is where a Run resumed onto a silent Site sits, rather than being left `running` with nothing driving it. A time box that runs out while the Site is silent is the one write this rule adds: nothing was stopped and nothing claims it was, so the node is blocked saying *the kill did not take* and the Run waits for a person. The one place a missing socket **is** an answer is the uniqueness check a launch makes before it picks a session name: `tmux new-session` starts the server it will then talk to, so a Site where tmux has never run holds no session of any name.

**When a Site's socket is gone for good** — a cleaner removed it from under a living server, and every question now answers `error connecting to`, for ever — the way out is on the Site and takes a moment: start and end one tmux session there (`tmux new-session -d -s probe true`), which makes a fresh server and a fresh socket, or send the living server `kill -USR1 <its pid>`, which is tmux's own instruction to recreate the socket it lost and keeps the sessions already running under it. The harness does neither by itself: nothing in it creates or removes a path on a customer's Site, and a Job of theirs is running behind that socket.

**The Permit** decides a Job as well as a read: a launch whose workspace does not resolve inside one of `allowedWriteRoots`, or whose first word is neither the full path nor the bare name of one of `allowedWrappers`, is refused before anything is launched and the shell writes a refusal record. The wrapper decision needs nothing from the Site, so it is made first — a command the permit will not run reaches the Site not at all. The same Permit decides the harness's own writes: every directory a Campaign workspace is made of, the flow copied into it, and the `workspace.json` that records it are resolved on the Site and tested against `allowedWriteRoots` before a single command is sent, and a refusal means nothing was sent at all. A target that does not exist yet is decided on the deepest ancestor that does resolve, and the first segment below that ancestor must then be nothing at all — a symlink pointing at something missing exists, fails to resolve, and a copy would write straight through it at the link's target, outside the write root if that is where it points. Separately, HimaChannel runs only its own small vocabulary on a Site: the read-only probes `cat` and `realpath`, the job plumbing `tmux`, `test`, `cat`, and `tail`, and the workspace plumbing `mkdir`, `cp`, and `tee`. Nothing on the first two lists creates or removes anything, and nothing on any of them removes anything at all — `rm` is on none of them, because nothing in this harness removes a path on a Site and a verb admitted before a caller needs it is permission granted on a customer's machine that nobody asked for. That holds for the one case that would most like an exception, a workshop's own write the ledger then would not record ("Workshops" below): the bytes stay where they landed and the harness says where they are instead. The three lists are disjoint from each other and from the permit's `allowedWrappers`: the permit says what a *user's* command may be, never what Hima's internals are, and the two are governed differently — a channel verb runs with the arguments the harness itself chose, each decided against the write roots first, while a wrapper runs with whatever arguments a Job's launch names and only its workspace is decided. Listing `cp` as a wrapper because preparation copies would hand a Job an unconstrained copy to anywhere the login can reach. Every command on any of the three lists is recorded at the wire before it is sent.

A failure is never an empty answer: the body is `{ "error": { "code", "message" } }` with one of

- `hima/run-not-found` (404) — no such Run in the ledger.
- `hima/record-not-found` (404) — no such record in the ledger.
- `hima/bad-request` (400 malformed body or query, 404 unknown route, 405 wrong method) — including an unknown site, an unknown pack, an unknown rule, a `run` the ledger does not hold or that belongs to another Site, a run request with no goal or no first strategy, a Site that cannot host the pack, a Campaign whose workspace path is occupied by something that is not its own, and a resume of a Run that *is* waiting but cannot be re-entered here — its workspace record, its node or its pack is gone.
- `hima/run-not-in-state` (409) — the Run is there and the request is well formed, but where the Run stands is not a state that request can be made of: a resume of a Run that is not waiting, a cancel of a Run HimaFabric never started. Its own code and its own status because there is nothing in the request to correct, and because another face may have moved the Run a moment ago — a workbench that read a waiting Run and posted a resume the instant a command line resumed it should re-read the Run, not rewrite its body. Nothing is written on either.
- `hima/not-authorized` (401, 403) — the web app's fence refused the request before it was read.
- `hima/run-not-stopped` (409) — a cancel killed the Run's Job and the Site did not report the stop inside the bounded wait. Nothing the caller sent is wrong and nothing inside the harness failed: the Site was asked to stop a Job and still has it. Its own code because it is the one conflict re-reading the Run does not resolve — the message names the session that is still there, and so does the Run's own blocked node.
- `hima/site-unreadable` (503) — a Site would not answer a question about a Job, so nobody knows the answer and **nothing was written**: not the caller's mistake, and nothing inside the harness failed either. The Run and its Job are exactly as they were, and the thing to do is ask again once the Site is back, which is what 503 says and no other code here does. Its message carries the Site's name and the Site's own words, because there is nothing written for the caller to fetch instead, and those words are what an operator acts on.
- `hima/internal` (500) — the fault was ours. The body names the route and nothing else, with one exception: a fault mid-drive carries its own message, the same text already written to the Run's blocked node, which the same fenced caller can already fetch through this namespace — that message may be raw errno text. Every other reason is in the host's log.

The browser adds one code of its own, `hima/unreachable`, when a request got no answer at all.

**The card** is what a person actually sees. The HimaGuide browser module claims the `tool.call.toolview` key of both Hima tools that answer with a Run — `hima_observe` and `hima_run` — and renders the same card for each, because both answer with a run id and the card reads the Run itself through `GET /hima/api/runs/<id>`; a second component for the second tool would be the same JSON rendered twice, drifting apart. `hima_cancel` and `hima_resume` claim no key on purpose: each answers about a Run whose card is already on screen, and a second copy of it would tell nobody anything new.

The card reads, in the order a person asks: **where the Run stands** — the status in the ledger's own seven words, with the pack, the Goal, the strategy, the Budget — the box, the allowance, the job cap and the Site's declared licence seats — and the meters (elapsed, how much of it waited on a person, jobs launched, turns taken, how long each licence was held, and what ended it, named in words — *the time box*, *the generation limit*, *a person's cancel* — from the one table `/hima status` reads it from); **the path** — one numbered row per node the Run touched, in the order it reached them, each with its kind, its state, its attempt, the outcome a judge node reached, the session it waited on and how that Job ended, and the reason in words whenever the state has one; **the cancel** a person asked for, beside what it found; **the blocker**, with the tail of the failed Job's own log, so nobody has to log in to the Site to see why; **what was refused or observed**, with every typed value; **the verdicts**, each with the observation it cited resolved into it; and **the decision**, with what the chooser chose, the named numbers it chose from, and each cited record named as what it is — a verdict or an observation this same view already carries, so nothing has to be fetched twice to resolve a citation. Every run status and every node state has a word in the card, by construction: the two label tables are keyed by `RunStatus` and `NodeState`, so a state added to the ledger is a build error here rather than a blank on screen.

The card is also where a person **acts** on a Run: a **cancel** control while it is running or waiting, a **resume** control while it waits, and beside them the reason a click was refused. Both act over the routes in the table above, with the session the card was loaded under, and neither mount holds any Run state of its own — the answer to a click is the Run, and that is what is then shown. The cancel section says what was *observed* of the stop it asked for — the kill seen to take, a Job that had already ended, a kill that did not take, a Site that could not be asked — because a cancel is two records and never one (the asking, and what actually stopped), and a status of `cancelled` without the second is exactly the guess the control was clicked to avoid: a licence is not free until dc_shell has really gone. The latest blocker's log tail is a region of its own, so nobody has to log in to the Site to read why a node gave up.

**The window** is where that card is read, and it is the only place it is read: HimaGuide is delivered as a desktop window and never as a browser tab (D39, [ADR-0003](docs/adr/0003-desktop-window-around-the-hima-profile.md)). `pnpm run desktop` starts one Electron main process which **prepares the home**, then starts `dsh --profile hima --host 127.0.0.1 --port <free> --no-open` as its own child, waits for the tokened URL *and* for the host to actually answer, sweeps every stale `dsh-auth-*` cookie off that loopback origin, follows the token inside the window's own session, and loads the page in one `BrowserWindow` titled HimaHarness — whatever the page inside it calls itself. The window has a native menu (quit, reload, developer tools, zoom, and two places in the host: **Chat**, dsh's own page at `/`, and **Workbench**, the page at `/hima/`) and remembers its size and position between launches. Closing the window stops the host: SIGTERM, four seconds, then SIGKILL, so a host holding a session lock and an append-only writer gets to close them — and the child is stopped whether or not the boot had finished, so quitting while the host is still coming up leaves nothing running.

**A Campaign is started in the window**, from the form at the top of the workbench page: the pack and the Site chosen from what this home has installed, the Goal's target period, the first period, the time box in minutes, the Retry allowance and the generation limit typed, and one click. The page posts them to `POST /hima/api/runs/start` behind the same session fence everything else on it reads through, and opens the new Run's card the moment the Run exists — HimaFabric goes on driving the Campaign in the host, and the card catches up with it once a second. A value the shared validator will not take is refused in the window in that validator's own words, with no Run started, because a form is the fourth face onto an operation whose other three already agree (`/hima run`, `hima_run`, `POST /hima/api/runs`). Nobody has to open a terminal to begin, and nobody has to keep a request open to watch.

Preparing the home is `src/hima-home.ts`, and it is the same five operations the contract suite makes its throwaway homes with: the profile template copied to `$DSH_HOME/profiles/hima` — which carries the bundle list dsh boots and `cordis.patch.yml`, the privacy overlay — with `@hima/harness` linked into the profile's own `node_modules`, and the agent presets the bundle ships copied into `$DSH_HOME/.agent-presets`, where dsh's own preset roster looks for a person's (today there is one, `hima-moment`; see "Model moments" below). `$DSH_HOME` is resolved the way dsh resolves it, so an unset or blank one means `~/.dsh`. A home with no hima profile in it gets one; a home that already has one keeps it, and only the link is refreshed to this checkout's build. Each step is printed. So `pnpm install && pnpm run build && pnpm run desktop` opens the workbench on a machine that has never run HimaHarness, which is what `test/contract/desktop.test.ts` proves by starting from an empty home, through the shell's own driver mode.

Nothing about the host is left without a surface. A host that fails to boot is shown in the window, its stderr and all, rather than left in a console nobody opened; a host that *dies while the window is open* is shown the same way, with its exit code or signal and the end of its stderr, because "the workbench is open" and "a host is running" are meant to be one fact in both directions. The window keeps its own title through all of it.

The shell is a window and not a second product. It contributes no plugin, patches no dsh package, disables no row of dsh's plugin tree, and gives the loaded page no preload bridge and no IPC channel; a link whose *parsed origin* is not the host's own opens in the person's browser rather than navigating the workbench away from itself, and one that does not parse at all opens nowhere. (Origins, not string prefixes: `http://127.0.0.1:<port>@evil.example/` begins with the host's origin and is a request to somebody else's machine.) A `target="_blank"` inside dsh's own app navigates this window, because this window is the only surface there is. The host-to-window interface is the `/hima/api/` table above and the workbench page beside it, and dsh's chat stays inside the page (D30). What it shares with the rest of the repository is `packages/desktop/src/host-launch.ts` — the argument vector, the launch-token parser, the readiness probe and the graceful stop — and `src/hima-home.ts`, the home. `test/contract/support/boot-host.ts` boots every route test's host with the first and `createHimaHome` makes every test's home with the second, so the window cannot start a host, or prepare a home, differently from the way the suite does.

The stale-cookie sweep is not housekeeping. dsh names its session cookie after the request authority, which includes the port; cookies are not port-scoped; the cookie lasts thirty days. A fresh port per launch would therefore leave one more `dsh-auth-*` cookie on `127.0.0.1` every time until the request header grew past what Node accepts and the workbench answered HTTP 431 for ever. Needing programmatic access to the window's cookie jar to fix that is why the shell is Electron and not Tauri.

## Workshops

A **workshop** is the scope on an act node where the AI writes code and HimaFabric runs it (#62): a directory under the Campaign workspace, a wrapper, the inputs and knowledge files it may read, and a declared output. It is the one Model moment that enters the fabric, and the harness learns nothing at all about what gets written — everything a workshop is is declared by the pack, in `contract.yml` beside its tools:

```yaml
workshops:
  - id: mine
    purpose: >-                                  # the pack author's own words to the model, verbatim
      Write the mining stage of this method. The campaign has already synthesized at this
      generation's clock period; what is missing is the script that states how many cell
      candidates that synthesis left, in the shape this pack's own reader reads.
    directory: hima-workshop/mine                # relative to the campaign workspace
    entry: miner.sh                              # the one file the fabric runs
    language: shell                              # the word every code record of this workshop carries
    inputs: [ ]                                  # argument names the node supplies, as a tool's
    reads: [qorReport]                           # contract outputs the model may read, by name
    knowledge: [mining.md]                       # files of the contract's knowledge: list it may read
    produces: candidates                         # the output the script must write; it must have a reader
    argv: [sh, '${ENTRY}', '${WORKSPACE}', '${DESIGN}']
```

| field | rule |
|---|---|
| `id` | unique among the pack's workshops; what an act node names with `parameters.workshop` |
| `purpose` | non-empty; becomes part of the moment's instructions **verbatim** and is never interpreted |
| `directory` | one or more plain path segments (`^[A-Za-z0-9][A-Za-z0-9._-]*$`), never absolute, never `.` or `..`, and never colliding with `flow/` or `hima-readers/` |
| `entry` | one plain file name of the same grammar |
| `language` | a slug; a word for the record, which this harness reads as nothing else |
| `inputs` | the argument names the node supplies that `argv` may reference, exactly as a tool's `inputs`; **never one of the harness's own six**, which a pack neither declares nor binds |
| `argv` | non-empty; the command line is **the wrapper, then the entry as its first operand, then the rest** — `argv[1]` is exactly `${ENTRY}` and no other word references `ENTRY`, so `sh -c '<program>' ${ENTRY}` cannot be declared, because the entry is the file the wrapper is given as its first operand and everything recorded about that Job — the `code` record's hash, the read-back before the launch, the `launched` record's `workshop.entry` — is evidence about that one file; `argv[0]` is a **literal** wrapper `environment.wrappers` declares, holding no `${` anywhere, because the check reads that word unsubstituted and the launch runs the word it substituted; and every `${NAME}` in the rest is one of `inputs` or one of the harness's own six: `ENTRY`, `WORKSHOP`, `WORKSPACE`, `FLOW_ROOT`, `DESIGN`, `CAMPAIGN` |
| `reads` | the contract outputs the model may read, by name |
| `knowledge` | the files of the contract's `knowledge:` list it may read, by `file` |
| `produces` | the contract output the script must write. **It must declare a `reader`**, because the declared reader is what turns that output into an observation and an output with none never becomes one |
| `licences` | what a Job of this workshop holds of the Site, exactly as a tool's does |

An act node names one instead of a `tool` or an `observes`, and it is **exactly one of the three**; `arguments:` binds the workshop's `inputs` as it binds a tool's — and **never a name the harness binds itself**: `WORKSPACE`, `FLOW_ROOT`, `DESIGN` and `CAMPAIGN` at any act node, and `ENTRY` and `WORKSHOP` as well at a workshop's. Each of the six is computed by the harness from a path it already decided and is described as such by every record of the Job, so a node binding one would substitute a word of the pack's own choosing under the harness's name — `ENTRY: '-c'` would make `sh ${ENTRY} …` launch as `sh -c …` beside a `launched` block naming the verified entry. The pack is refused when it loads, naming the node and the name. Everything above is held when the pack is loaded, because it is all in one file.

**The three tools**, built per moment and reaching a Site only through HimaShell under the Permit. Every answer is a JSON value:

- **`hima_workshop_write { path, content }`** — `path` is relative to the workshop directory. The grammar is held **before the Site is asked anything**, so a path that could never be allowed sends nothing; then the Permit decides; then the path the Permit resolved must lie inside the **realpath'd** workshop directory, which is the second containment and not a repetition of the first — the Permit's write roots are the whole Campaign workspace, so a symlink an earlier script of the model's own left inside the directory would otherwise be followed straight out. Only then are the bytes sent, on standard input to `tee`, exactly as a reader's script is shipped: the wire carries the command and never its payload. **Then the file is read back** through the same channel, under the Permit: the path must still resolve to itself, the bytes must come, and they must hash to what was sent — and only then is the `code` record written, of the bytes that were read back. Every refusal — grammar, Permit, containment, a channel that failed, a read-back that did not answer for what was sent — is a `refusal` record naming the path **as the model spelled it** and an answer `{ wrote: false, refused, reason }`, so the model reads why.

  What that promises, exactly: **no landed byte goes unrecorded** — as a `code` record when the harness verified what is there, as a refusal naming the path when it could not, and, when the ledger itself will not take the record, as a path **named** in the three channels that are left: the tool's own answer to the model (`{ wrote: false, reason }`, carrying the path and the ledger's words), the host log at the instant the append failed (`hima: workshop <id> landed <path> and the ledger would not record it: <error>`, which is the operator's channel and the only one that does not depend on either the ledger or the rest of this turn), and the node the Run then blocks at, which names the path too — a Hard blocker, because a retry would only write another one. **In that order, reversed**: the fault the node blocks on is set first, then the answer is composed, then the log is written inside its own `try`. The log is the one of the three the harness does not own — it is the host's logger — and a throw from it is reported in the answer's reason (`; and the host log would not take that either (…)`) and swallowed, because a best-effort telling that pre-empted the fault would leave the turn reading an empty box, retrying the node, and landing a second unrecorded file. **The harness deletes nothing on a Site, ever**, this case included: the bytes stay where they landed and are accounted for in words. It does *not* promise that a refusal means nothing landed. A `tee` that fails with ENOSPC can leave a partial file behind it and an ssh response that never comes back can leave a whole one, so a channel failure is a refusal about a path and never a statement about the bytes at it. What the audit does show is that no `tee` was ever *sent* for a write refused before the Site was asked — the grammar, the Permit and the containment all refuse ahead of the wire.

  And what stays outside this boundary, for a workshop exactly as for every other Job: a process running on the Site with the Site user's rights — a script the model wrote that forks a background child, anything else logged in as that user — can rewrite the workspace between any two of the harness's commands. The workshop bounds what the model's *tools* do, and the harness records only what it read back and launches only what still hashes to its record; a hostile process on the Site is the Permit's and the Site login's business, as it is for `make`. Nothing here claims more.
- **`hima_workshop_read { output }`** — one of the declaration's `reads`, at its bound path under the workspace, through `decideRead`. The text is capped at 256 KiB and the answer always says `truncated` — `true` when it was cut, `false` when it is the whole file — because a silently shortened file is one the model would reason about as though it had seen the end of it, and an absent key is a thing to infer rather than a thing to read.
- **`hima_workshop_knowledge { file }`** — one of the declaration's `knowledge`, read from the pack folder **on this machine** and never from a Site, with what the pack says it is for.

None of the three is one of the names the pack authoring guard governs (`write`, `edit`, `bash`), which is what makes them tools a moment may be opened with at all.

**The instructions** are the whole of the moment's system prompt, and they are a fixed frame in the harness's own words: what a workshop is and that nothing it says is acted on; the node, the attempt and the allowance; the purpose verbatim; the directory and the entry, absolute on the Site, with the command line that will run it; the outputs it may read by name and bound path; the knowledge files by name and purpose; what it must produce — the bound path, the reader that reads it, and the value types that reader emits with the units the resolved semantics give them; the argument values of this attempt; and the three tools. The ask is one line: `Write <entry> now, and say so when it is written.`

**The `code` record** is one per **version** of a file that actually landed — a moment that writes its entry, thinks again and writes it over leaves two records and one file, the launch gives the wrapper, as its first operand, the version the later record hashes, and every face counts files (distinct paths) rather than records: `nodeId`, `attempt`, `sessionId`, `workshop`, the absolute `path` on the Site, `sha256`, `bytes` and `language`. It is written after the bytes are on the Site and never before, because it is the claim that the file is there. The run view serves every one of them as `code`, the records route serves `?type=code`, and the card lists this attempt's **files** under the workshop's standing line, one row each at the version that is there — `path · sha256 (first 12) · <bytes> bytes · <language>` — so a person can hold the file on the Site against the hash, and reads the versions that came before it on the records route. Reading the file itself on the card is #66.

**The turn.** The attempt is counted when the moment opens, as an observe node's is, so the Job adds the Job alone. Everything the moment is composed from is resolved first — a failure there blocks the node naming the thing rather than opening a moment over a half-resolved declaration; a value type the resolved semantics does not declare and a knowledge file that is not a plain file both block it — and the directory is made under its own write decision. **The root is the declared path and nothing else**: after the `mkdir`, the directory is resolved for real and must equal `<realpath of the workspace>/<directory>` exactly, and must not lie inside the workspace's own `flow/` or `hima-readers/` once those are resolved too. Any link anywhere in the declared segments — an `alias -> flow` an earlier Job left, a case alias that resolves elsewhere on a case-insensitive Site — is a `refusal` naming both paths and a blocked node, because every containment check afterwards is made against this root and a root that moved would authorise writes wherever it moved to. The moment is opened with **the node's own attempt**, so the `session` records and the node records number the same thing. It is closed either way. A completed moment that left no `code` record for the entry at that path is a failed attempt reading `the model wrote no <entry> in workshop "<id>"`: what says the file was written is a fact about bytes, never a sentence the model produced. Then **what is launched is what was recorded**: the entry is read back through the channel and must still hash to the `code` record's own hash, or the attempt fails saying so, and the `launched` job record carries `workshop: { id, entry: { path, sha256 } }` — the tie between the Job on the audit and the bytes in the ledger — beside the `attempt` it belongs to. And **what is recorded is what the command line runs**: the command line is the wrapper, the entry as its first operand, and then the rest — `argv[1]` is exactly `${ENTRY}` and nothing else references it, held when the pack is loaded — so the file that was verified is the word the wrapper is given to act on rather than a program written inline beside it. What the launch record's `workshop.entry` claims is exactly that and no more: the file the wrapper was given as its first operand, at the hash it had when the Job was launched. What a wrapper *does* with its first operand is the Site owner's business, settled when they allowed that wrapper in their permit. It settles from its exit code exactly as a tool's does, so a non-zero exit is `retrying` inside the Retry allowance and a Hard blocker with the log tail when it is spent.

**A retry is given the attempt before it.** From attempt 2 on, the instructions carry a block after the attempt line: `What the previous attempt did:`, the reason that attempt's own node record holds, and the last lines of its Job's log (the blocker's own bound — 40 lines, 16 KiB). It is read off the `retrying` record of attempt N−1, or off the `blocked` one when a person resumed after a Hard blocker, so attempt 4 after three failures sees attempt 3. A log that cannot be read says so in the line where it would have been and the moment opens anyway: the evidence is for the model, never a gate.

**A restart.** Nothing new. A host taken away **mid-moment** leaves an `opened` with no `closed`; the next boot writes the one `closed: interrupted` it is missing, and `reconcileRuns` then finds the Run `running` at a node with no Job open and does what it has always done — blocks the node saying so and sets the Run `waiting` for a person. Nothing re-asks a model on its own. A resume re-enters the node, and the moment it opens is the next attempt. A host taken away **mid-Job** is the ordinary case: the next host picks that Job up by its session, settles it from its exit code, and opens no second moment and writes no second `code` record.

**Where it stands**, in one word, read the one way by the card, the run view and `/hima status`: `writing` while the session is open, `written` once **the entry** is on record and the Job is a moment away, `no entry` for a moment that closed having written something else and nothing to run, `running`, `done`, `failed` for an attempt that failed inside its allowance, `blocked` for one that failed without it, and `interrupted` for a host that went away mid-moment. It is read of the workshop node the Run **last stood at**, not only of the current node: a workshop that succeeded leaves the Run standing at the node after it within milliseconds, and one whose allowance ran out leaves it at the pack's own Wait node, so either way what a person came to read is about a node the Run is no longer standing at. `/hima status` prints `workshop mine: done · 1 file`.

It is composed **from the ledger alone**, synchronously, and no pack folder is opened to compose it: the `opened` session record of a workshop moment carries `workshop: { id, entry, entryPath }`, which is where the card learns which node is a workshop node, which workshop it opens, which file of it runs and where that file is — the path a `code` record is held against to say the entry itself was written, which is the same question the turn asks before it launches anything. So a Campaign whose pack has since been uninstalled, renamed or edited into something that will not load still says on its card what its workshop wrote and how it went. The fold is narrowed to the Generation and the drill-down Loop the Run is in, exactly as every other count over a node is, so a Loop that revisits its workshop never folds the previous Generation's sessions, files and Jobs into this one's attempt 1.

**The live check.** `node scripts/live-check-workshop.ts` boots the shell with **no** replay overlay, installs the workshop pack variant on the local stand-in Site, and runs one generation with the owner's key: what it holds is that a real model, given these instructions and these three tools, writes a script the pack's own reader can then read. It writes `docs/validation/<date>-live-check-workshop.{md,json}` — the session pair, every `code` record with its hash held against the bytes on the Site, what the model wrote, the Job's exit, the reading, and a read of every file under the home afterwards. Run without a key it refuses in words and boots nothing. D48: it runs before any merge that touches a moment.


## Model moments

Nothing in this product asks a model anything, with one exception, and this is it. A **Model moment** is one isolated model session HimaFabric opens for one purpose at one node of one Generation and closes, carrying the instructions and tools of that purpose only, recorded on HimaLedger at open and at close. It is the one generic element the harness owes a HimaPack that wants a model's judgement; what a pack does with one is the pack's business, and nothing in `packages/` knows what any of them are for.

**What makes it isolated.** Three things, and the third is the one worth trusting:

1. **The preset.** The session is composed from `hima-moment`, the agent preset this bundle ships (`packages/harness/presets/hima-moment/`), installed into the home's own preset root by `prepareHimaHome`. Its composition mounts **no tool row at all** and one persona row whose only job is to shadow the deployment's identity away and turn off dsh's runtime-context snapshots. In the profile HimaHarness ships, dsh's own model-facing tools are not in the host composition — the web bundle disables every one of them and the `standard` preset mounts them on the agent plane — so a session composed from a preset that mounts none has none.
2. **The restriction.** Whatever *is* registered globally — Hima's own four tools are — is denied for that one session's scope through `ctx.tools.restrict`, which filters what a scope inherits and never what its own layer registers. So the moment's tools are exactly the ones handed in, whatever the host around it was composed with.
3. **The proof.** What the `opened` record and the route's answer carry is not the caller's list but **the list dsh itself reports for that session's scope**. A record of what we meant to give a model would not be evidence of what it could reach.

**No shell, and no host filesystem, whoever opens one.** `openMoment` takes the caller's tools on purpose — a workshop node hands it the pack's three (#62) — so the one thing a moment may never be is enforced where a moment is made: a request naming `write`, `edit` or `bash` is refused outright, before a session is composed and before anything is recorded. Those are exactly the three names the pack authoring guard governs, read from that one list rather than spelled twice, and the reason the two rules are one: the guard denies them inside an authoring session, so a Model moment — which is never denied by it — must never be handed one in the first place. It costs the product nothing, because the tools a pack gives a moment are Hima's own (`hima_*`) and reach a Site through HimaShell under the Permit.

The session's approval policy is set to `never`, deliberately: dsh's approval is one-shot and needs an answerer, the only answerer in this product is a browser chat surface, and a moment's session is in no browser tab — so a call that asked for approval would hang until the turn's signal cut it off. `never` is refused deterministically before any answerer is dispatched, which is the fail-closed answer for a session with nobody to ask. The sandbox mode is left as the host composed it; a moment reaches no filesystem because a moment has no tool that does. The model is the profile's own default (D9) and the record carries the name read off the session, never one this bundle spells.

**The records.** One `session` record when a moment opens and one when it closes, described in the record list above. The pair brackets the moment as the `loop` pair brackets a nested Loop. A moment lives in one process, so an `opened` with no `closed` is a host that went away mid-turn: the next boot's reconciliation (`reconcileRuns`) writes the one close it is missing, `interrupted`, over every Run in the ledger and before any Run is carried on — exactly one close per open, never two. The node can then take another moment, which is the next attempt at it; the Run reads open, closed-interrupted, open, closed-completed, each pair sharing its session id.

**The route.** `POST /hima/api/runs/<runId>/moment`, in the table above, behind the same fence as everything else in the namespace. It is how a test and the live check reach the mechanism with no tools at all. A **workshop** node's turn does not go through it: it calls `openMoment` directly, with the pack's three tools in hand ("Workshops" below). It refuses a Run that is **running**, with `409 hima/run-running`: a Run somebody is driving opens its own moments at the node it stands on, numbered by that node's attempt, and a moment opened through the route beside it would take the number the drive's next retry is about to take — leaving that node's session records no longer one pair per attempt. It refuses a Run that is **waiting at a workshop node**, with `409 hima/workshop-node`, for the same reason one restart later: a workshop interrupted mid-moment leaves the Run waiting at that very node, the attempt after it is the resume's to open, and a moment opened here would take its number. Which node is a workshop node is read off the ledger alone — the latest `opened` session record there carries the `workshop` block — so no pack is loaded to answer it. Every other status is allowed, including a Run waiting at the pack's own Wait node, where the route's moment collides with nothing.

**The model, in a test.** The contract suite has no DeepSeek key and must never need one, so a driven host mounts dsh's own keyless replay adapter (`@deepseek-ai/dsh-llm-replay`, pinned exactly) in place of the DeepSeek one and plays a committed transcript back. Everything else is real: a real agent, a real loop, a real system prompt, a real tool catalog. The overlay is two rows — `llm-deepseek` disabled, the replay adapter inserted with the scenario's fixture and a provider catalog naming the model the profile's default selects — written by the shell into `$DSH_HOME/cordis.patch.yml`, the home's own patch layer, and nowhere else: `profiles/hima/` stays byte for byte what `prepareHimaHome` put there, and the product profile's manifest never mentions the adapter. The shell writes it only when told to, with `--replay <fixture> [--replay-override <sidecar>] [--replay-child <log> …]`, and **only in driver mode** — a window a person opens cannot be told to fake its model. The scenarios and the shape of a fixture are `test/fixtures/moments/README.md`; a scenario with more than one moment in one host process needs a child session log per moment after the first, and `test/fixtures/workshop/README.md` says why and what one is.

**The model, for real.** Three checks in this repository reach DeepSeek, and they are the only three: `scripts/live-check-moment.ts`, which is this one; `scripts/live-check-pipeline.ts`, which holds a real model to all five stages of the pack authoring pipeline (described under [Pack authoring pipeline](#pack-authoring-pipeline)); and `scripts/live-check-workshop.ts`, which holds one to a workshop ("Workshops" below). All three are run by hand by whoever holds a key, and none of them is part of the contract suite. `node scripts/live-check-moment.ts` boots the shell **without** the overlay, starts a Campaign on the local stand-in Site, opens one moment with an instruction whose answer is checkable, and writes `docs/validation/<date>-live-check-moment.{md,json}`: the turn, the session, the model, both records, and a read of every file under the home afterwards. Run without a key it refuses in words, says where a key comes from, and exits non-zero without booting anything.

**The key.** A DeepSeek key reaches this product through DeepSeek Harness's own three doors and through no door of this harness's: the launching environment, dsh's credentials store at `$DSH_HOME/.credentials.yaml` (which the window's Models page writes), and an env file dsh loads. HimaHarness writes none of those files, reads a key by no path of its own, and puts no key in any record. A contract test runs the whole mechanism with a made-up key in the launching environment and then reads every byte under `$DSH_HOME`, the window's user-data directory and the workspace: the key is in none of them, no `.env` exists, and the one credential-shaped file a hima home ends up with is dsh's own store holding the window's browser-session grant and no model route at all.

## Pack authoring pipeline

A HimaPack is not written by hand. A pack author describes their business in plain language, points HimaGuide at the Golden Flow it is learned from, and is carried to a released pack by five stages — **grill, spec, fabric, test, release** — each of which is a skill: instruction text a person invokes by typing its name in the window's chat, which the model then follows with its own read and write tools inside the pack folder. dsh has no stage machine and needs none; a stage is instructions plus the tools the session already has.

**How a person invokes one.** Type `/hima-grill`, `/hima-spec`, `/hima-fabric`, `/hima-test` or `/hima-release` in the chat, in a session whose working directory is the pack folder being authored. dsh reads the `/name` gesture out of the message and injects that skill's instructions into the step. Nothing else invokes one: every candidate is **user-invocable and not model-invocable**, so none of the five appears in the model-facing skill catalog at all and the model cannot choose to run a stage on somebody's folder unasked. A stage is a person's decision.

**Where they come from.** One provider, `hima`, registered from the bundle (`packages/harness/src/skills.ts`) the way dsh's own packaged skill provider does it, with `source: 'bundled'` and the standard bundled rank. The bodies are `packages/harness/skills/<name>/SKILL.md`, read from disk on every load, and every candidate declares `packages/harness/skills/` as its resource base so a body's relative `knowledge/<file>.md` resolves for the model. They live inside the package rather than under a person's own skill roots on purpose: a bundle's skills installed into somebody's home are skills the bundle can no longer correct, and a person editing one would be editing the product.

**The knowledge.** Six reference files under `packages/harness/skills/knowledge/`, which the grill, spec and fabric stages read in full and cite by file name where they applied:

| File | What it says |
| --- | --- |
| `over-constrain-and-read-the-violation.md` | A met constraint states no margin; ask one step tighter than you believe possible and read the violation, because the achievable value is `asked + \|violation\|`. This is D45's lesson, which cost a whole acceptance run. |
| `end-honestly-in-more-than-one-way.md` | A Campaign ends goal met, converged, or at an ending the pack declares in its own words — never at a generation limit it cannot explain. |
| `assert-the-checker-options.md` | A verification session's options are declared and asserted before the run counts, because a run made under the wrong options passes for the wrong reason. |
| `one-checker-per-session.md` | One verification tool per session, so a count belongs to one tool and one option set. |
| `attribute-by-database-relation.md` | Adoption is read through the instance-to-master relation in the tool's own database, never by matching a name in a netlist. |
| `what-a-golden-flow-is.md` | The reference flow the pack is learned from and checked against: read where it lies, never copied, never the goal. |

These are the **pipeline's** knowledge, not a pack's. A HimaPack's own Knowledge files are a different thing (`CONTEXT.md`): domain knowledge for one business, written into the pack folder and named by its contract.

A seventh file sits beside them and belongs to the fabric stage alone: `knowledge/pack-anatomy.md`, the **skeleton the fabric stage compiles to** — the smallest valid `contract.yml`, `graph.yml`, `semantics.yml`, `rules/<id>.yml`, `choosers/<id>.yml`, `readers/<id>.yml` with its script, knowledge file and the five records, each with a note per field. It is not cited and it is not method: the grill and spec stages write no such file and never read it. It is what makes the fabric stage's authority complete — with it, the pack installed beside the folder being authored, the bundle's own `../rules/`, `../choosers/` and `../semantics.yml`, and `hima_pack_check`'s answer, that stage never has to read this harness's source to learn how a file of a pack is spelled.

**What grill writes.** The grill stage interviews the author in rounds of numbered questions, each carrying the answer it recommends, asking only the frontier — the questions whose prerequisites are settled. The business first (what is explored, what is measured, what ends it, what a person must never have to guess), then the Golden Flow: the author says where it lies, the stage reads it there with its read tools and copies no file of it anywhere, and every place the author's words and the flow disagree becomes its own question so that neither side wins silently. It ends by writing **`INTENT.md`** — the pack intent record — into the pack folder, with exactly five sections: `Business`, `Golden Flow` (the path and what was read there, as pointers), `Answers`, `Ambiguities resolved`, `Knowledge applied`. Run again on a folder that has one, it reads it first and asks only what is still open.

**What spec writes.** The spec stage reads `INTENT.md` — its body tells it to refuse in words, naming the section, when the record is absent or half-written, rather than filling the gap or overwriting a record a person edited — reads the Golden Flow at the pointers the record gives it, reads the six knowledge files, and writes **`SPEC.md`**, the pack spec, with exactly nine sections: `Goal template`, `Constraints`, `Run contract`, `Semantics`, `Judge rules`, `Choosers`, `Endings`, `Workshops`, `Knowledge`. Each is in the pack's own words and says which knowledge file shaped it. It writes nothing else and edits no other file.

That refusal is instruction, and instruction is not enforcement. The harness's half of it is the ladder below: it is cumulative, so a folder whose `INTENT.md` does not validate stands at `none` **even with a perfectly good `SPEC.md` beside it**. A stage that ignored its body and specified anyway still cannot make the folder read as `specified`, and the fabric stage has a machine-checkable reason to refuse it.

**What keeps a stage inside the pack folder.** A rule of this product, enforced where a rule belongs. A session whose working directory lies inside the bundle's packs directory is an **authoring session** of the one pack folder `<packsDir>/<id>` it stands in, and in such a session: every file-writing tool's target, resolved against the session's own working directory, must lie inside that pack folder; and `bash` is refused outright, because an authoring session has no shell — the Golden Flow is read with `read`, `glob` and `grep`, and one `sh -c` is a hole through every path rule above it. The rule asks about the tool before it asks about the session: a call of anything but those three is answered without a path being resolved at all, so every `read`, `glob`, `grep`, `skill` and `hima_*` call in the product is exactly what it was, wherever the session stands. Only for one of the three is the session then placed — and a session standing anywhere but inside the packs directory is left alone in turn, so an ordinary chat session and a Campaign's own work write and open shells as they always did.

It lives on dsh's tools seam as `ctx.tools.guard` (`packages/harness/src/authoring.ts`, registered once and globally as an effect of the bundle): a monotonic synchronous check run after every `tools/pre-execute` listener and before the tool body, whose returned string denies the call — and guards have no allow result, so nothing registered later can turn a denial back into permission. The file-writing tools are read off `ctx.tools.schemas()` on a real boot (`write` and `edit`; `read`, `glob` and `grep` are deliberately not among them), and the contract suite holds that classification against the booted host, so a dsh release registering a third fails the suite rather than opening a door quietly. A subagent inherits its parent session's `cwd`, so a subagent of an authoring session is an authoring session too.

**Three paths, three resolutions, on purpose.** Every comparison is on resolved paths, never on spellings — the temporary directory a home is made under is itself a symlink on macOS — but the three paths are not asked the same question.

- The **packs directory** is resolved as itself. Its not being there at all is the one benign failure: no working directory can lie beneath a directory that does not exist, so every session on the host is left alone. Any other way of failing to resolve it — a link to nothing, a directory this process may not traverse — stops `write`, `edit` and `bash` in *every* session until it resolves, because until it does the host cannot tell an authoring session from an ordinary one.
- The **session's working directory** is resolved as itself and has no benign absence: a session whose own directory cannot be resolved to a directory is one this harness cannot place, and answering "somewhere else" for it is the fail-open the rule exists to refuse. It is refused, naming the directory.
- Only the **write target** is reconstructed, because the file a stage writes usually does not exist yet. It is taken as the tool received it — a relative one prefixed with the session's own directory — and a `.` or `..` **anywhere** in it is refused by name before anything is resolved. That is not a formality: a `..` beside a symlink names two different files depending on who resolves it, lexically before the filesystem is consulted or by the kernel after each link is followed, and Node's own `fs.realpathSync` and `fs.realpathSync.native` give the two different answers. Nothing an authoring stage writes needs such a segment, and refusing it is what makes "inside the pack folder" one fact rather than two. What is left is plain names: the deepest ancestor that exists is realpath'd, the segments below it are kept in order, an ancestor that will not resolve for any reason but "it is not there" refuses, and the first segment below the resolved ancestor is asked without following links whether anything is there at all — a symlink pointing at something that does not exist is still a path a write follows to wherever it names.

**Why this is not left to dsh's file sandbox.** The sandbox is real and it still applies: the deployment composes `sandbox-policy` in `workspace-write`, `sandboxPolicy.resolve` takes the workspace root from the calling session's own `cwd`, and `dsh-fs-sandbox` fences every `write` and `edit` against it with a structured `FS_SANDBOX_DENIED`. But it is not *this* rule — `workspace-write` permits the session's workspace root **plus the platform temp areas**, `/tmp` and `os.tmpdir()`, because that is what the mode promises tools that write temporary files. A Golden Flow, a scratch checkout or a home under one of those is inside the sandbox and outside the pack folder. That gap is not dsh's fault and not dsh's to close; it is a rule of this product about its own authoring sessions, and `test/contract/skills.test.ts` proves it the only way that means anything: one home, one flow, one committed transcript replayed twice — a `write` aimed at the Golden Flow's own `Makefile` and a `bash` — refused in the guard's words with the flow byte for byte unchanged when the session stands in the pack folder, and both going through, rewriting the flow, when the same session stands in the ordinary workspace. Two further scenarios in the same file hold the resolution itself: one authoring session whose seven calls cover a new file at the top of the folder (allowed — creating one is the stage's job), a dangling link inside it, three spellings that climb through `..`, and an `edit` aimed outside; and four sessions for the failure posture — an absent packs directory (every session untouched), a packs directory that is a link to nothing (an ordinary session refused), a working directory removed after the session opened, and a session standing below an ordinary file where a pack folder would be.

That the two stages *as written* touch nothing outside the pack folder at all is a separate claim, and the suite answers it with a digest of every file under the flow, the workspace and the other installed packs, taken before and after both stages.

**What fabric writes.** The fabric stage reads `SPEC.md`, refuses in words when it is absent or half-written, reads `INTENT.md`'s Golden Flow pointers and the flow there, and reads the six knowledge files. Then, **before it writes anything**, it holds the spec against itself and refuses a contradiction — a value a judge rule or a chooser reads that `Semantics` does not declare, an ending nothing can reach, a tool with no wrapper the contract declares, a workshop whose output is no declared value, a knowledge file named nowhere. The refusal's first line is `SPEC.md does not compile:` and each finding is `<section>, line <n>: "<the line>" — <why>`; nothing at all is written.

Otherwise it writes the pack, in the pack folder and nowhere else: `contract.yml`, `graph.yml`, `semantics.yml` where the pack's own readers emit value types (a pack whose outputs are all read by readers this harness ships writes none), `rules/<id>.yml` and `choosers/<id>.yml` where the rule or the move is the pack's own, `readers/<id>.yml` with its script under `tools/`, `knowledge/<file>.md` per entry of the spec's `Knowledge` section, and one `tools/<name>` script per tool **whose command line the Golden Flow showed it**. A tool or a reader the flow never showed is not invented: it is a **gap**, one line each, left to the author. Every script the stage did write is put to the author one at a time (`Review tools/synth.sh: … — approve, or say what to change`) and their verdict is recorded in their own words. It then writes **`FABRIC.md`** with exactly three sections — `Files written`, `Gaps`, `Reviews` — and calls `hima_pack_check` on its own work, fixing what that names in the pack's own files until the folder is `compiled` and fits, or saying what it cannot fix. A `Workshops` entry is still carried into `PACK.md` as prose and not compiled into the contract's `workshops:` block: that block landed with #62, and teaching this stage to write one is its own change, because a stage body is a body a live check has to be run against (D48).

**What test writes.** The test stage checks the folder first (below `compiled`: it refuses in words), takes the Site from the author's message or asks for one, reads the spec's `Goal template` and `Endings` and `INTENT.md`'s Golden Flow pointer, and calls `hima_run` with **`test: true`** — a real Campaign on a real Site, marked as the test of this pack. When the Run stops it calls `hima_status` for that Run's own records and writes **`TEST.md`** with exactly seven sections: `Site`, `Run` (holding one line `run: <run id>`, and the Goal and Strategy it started at), `Ending`, `Generations` (one line each), `Code`, `Refusals`, `Disagreements`. One file, nothing else edited. Every line of it comes from what that Run recorded, with two exceptions the body names as such: the Golden Flow the `Site` section says it was checked against, which is the intent record's pointer and the flow at it, and whether the ending is one `SPEC.md`'s `Endings` declares.

**The numbers that Run asks for are the author's.** Every value on its `goal`, and every override on its `strategy`, comes from the author's own message or from the spec's `Goal template` recommending one, and from nowhere else — not the flow's numbers, not the contract's defaults, not a pack beside it, not anything in this harness. Where neither states a value for a parameter of the Goal, the stage asks for it (`The Goal template names <parameter> and recommends no value; what should this test Run ask for?`) and starts no Run. That rule is in the body's rules that do not bend, and `test/contract/skills.test.ts` holds the body to both sentences, because it is the one thing a stage cannot be trusted to improvise: a Campaign spends a Site's licensed time, and a target nobody set makes a test record for a pack nobody asked to have tested that way. The live check states its Goal in the message it sends and holds the Run's own `goal` to it.

**Three of those lines the harness reads back and holds against that Run**, because the rest are prose and a record whose prose was rewritten after the test would otherwise seal unchanged: `Ending` holds **exactly one** line `status: <the Run's status exactly>` — two such lines state two endings of one Campaign and are refused naming the section; `Code` holds, for every `code` record the Run wrote, a line carrying that record's sha256, or is exactly `none`; `Refusals` holds, for every refusal record, a line carrying that record's id, or is exactly `none`. What differs is named by its section (`test record's Ending says status: ended-goal-met and run <id> ended ended-converged`), and the folder is answered at `compiled` until the record says what the Run did. The `Run` section holds **one** `run:` line and `Ending` **one** `status:` line: a record naming two runs names none, and a record stating two endings is refused naming the section.

**And what a person may still rewrite after the test and have sealed**, plainly: everything else in the five records. The `Site` and `Disagreements` sections and every `Generations` line of `TEST.md`, any prose under its `status:` line, and the whole of `INTENT.md`, `SPEC.md` and `FABRIC.md` — the digest excludes all five records, so editing one moves no hash a Run is held to, and the seal carries the hash of what is there when the release runs. That is deliberate: a record is a person's document, the harness checks the claims a ledger can be asked about, and a harness that graded the rest would be inventing a verdict rather than checking one.

**What release writes.** The release stage checks the folder (below `tested`: it refuses in words, naming what is missing) and calls `hima_pack_release`. It writes nothing by hand at all, which is the whole of what a release is worth: a version file a model typed would carry hashes nothing computed. The verb writes **`VERSION.yml`** — `pack`, `version` (the contract's), `released` (an ISO instant), `test: { record, run }` (a run id), and `files:` with one sha256 per **every** file of the folder except the seal itself, the pipeline's own records included — and the stage reports the version, the file count and the run it rests on. Releasing again over the same version rewrites the seal, which is what follows a corrected script and a re-run test stage.

The release **reads the folder once** (`release.ts` over `snapshotPackFolder`): the rung it stands on, the pack it seals, the digest the ledger's test Run is compared against, the bytes of the `TEST.md` that Run is read out of and the file list the seal carries all come from that one reading, and the check after the write holds what is on the disk against it — first release and re-release alike. So a release can never authorise one set of bytes and seal another, and no seal can carry a file list, a version and a test Run that were never all true at once. The folder is held as plain files and the whole seal is composed and validated against its own schema **before a byte is written**, so a folder is never left carrying a seal that nothing will accept; the file is then written under a hidden temporary name with the exclusive flag and renamed over `VERSION.yml`, so nothing is ever written *through* whatever stands at that path and a reader sees one seal or the other and never half of either.

**The mark, the digest and the seal.** Three facts the harness keeps so that none of the above is a claim only a record makes.

- Every Run carries **`purpose`**: `test` when the tool, the route or `--test` said so, and otherwise whatever the pack folder says — a folder in the pipeline and unreleased is a test run, a released or hand-written pack an ordinary Campaign. The card on both mounts, the run list and `/hima status` mark a test run, and the start form marks the pack: a folder in the pipeline is offered as `<id> — test pack (<stage>)`, a released or hand-written one plain. A folder whose **own reading refuses it** — a link out of it, a socket, a name no pack file can have — is offered as `<id> — unreadable: <the reading's sentence, naming the path>` and rendered `disabled`, so it is an option nobody can choose rather than a pack that vanished off the form; the form's default selection is a pack a person could actually start, and the route refuses a start of it in the same words `/hima pack check` and `/hima run` use. One broken folder is one bad option and never a page with no start form on it — and a home where *every* installed folder is unreadable is the same page with every option marked and disabled, never a list of plain options for folders nothing can read. Nothing is selected there **unless** the page's own `?pack=` named one of those folders, which is then rendered selected *and* disabled: a person who asked for a folder by name is owed the option they asked for with the reason it cannot be started on it, and a selection nothing can be started from is exactly what the form's own default selection avoids.
- Every Run carries **`packDigest`**: sha256 over the sorted `(path, sha256)` pairs of every file of the pack folder **except** the pipeline's five records (`packDigestExcludes`), so that "which files did this Campaign run" survives a rule being corrected the next day. `startRun` **reads the folder once** and derives all four of the things it says about it from that one reading — the contract and graph the Campaign is driven by, the rung the folder stands on, the seal the check verifies, and that digest — so the pack that runs, the folder the check accepted and the folder the row records are one folder.
- **One reading holds the folder** (`packages/harness/src/pack-folder.ts`), and every decision about that folder is made from it: the loader parses `contract.yml` and `graph.yml` out of its bytes, the ladder validates the records out of its bytes, the check asks it which knowledge files are there, the digest and the seal are derived from it, and the release seals it. Every entry is `lstat`ed **first** — hidden or not — and a symlink, a socket or a dangling link is refused naming the path, so a `VERSION.yml` that is a link is refused there rather than read through and a `.linked` is refused too. A **hidden** entry — a leading dot — is then left out of the pack's files, and a hidden **directory is walked all the same**: nothing in a pack can declare one, so a `.DS_Store` or a `.git/` must not make a folder unhashable, but a namespace nobody may declare is not a namespace nobody has to look at, and a link under `.state/` is refused naming it. Directory names are read as bytes and a name that is not UTF-8 is refused naming the directory and the bytes. Every discovered path is held to the same grammar a seal's own keys are parsed against, so a quote, a newline or a control character never reaches a digest line or a YAML key. A hidden regular file is `lstat`ed like any other and then skipped — never opened, never read. **What is read is the inode that was inspected**: each file is opened with `O_RDONLY | O_NOFOLLOW`, `fstat`ed as a plain file, and its `dev`/`ino` compared with the `lstat`'s before a byte is read from that descriptor; each directory is `lstat`ed again after its names are read and compared the same way. A name swapped for a link, or for another ordinary file, between the inspection and the read is refused naming it rather than entering a digest, a seal or a Run. **The limit, plainly:** Node offers no `openat`, so a path is resolved twice however this is written, and a process racing the reading with the user's own rights is outside what the reading promises — as it is for every Site operation. Two windows, and they differ: a *file* swapped under the walk is refused, because the open refuses a link and the `fstat` refuses a different inode; a *directory* swapped for a link after its names were read but before its children were walked is **outside the promise** — each child's own `lstat` and `open` then resolve through the replacement and agree with each other, so children that are not this folder's can enter. What is promised is that no entry that was not a plain file when it was inspected enters a digest, a seal or a Run, and that every byte hashed was read from a descriptor opened without following a link. And `<packsDir>/<id>` is itself `lstat`ed by every reader of a pack folder: a link named with a valid pack id is refused naming the path rather than loaded, checked and run as an installed pack, and an ordinary file standing under a pack id is named by the start form's own inventory rather than dropped from it. Every one of these refusals is a `PackFolderError`, which every face answers in words naming the path — a folder that is not a folder of plain files is a fact a person can act on, not a crash.
- **`/hima pack check` holds the test record against the ledger** where it has one: the named Run exists, it ran this pack, its purpose is `test`, it ended, and its `packDigest` is the folder's digest *now*. It also holds the three bound lines above against that Run's own records. It prints `test record: run <id>, ended <status>, files as tested`, or names what differs — and a folder whose files moved since is answered at the rung it really stands on, `compiled`, which is what re-entering a stage after a change means. A released folder is held against its **seal** instead, not against this machine's ledger, because the ledger that holds a pack's test Run is its author's and a pack is installed wherever somebody installs it — and the seal's own `test.run` must be the run the sealed `TEST.md` names, which is the one edit no listed hash would move.

**The three verbs a stage calls.** Registered globally beside the four (`packages/harness/src/tools.ts`), so an authoring session reaches them — the guard governs `write`, `edit` and `bash` and nothing else. `hima_pack_check { pack, site }` answers `{ fit, stage, next?, needs?, issue?, text }`, the ladder as data beside the words `/hima pack check` prints. `hima_status { run }` answers the run view the route serves, so a stage can write a record from a Run's own records without a browser; a run this ledger does not hold is `unknown` in words, and a Run whose pack will not load is `unreadable` naming the pack — never a view with the pack's words silently missing. `hima_pack_release { pack }` is the release. `hima_run` takes an optional `test`, as `/hima run` takes `--test` and the start route takes `"test": true`.

**A folder's stage.** `packStage` reads a pack folder and answers which rung of a ladder it stands on: `intent` (`INTENT.md` validates), `specified` (+ `SPEC.md`), `compiled` (+ the folder loads as a pack **and** `FABRIC.md` validates), `tested` (+ `TEST.md` validates and its `Run` section holds one `run: <run id>` line), `released` (+ `VERSION.yml` parses, agrees with the contract's id and version, and covers every regular file of the folder with a matching hash and nothing unlisted). It is cumulative — a rung is reached only when its own files and every earlier rung's files are there and validate — so a folder holding a spec and no intent record is at `none`, because the record is what the spec was written from, and a `VERSION.yml` beside no test record leaves the folder at `compiled`. A record validates when its ordered `##` heading sequence **equals** the sections its stage was told to write: nothing missing, nothing extra, nothing twice, nothing out of order, nothing empty — the same "exactly these sections, in this order, and no other heading" the two skill bodies say, so a record the next stage cannot read section by section cannot carry the folder up a rung. `compiled` means `loadPack` returns, not that two YAML files each pass their own schema: the loader also holds the folder's name against the id both files declare, every reference one makes to the other, the tool files the contract names and the node ids across every graph, and a rung whose whole meaning is "this can be run" cannot be reached by a folder the thing that runs packs rejects. Only `ENOENT` is absence: a file that is there and will not open is an error naming the path, never "not authored yet". `/hima pack check` prints one line of it under the verdict:

```
stage: specified (INTENT.md, SPEC.md validate); next: compiled — contract.yml, graph.yml and FABRIC.md, written by /hima-fabric
```

and a folder under the packs directory that has no contract yet is answered by the ladder — `unfit — not compiled`, plus that line — rather than as a pack nobody installed. The `released` verification is also carried as **errors** whenever a `VERSION.yml` is present, so a released pack whose files changed under it is `unfit` naming the first offending file (`VERSION.yml is there and tools/synth.sh no longer hashes to it`, `… and rules/new.yml is not listed in it`) and `/hima run` refuses it before anything is sent to a Site: a Campaign names a pack that cannot have changed under it. A folder whose contract is there and does not load is answered the same way, with the loader's own sentence as the verdict and the ladder line beside it, so a person is told both what is broken and which rung it broke on. A name nobody installed is still unknown; an id that is not a pack id, and a path holding something that is not a directory, are refused naming what was found. Nothing gates `/hima run` on a stage, and `fit` is untouched by one.

**The stages under test.** The contract suite drives all five end to end against dsh's keyless replay adapter, through `bootInProcess` — the same host the window's chat runs. That seam and not the desktop driver, because the driver marks Hima's own controls (ADR-0004) and has none for the web app's composer: a person's `/hima-grill` message cannot be typed through it. `test/contract/skills.test.ts` holds grill and spec; `test/contract/pipeline-stages.test.ts` holds the three this ticket built — the fabric stage compiling the committed spec into a pack that loads and fits and refusing one that contradicts itself, the test stage running a real Campaign on the stand-in and writing the record from it (and a script edited afterwards putting the folder back at `compiled`), the release stage sealing the folder with two calls and no write at all, a file changed or added under that seal refusing a Campaign, and all five stages in **one recorded session** on one folder. The transcripts are `test/fixtures/pipeline/`, and that nothing outside the pack folder was written — and no file of the Golden Flow copied into it — is read off a digest of every file under the flow, the workspace and the other installed packs, taken before and after. The one thing that is really a person clicking, the start form's marks and the Run a click of it starts, is driven through the shell in driver mode on the very home the stages authored in.

**The stages for real.** `node scripts/live-check-pipeline.ts` is one of the three things here that reach DeepSeek, and D48 asks for it before any merge that touches a skill: a skill body is instructions a model follows with real file tools on a person's machine, and a body nobody has run is a guess. It boots the host with **no** replay overlay and runs one turn per stage on one folder: a business in plain language with the stand-in flow's path (checking that grill *asked* rather than acted and wrote nothing yet), the committed intent record written into the folder, one `/hima-spec` turn (checking that the sole change under the folder is one new `SPEC.md` whose ordered heading list is exactly the nine), one `/hima-fabric` turn with the author's reviews answered `approved — keep it` by the script (checking that what it wrote loads, that `/hima pack check` says `compiled` and fit, and that `FABRIC.md` validates), one `/hima-test` turn on the local Site, its message stating the Goal the way an author states one (checking that the Run its record names is in the ledger, marked `test`, ended, ran the files the folder now holds, and asked for exactly the Goal that message stated), and one `/hima-release` turn (checking that the session wrote nothing by hand and that the seal parses and leaves the folder `released`). It writes `docs/validation/<date>-live-check-pipeline.{md,json}`. Run without a key it refuses in words, says where a key comes from, and exits non-zero without booting anything.

## Driving the window

The product is tested as the desktop app a person uses, never through a browser (D42, [ADR-0004](docs/adr/0004-desktop-driver-as-the-test-seam.md)). Started with `--driver`, the shell does everything it does for a person — prepares the home, launches the host, exchanges the token in its own window's session, loads the page — and then reads **JSON lines on stdin** and answers each with **exactly one JSON line on stdout**; its own `hima-desktop:` lines go to stderr, and nothing else is written to stdout. A request is `{"id": <string|number>, "op": "<name>", ...}`; the answer is `{"id": …, "ok": true, ...}` or `{"id": …, "ok": false, "error": "<why>"}`. A line that is not JSON, or has no `op` or no `id`, is answered `ok: false` with `id: null`. Requests are answered one at a time, in order. The ops:

| Op | Takes | Answers |
| --- | --- | --- |
| `host` | — | `{ url, origin, session: { cookieName, cookieValue } }`: the host's tokened URL, its origin, and the session cookie the shell established, so a test's route calls carry the window's own session |
| `open` | `path` | loads `<origin><path>` and answers once the load finished with `{ url, status, title }` — the HTTP status the navigation got and the window's title. Anything that does not resolve to a URL under the host's origin — an absolute URL elsewhere, `file:`, another port — is refused in the fence's own words; a path the host answers 404 for is opened and its 404 reported, because the fence is about origins |
| `read` | `region` | `{ text, state }`: the rendered text (trimmed) of the element marked `data-hima-region="<region>"` and every `data-hima-state-<key>` attribute it carries as `state: { key: value }`; an unknown region is `ok: false` naming it |
| `wait` | `region`, `text`, `timeoutMs?` | resolves as `read` does once the region's text contains `text`, polled from the main process every 200 ms, 30 s by default; on timeout `ok: false` naming the page the window was on and saying what the region last showed, or that it was absent, or that the page could not be asked at all — three different faults that used to read as one. The workbench page refreshes itself once a second, so a wait is satisfied by the page catching up with a Run that is still moving, and not only by what the document said when it was opened |

A `<select>` is set by choosing the option whose `value` is `value`, or failing that the one whose visible text is, with the same two events; an option it does not offer is refused naming the ones it does. An element that holds no value (a button) is refused: a click is what it takes. An unknown control is `ok:false`. |
| `zoom` | `factor` | the page's zoom set through the shell's own handle (the one the View menu's zoom items use), held to 0.25–5; answers the factor, the page's own width and height in its pixels, and the width the document laid itself out at (`scrollWidth`), all read after the page has laid itself out again. What `scripts/workbench-screenshot.ts` uses for a card taller than the display's work area, which macOS clamps every window to, and what a test asks whether anything on the card is wider than the window with. |
| `screenshot` | `path` | `webContents.capturePage()` written as PNG to `path`; answers `{ path, width, height, bytes }`. A capture that painted nothing is refused; the window is shown in driver mode (without taking focus) so it paints |
| `quit` | — | answers `ok: true`, then stops the host the way closing the window does, and exits 0. A closed stdin quits the same way |

### The page's design

What the workbench page **looks** like is one file, `packages/harness/src/workbench-style.ts`, inlined into every page as a single `<style>` (the window's fence permits no external asset, and the page must render offline). `packages/harness/src/workbench.ts` beside it is the page's **structure**: it states no colour at all and no type size, and the only sizes it does state are the ones that are a table's shape rather than its look — the `min-width` a table may not be squeezed below, computed from its own columns, and the `<col>` width of each column, which are the proportions of the table itself — together with the percentages that place a bar's fill, its tick and the convergence plot's two values where the numbers they draw actually fall.

The stylesheet opens with one token sheet, delimited by `/* HIMA WORKBENCH TOKENS BEGIN */` and `/* HIMA WORKBENCH TOKENS END */`: the two font stacks (dsh's own, copied in as values), the type scale (`--hima-fs-body` 16 px, a 14 px floor — five steps, and the test reads every size the sheet states, so a step shrunk by a factor inside a rule is caught too — one 28 px display size spent on the Campaign's verdict), the 4 px spacing rhythm, three radii, one shadow, and a light palette with a dark one re-cut under `@media (prefers-color-scheme: dark)` — the media query and not a class, because Electron routes a forced theme through `nativeTheme.themeSource`. **No rule outside those two delimiters states a colour by value**, so a palette re-cut is token edits and nothing else; `test/contract/window.test.ts` reads the stylesheet the host served and fails when that stops being true. The `--dsw-alias-*` names `card-labels.ts` paints the shared words through are defined in the same block out of these tokens, so one set of words is coloured by one palette on both mounts of the card.

The page is three bands at every width — the verdict, the generation ledger with the path under it, and the evidence — in a content column of at most 1040 px. **A section a later ticket adds is a `<section class="band">` with an `<h2 class="eyebrow">` inside it**, and it inherits the whole look; a band that holds more than one part gives each part its own `<section>` with an `<h3 class="eyebrow">`, ruled off automatically. ## Acceptance runs

`scripts/acceptance-step2.ts` runs one whole generation of the opene902 timing probe on a Site (one, and it says so: `--generations 1`, since the pack itself loops) and writes down what happened, as `docs/validation/<date>-step2-acceptance.{md,json}`. It probes the Site read-only first — `/hima observe` of the Site's own last qor report, which is where the target period comes from (that period minus 0.2 ns, or whatever `--target` says), and a tmux question about what is already running there, which reads a pane as busy when its session is one of this harness's own, or when its command line names the Site's own flow root, one of `dc_shell`/`icc2`/`innovus`/`pt_shell`/`/usr/local/bin/eda`, or `make` with a `synth` target, because the site owner's rule is one large DC or Innovus job at a time and the flow here launches Design Compiler through `make` and a container, so `dc_shell` is never the name on the pane — and launches nothing at all if either answer does not clear the Site, if either of the Site's two roots does not resolve, or if the target period is outside the sanity band (0.5 ns to twice the Site's last result). Then it drives the generation through the faces and nothing else: `/hima run <pack> --site <site> --goal target_period_ns=<target> --set periodNs=<target> --time-box 20`, then `/hima status <run>`, then the run view over the real web profile (`GET /hima/api/runs/<id>` and `/records`, behind the session cookie the tokened URL hands out), read once more over a second booted host to show the Run comes back unchanged. Everything the record claims is a check with its predicate written out beside what was observed — that the Job ran inside `<workspaceRoot>/<campaign>` through `make` in tmux under `EDA_CONTAINER_NAME=hima-<campaign>`, that every write the channel was asked for landed inside that workspace (what the Job itself writes once `make` is running is the flow's own doing and is not covered), that the report the target was derived from is unchanged in content and length, that the clock period the generation's report states is the one that was asked for, that each verdict follows from the measured value it cites, and that the decision is the clause `timing-push` declares for those two verdicts — and a check that could not be evaluated is a failure, never a pass, so one failed check writes the record and exits non-zero. `--site local` runs the same script against the stand-in flow the contract suite generates, which is how it is developed; `--out <dir>` puts that dry run's record somewhere other than `docs/validation/`, because only a record from the reference Site belongs in the repository. A record is never overwritten: when the date's name is taken the run writes `<date>-step2-acceptance-<HHMMSS>` beside it and prints which files it wrote. The Campaign workspace and the isolated harness home are left in place with their paths in the record: nothing in this harness removes a path on a Site, and removing them is the Site owner's call.

```bash
node scripts/acceptance-step2.ts                            # the reference site; the record into docs/validation/
node scripts/acceptance-step2.ts --site local --out /tmp    # the stand-in flow, for developing the script
```

`scripts/acceptance-step3.ts` runs a whole **Campaign** — several generations of the same pack, each one synthesizing at the period the last one's chooser picked — and writes `docs/validation/<date>-step3-acceptance.{md,json}` beside `<date>-step3-acceptance-card.png`, a photograph of the ended card. It starts that Campaign the way an engineer does, which is the whole point of it (D42, ADR-0004): the desktop shell in driver mode, on an isolated home, with the workbench page's own start form filled control by control — pack, site, target, period, time box, retries, generations — and `start` clicked. Nothing here posts to a route to start anything. What it then watches is the card the window renders, waiting on the `run-status` region for one of the four endings and saying where the Campaign stands each half minute until it arrives; what it reads afterwards is the run view, the records and the experience over the routes with the session the shell established, then the same three over a second shell booted on the same home.

The read-only probe and the gate are step 2's, for step 2's reasons — the Site's own last qor report over `POST /hima/api/observe`, which is where the target comes from; `realpath` of both of the Site's roots; the tmux question about what is already running there; the sanity band on the period — and nothing is launched if any answer does not clear the Site. The Budget is the Campaign's: `--time-box` (30 minutes by default) is the whole Loop's clock, and `--generations` defaults to the pack's own `converge.generationLimit`. Every claim in the record is a check with its predicate beside what was observed — that the Run's goal, first Strategy and Budget are what was typed into the form; that at least three generations ran; that it ended `ended-goal-met` or `ended-converged`, with the convergence rule re-derived from the values compared; then, **for every generation**, that its report states the period it was asked for, that each verdict follows from what it measured, that its decision is the clause `timing-push` and the pack's `converge` declare for those verdicts and those numbers, and that the next generation asked for exactly the period it chose; that every generation ran in the one Campaign workspace under that Campaign's own container; that nothing the ledger records as written landed outside it; that the report is on the Site beside the results, hashing to what the `experience` record states, shown by the window and reproducing the card row for row; that the whole Campaign reads back unchanged after the window is quit and another shell boots on the same home; and that every meter stayed inside its bound. A check that could not be evaluated is a failure, so one failed check writes the record and exits non-zero.

Every remote command is recorded, and it takes two audits to do it: HimaChannel's audit is per process, and a Campaign here is driven by the dsh host **inside the desktop shell**, not by this script. So the script drains both — its own in process, and the host's over `POST /hima/api/audit/drain` — every two seconds from the click onwards and at every phase boundary, so that neither 500-entry window can evict a command before it is read; a window that filled fails the check rather than being written down as a complete list. The record lists the host's commands with the phase each belonged to, this script's read-only probes apart from them, and the ledger's own account of the same launches beside both. The first shell's audit is drained before it is told to quit, because a host's audit dies with the host.

`--pack <id>` is the pack it drives, the reference pack by default. `--site local` runs the same script against the stand-in flow, which is how it is developed, and seeds two packs into the isolated home: the reference pack, and the converging variant beside it (#57) — the same method with the over-constraining push in its own `choosers/` folder. **The two forms show two different things, and both are the dry run doing its job.**

```bash
node scripts/acceptance-step3.ts --site local --out /tmp                                 # the reference pack: 45 of 46, red by design
node scripts/acceptance-step3.ts --site local --pack over-constraining-probe --out /tmp  # the variant: green
```

On the reference pack the stand-in's "last result" is seeded at the 2.20 ns it closes at, so the first generation is asked for 2.00 and misses by 0.20. What happens next is the D45 trace and not a convergence, because the stand-in reports slack the way the real tool does (above): 2.25 is met and reports no margin at all, so the push loosens by its guard band every generation — 2.30, 2.35, 2.40, 2.45 — until the sixth is spent. 45 of the record's 46 checks pass and `ended-goal-met-or-converged` fails, which is the check the reference Site failed too, so that form exits non-zero. It is red **by design**: the reference pack's chooser is a stand-in for a method rather than the method, and what it should be is the step-4 pack authors' to say (D45, `packs/opene902-timing-probe/PACK.md`). On the variant the same script drives the same flow and every check passes: the Campaign walks in one step at a time and converges one step below what the tool violated at, with the violation on record. What the two forms say together is that the infrastructure is sound and the reference pack's chooser is the one thing that is not — which is exactly what D45 ruled and what this repository still declines to paper over.

`--out <dir>` puts a dry run's record somewhere other than `docs/validation/`, because only a record from the reference Site belongs in the repository. A record is never overwritten: when the date's name is taken, all three files are written as `<date>-step3-acceptance-<HHMMSS>` beside it. The Campaign workspace, its container, the report inside it and the isolated harness home are left in place with their paths in the record.

### The stand-in's stages

`synth` was the whole of the stand-in flow while the only pack was a timing probe. A pack for a cell-mining and Fmax-push business runs nine stages — foundry-only synthesis, mining per route, transistor netlists, abstract layouts, Liberty characterisation, the library compile with its hard gate, synthesis with the generated library, both post-route arms, the verification session — so the flow answers all nine (#60), and the seeding says which. Each is a make target taking its inputs as command-line variables and writing inside the workspace, under `results/<design>/<stage>[-<arm or route>]/` and `logs/<design>/`. The stand-in is the one file the pack-first boundary exempts: it imitates the tools' report shapes on purpose, because the bundled readers read them.

| target | variables beyond `DESIGN` | report | what it computes |
|---|---|---|---|
| `synth` | `CLOCK_PERIOD_NS` `FORCE_SYNTH` `EDA_CONTAINER_NAME` `RESULT_TAG` | `syn/report[-<tag>]/qor.rpt` (`dc-qor-report`) | setup slack `min(0, period − 2.20)`, unchanged |
| `mine` | `ROUTE` `PROFILE` `TOP_N` `CLOCK_PERIOD_NS` | `mine-<route>/candidates.json`, `cells.txt` | `min(TOP_N, base(PROFILE) + factor(ROUTE))` candidates, named for their route |
| `netlist` | — | `netlist/netlist.json`, `cells.txt`, `<cell>.sp` | the union over every route mined, de-duplicated by identity |
| `abstract` | — | `abstract/abstract.json`, `<cell>.lef` | one abstract layout per netlist |
| `charlib` | `CLOCK_PERIOD_NS` | `charlib/charlib.json`, `generated.lib` | one Liberty cell group per abstract, each with an `internal_power` group |
| `lc` | `LC_FAIL` | `lc/lc.rpt`, `lc/generated.db` | zero errors and a database — or, told to fail, an error per cell and at the least one, no database, exit 4 |
| `synth-custom` | `CLOCK_PERIOD_NS` `EDA_CONTAINER_NAME` | `syn-custom/report/qor.rpt` (`dc-qor-report`), `adoption.json` | adoption from the library's size, and the slack of the period it bought |
| `pnr` | `ARM` `CLOCK_PERIOD_NS` | `pnr-<arm>/postroute.summary` (`innovus-timing-summary`), `postroute.json` | the arm's critical path, `2.20 × (1 − 0.015 × adopted masters)` |
| `verify` | `ARM` `VERIFY_VIOLATIONS` | `verify-<arm>/verify_drc.rpt` (`innovus-verify-drc`), `liveness.json` | the violation count it was asked for, echoed on both reports' inputs, and the liveness pair for that arm |

Every report carries the inputs it was computed from, so a reader can assert the period asked and the arm. One mechanism produces all the numbers, and the makefile's own variables state it: a mining profile has a base yield (`narrow` 3, `steady` 12, `broad` 20 a route) and the route being mined adds a factor of its own — the sum of the route slug's characters modulo `ROUTE_SPREAD` (3), so `r1` adds 1 and `r2` adds 2, and `candidates.json` says which — with `TOP_N` capping the two together. Without that factor every route of one profile would yield the same count, and a pack mining six routes would be reading one answer six times under six names. A library of at least `ADOPTION_FLOOR` (10) cells is adopted, one master per `CELLS_PER_MASTER` (4) cells and `INSTANCES_PER_MASTER` (9) instances of each, and a smaller one is adopted not at all; every adopted master buys `GAIN_PER_MASTER` (1.5%) of the critical path. So over route `r1` at `TOP_N=20`, `narrow` mines 4 cells, which is under the floor, and ends in zero adoption; `steady` mines 13, adopts 27 instances of 3 masters and improves the two arms' ratio by 4.7%; `broad` mines 20 (its 21 capped), adopts 45 of 5 and improves it by 8.1% — a five-percent Goal met by one and missed by the others, decided by nothing but the profile the Strategy asked for. Zero adoption is a result and not a failure, so `verify` reports both halves of the liveness pair — whether the generated library was in the library set before the session launched, and how many generated cells the restored database answers with — because "the mapper took none of it" and "the mapper never saw it" give the same adoption count and mean opposite things.

Every stage refuses a value it cannot safely use before it makes anything at all. `ROUTE` and `ARM` name a directory — the route's candidate set, the arm's report directory — so a value carrying path components would put a stage's output where the Permit resolved no write: `ARM` is one of the two arms, `ROUTE` a slug of lower-case letters, digits and dashes starting with a letter or a digit, and each is checked before the first `mkdir` rather than after it. `TOP_N` and `VERIFY_VIOLATIONS` are held to the same canonical-integer grammar the parse-time table holds `STANDIN_SLEEP` and its neighbours to — `0`, or a digit that is not `0` and more digits — and `LC_FAIL` is exactly `0` or `1`; a malformed or non-canonical one is refused in words with exit 2, never taken as a zero and never rewritten to the number it would mean, because a gate ruling on a violation count that quietly became zero is a gate that passed on nothing, and this flow does not rewrite a caller's answer, only refuse the one it will not use.

And what make itself is refused, because a shell check is worth only what make left for it to check. Make takes any `VAR=value` a command line carries, declared in the makefile or not, and expands it the moment anything references that variable — so a `ROUTE=$(shell …)` ran its command at the instant `export ROUTE` put the value in a recipe's environment, and the slug check that followed ruled on what that command had printed. Three things answer that, in the order the makefile does them.

**What a caller may name**, first, before anything else. The command line is read by name and never by value — `$(.VARIABLES)` and `$(origin …)` answer with names, and a name expands to nothing and runs nothing — and a name that is this flow's own (`PROJECT_ROOT`, `SHELL`, every path it derives) or one it has never declared (the helpers the boundary itself is made of, or anything else at all) stops the flow in words before a single value is looked at. A boundary a command line can redefine is not one: `standin-hold=` would otherwise switch every check below off, and `standin-hold=$(shell …)` would run its command while make was still reading the file. Every helper, every derived path and every declared variable is `override` as well, so a caller's value never wins even where nothing refuses it.

**What a caller may set**, next. Every declared variable is frozen to the characters that were typed rather than to what they would expand to; after that block nothing in the makefile expands a caller's value. The ones a recipe reads out of the environment reach the shell as a word and never as syntax, and each recipe refuses one it cannot use, in its own words, before it makes anything for it. The rest — `DESIGN`, which every path is named for, the numbers the arithmetic is made of, and the two words a wrapper is told — are held at parse time to the grammar of their kind and not merely to a class of characters, because a class is not a shape: `--` and `1-2` are made of nothing but number characters and are not numbers, `01` is a whole number spelled so that no report can carry it, and `-x` is made of name characters and is not a name. A whole number is `0` or a non-zero digit and more digits; a switch is `0` or `1`; a number is a whole number, optionally signed, optionally followed by one dot and digits; a name is lower-case letters, digits, dashes and underscores not beginning with a dash. Between the two lists every variable a caller may set is held by exactly one of them, by construction, so a variable added to the flow and to neither is refused rather than left unruled.

**Where a removal lands**, last. `PROJECT_ROOT` is the makefile's own location and is not a caller's to set, so the tree a stage builds and clears in is the copy it was run from (D19). Each `rm` then asks, immediately beside itself, where its target *is* rather than what it is spelled: a `..` component and a symlink are refused in their own words, and the target and the root are each resolved on disk (`cd -P … && pwd -P`, which walks every symlink and every `..` as the kernel does) and compared. A prefix check on the text is not that question — `<root>/results/../../elsewhere` begins with the root character for character and names a directory two levels above it, and a directory inside the root that is a symlink names wherever it points.

A stage that writes one artefact per candidate — `netlist`'s `.sp` files, `abstract`'s `.lef` files — clears its own set inside the workspace before it writes this pass's, so a run over a smaller candidate set leaves none of the larger one behind: a netlist left over from a wider pass is a candidate the next stage would lay out and characterise, and the library would end up holding cells nobody mined.

A flow can also be generated with **a link for `synth` to plant** (`plantsLink: { name, to }`, beside `failures` and `sleepSeconds`): before the stage writes anything it makes `<name> -> <to>` at the Campaign workspace root — the copy's own parent, `WORKSPACE_ROOT`, derived from the project root like every other path here — once, and leaves it alone afterwards. Nothing plants one unless the generator was asked for it, both of its names are this flow's own and are refused from a command line, and each value is held **on the generating side** before a character of makefile is written: the name a slug, the target a relative path of plain segments, so what reaches the recipe is a word and never syntax. It exists for one contract test, the workshop's resolved-root rule, which needs a workspace a Job of the Campaign's own rearranged — the way a link really gets into one — rather than a link the test reached in and made during a window it had to win a race for.

Heavy stages (`synth`, `synth-custom`, `pnr`) sleep `STANDIN_SLEEP` as `synth` always has; the light ones take what they take. A stage whose predecessor left nothing stops with exit 2 and names the stage to run first. `test/contract/standin-stages.test.ts` runs the whole sequence by hand, every stage a Job launched through `/hima job launch local <workspace> -- make …` so the Permit decides the wrapper and the workspace, reads every report through the reader that reads it and rules on what that reader read where a shipped rule speaks for it, and asserts the bound flow root is byte for byte what it was: a Campaign builds in its own copy and never in the flow the Site binds. It also drives what every stage refuses, a rerun over a smaller candidate set, and the library gate told to fail over an empty one. The containment is tested adversarially: a value make would have expanded (`$(shell touch …)` in a route, an arm, a count, a design, a period, the helper that holds them all, a variable this flow never declared, and the container name), a `PROJECT_ROOT` of someone else's choosing, a derived path of someone else's choosing, a `DESIGN=../x` and a malformed value of every kind are each refused; a stage whose output directory is a symlink pointing outside the project root, and a design whose `..` climbs out of it, are each refused with what they pointed at intact. No canary outside the workspace is ever written, and the bound flow root's listing is byte for byte what it was. A handful of those cases are handed to `make` directly rather than through a launch line, because a chat command's words are separated by whitespace and every make expression that runs anything needs a space in it; the values that can be typed on a launch line are launched.
