# Test the product's window through the desktop shell's own driver mode, not through a browser

HimaGuide is delivered as one desktop window around `dsh --profile hima` ([ADR-0003](0003-desktop-window-around-the-hima-profile.md), D39), and step 3 of the acceptance ladder — the Campaign: a multi-generation Loop started, watched, cancelled and resumed from that window — is where the window stops being a viewer of one Run and becomes the place the work happens. Until now the contract suite exercised the product a person uses with one smoke test (`--smoke`: open the window, check the page carries dsh's boot graph, exit), while every other test drove the harness through a booted host over HTTP or through a test-only in-process boot. Whatever the card, the page, the fence and the session look like to a person went untested, and the user's direction for step 3 is that the harness looks and acts like a desktop app and is tested as one. We decided that the desktop shell gains a driver mode and that it is the one seam every step-3 contract test drives the product through.

Started with `--driver`, the shell's main process does everything it does for a person — prepares the home (or uses the one `DSH_HOME` names, a test's isolated home), launches the real host through the same `host-launch.ts`, sweeps stale cookies, exchanges the token in the window's own session, loads the page — and then reads JSON lines on its standard input and answers each with exactly one JSON line on its standard output: `host` (the host's URL and the session cookie the window holds, for a test's route calls), `open` (a path under the host's origin, answered when the load finished with the status the navigation got), `read` (a marked region's rendered text and `data-hima-state-*` attributes), `wait` (until a region shows a text, polled from the main process), `click` (a marked control, scrolled into view and clicked with a real mouse event at its centre, answered once the page has counted the click and re-sent until it has), `screenshot` (a PNG), `quit` (answer, stop the host, exit). Nothing else is written to stdout; the shell's own lines go to stderr; a line that is not a request is answered `ok: false` with a null id; an unknown op, region or control is a loud refusal, never a no-op. `packages/desktop/src/driver.ts` is the mode; `test/contract/support/driver.ts` is how a test boots through it, skipping with the reason where Electron cannot open a window.

The boundary is ADR-0003's, restated: the driver is the shell's own code and patches nothing in dsh; reads, waits and clicks run from the main process through `webContents.executeJavaScript` and `webContents.sendInputEvent`, the way developer tools look at a document, and the page gets no preload and no IPC surface for any of it; the navigation fence stands in driver mode, and `open` refuses every URL outside the host's origin — an absolute URL elsewhere, `file:`, another port — in the fence's own words. The host-to-window interface stays the `/hima/api/` routes of [ADR-0002](0002-hima-remote-over-webserver-routes.md), plus one document beside them: `GET /hima/`, the workbench page the bundle serves behind the same session fence, listing the ledger's Runs and, with `?run=<id>`, rendering that Run's card from the very run view the JSON route answers with. The card on that page carries the same sections, words and markers as the card the tool view renders in dsh's chat; the words are one module (`packages/harness/src/card-labels.ts`) both mounts read.

## Considered options

- **WebDriver or Playwright against the page.** Rejected: a dependency on a browser-automation framework and a driver binary that has to be kept in step with Electron's Chromium, and a second way of reaching the window that is not the window's own — the shell already owns the `BrowserWindow` it would be automating, and can answer for it directly. It would also be a third mechanism between the host and the window where D39 allows one.
- **Route-only tests that never open the window.** Rejected: what they prove is the routes, which the step-2 suite already proves at the booted-host seam. The card, the page, the fence, the session cookie a person actually gets, and the clicks a person actually makes would stay untested, which is the gap this decision exists to close.
- **Mount the HimaGuide client module on the workbench page** so the card is one React component mounted twice. Not feasible without a second bundle: dsh's client-module envelope answers React and the baseline libraries only inside the web app's own index, so a page of ours would have to carry its own React. The card is rendered on the host instead, from the same run view, with the words shared and the markers identical; a change to what the card shows lands in both mounts, and a change to what it says lands in one.

## Consequences

- Every step-3 ticket (#25–#31) tests through `bootDriver` and the markers: a start from the window's form, generations arriving in the card, cancel and resume as clicks, the experience report read off the page, and the ledger and the run view read over the routes with the session from `host`. The step-3 acceptance script starts the Campaign from the window through the driver. The step-1 and step-2 tests keep their seams.
- `--smoke` is gone: the driver covers it (the profile made from an empty home, the host booted, the product's own page loaded in a window titled HimaHarness, the host stopped on quit) and one mechanism is one thing to keep true. `test/contract/desktop.test.ts` is now that test, from an empty home with `--site local`, so the developer entry's seeding is proven on a fresh home too.
- A driver test opens a real window on the developer's screen — shown without taking focus, and focused only when a click needs it. A headless machine skips with the reason; a skip is never a pass.
- The card's markers (`data-hima-region`, `data-hima-state-*`, `data-hima-control`) are part of the product's contract with its tests, listed in the README's "Driving the window". A ticket that adds a control marks it; a ticket that adds a region documents its state attributes there.
- `pnpm run desktop --site local` seeds a developer's home with the same `local-site.ts` the suite writes its stand-in flow and local site with, so a Loop is watched converging in the product on a stand-in before it touches the reference site. The stand-in's report is constant here; the period-aware stand-in is the Loop ticket's.
- Requests are answered one at a time in order. A test that needs two things at once — a wait on one region while a route call is in flight — makes the route call from its own process, which is what the session from `host` is for.
