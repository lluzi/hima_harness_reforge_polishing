## What was checked and held up

- **Path confinement (run-reports.ts).** The relative path is held to
  `^<dir>/<node>/r<k>/<name>$` with `[A-Za-z0-9._-]`, and `.`/`..` segments are refused.
  `dir` is schema-held to `[a-z0-9][a-z0-9_-]*` (packs.ts `packReports`). The workspace and the
  target are each resolved with `decideRead`: realpath on the Site, then the Permit read roots,
  then an `inside(real, ws.real)` check. That refuses symlinks out of the workspace,
  absolute-path tricks and a reports dir that escapes the workspace. Reads use `test -f` and then
  `head -c 262145 -- <abs>`. The listing uses `find <real root> -mindepth 3 -maxdepth 3 -type f
  -print0` (`-P`, so links are not followed), filtered by the same name patterns, capped at
  4 MiB by the channel and at 500 entries. Sizes are fetched in batches of at most
  3 000 path bytes.
- **Command injection.** The ssh wire quotes every argv word (`quote`), and a local Site spawns
  without a shell. Unix names cannot hold NUL, and newlines or odd bytes in names fail the
  name pattern before `wc`. The `admit` shapes for `find` and `head` are exact (argv length,
  literal flags, numeric byte count, `--`, absolute path).
- **Project scoping.** `/runs/<id>/reports[/file]` sits under the generic
  `scopedRun` gate (remote.ts:1664-1668), which requires a live `sessionId` and
  `authorizeRunAccess`. The client passes `viewer` through `scoped()`. `hima_chart {runId,path}`
  calls `assertProjectAccess` before any read (tools.ts:475), and so does `hima_context`
  (tools.ts:569) before `newestRoundCharts`. Pack charts are global by design, and the pack id
  is schema-checked by `installedPackFolder`.
- **Chart JSON.** It is read at most 256 KiB (a truncated read is refused) and decoded as fatal
  UTF-8. A strict zod schema bounds strings and arrays (≤16 categories, ≤3 series, finite
  numbers).
- **XSS.** HimaChartCard, ReportsView (`<pre>{text}</pre>`) and TeamCanvas render only through
  React text nodes and attributes, with no `dangerouslySetInnerHTML`. The LibInsight insight
  page escapes `<>&  ` in the data JSON, its template `esc()`s every string it puts
  into `innerHTML`, and the CSP allows only the template's own script hash (no `unsafe-inline`,
  `default-src 'none'`). Injected handlers therefore cannot run and the page cannot reach the API.
- **DBOS lookups.** `readRun`, `readRunRecords(...,'workspace')` and `executionContext` each fall
  back to the Ledger or `fabric.executionContext` for a legacy (pre-DBOS) Run. A cancelled Run
  reads through `readDurableExecutionContext`, and a Run still preparing has no workspace record,
  so its listing is empty.
- **Architecture.** No autopilot is revived and nothing drives through the Ledger. The andes
  `autopilot:` segments parse but are display-only (pack-on-dbos R5), and the DBOS route drives
  the compiled IR. `resident-activity` is an in-memory display cache that nothing decides on.
  The Reports listing cache is a 5 s TTL display cache. Shared wiring is small: `channel.ts` +10,
  `index.ts` and `remote.ts` add routes and exports, `packs.ts` changes are schema only.
- **"Project" wording.** It is confined to user-visible strings. `data-hima-control` and
  `data-hima-region` values, tool names, APIs and identifiers are unchanged. The only stray
  user-visible "Campaign" is Host-side (M3).
- **Leakage scan.** Over the whole `+` diff there are no `tcbn`, `bwp<digit>`, `smic`, real
  OpenC910 data or chart JSON. `.gitignore` coverage was verified with `git check-ignore`:
  - `packs/andes-cell-fmax/knowledge/.gitignore` covers `design-notes.md` and `charts/`.
  - `sites/eda_cluster_ctu_01/mock-eda/share/designs/.gitignore` covers `openc910/`.
  - `git ls-files` shows none of those tracked.
  - `openc910-mini` fixtures are labelled synthetic.
  - The 1951.60 MHz / 41 200 µm² / 474 numbers come from the synthetic AES mock model.
  - The `tsmc28` permit path predates this range (on main).
  - "TSMC, N12" appears only in a policy sentence.
- **Test registration.** All new contract tests are registered in `test/contract-groups.json`.

## Important

### I1. Auto-open misses a Run that `hima_run` returned while still preparing
- **Where:**
  - `packages/harness/src/client/HimaRunCard.tsx:1056-1064`
  - `packages/harness/src/client/run-auto-open.ts:50`
  - Upstream: `packages/harness/src/durable-fabric.ts:56-58,71`
- **What:** `shouldAutoOpen` requires `status === 'running' || 'waiting'`. A DBOS Run whose
  `preparation` flow fact is not yet written has **no status** (`durableRunView` yields
  `undefined`), and `durableStartResult` returns `kind: 'preparing'` in that case.
  `HimaRunCard` reads the Run **once** (`fetchRun` effect, deps `[runId, sessionId]`). The
  auto-open effect is keyed on `[runId, startedRun?.id]` only, so it is decided once on that
  first read and never re-evaluated when the status changes.
- **Failure scenario:** On an SSH Site (Linglong andes/MAGE), the person approves and
  `hima_run` returns `preparing`. The receipt card mounts and reads `status: undefined`, so the
  pane never opens. The recorded take then shows no auto-open, and since no `undefined` case is
  tested, nothing catches it.
- **Fix:**
  - Treat an absent status on a fresh `hima_run` receipt as starting (`status === undefined`
    → allowed, ended statuses still refused). Alternatively, re-run the effect on
    `startedRun?.status` while the claim stays once-only (`claimAutoOpen` already guards it).
  - Add a test for `status: undefined`.

### I2. Report lookups are heavy, unbounded in time, and now on `hima_context`'s path
- **Where:**
  - `packages/harness/src/run-reports.ts:83-95` (`workspaceOf`, `methodOf`), `:195`
    (`workspaceOf` outside the try)
  - `packages/harness/src/tools.ts:409-419,575`
  - `packages/harness/src/durable-views.ts:50-110`
- **What:** On DBOS, `readRunRecords(runId,'workspace')` still walks **every** task projection.
  For each result it re-verifies task-result, observation and verdict source facts and digests,
  plus effect facts and delivery facts, and only then filters by type. `methodOf` calls the full
  `executionContext`, which includes `taskViews`. Each listing (every 10 s per open Project tab,
  5 s cache), each report open (uncached) and now **every `hima_context` call** pays for both,
  then runs 4 or more Site commands with no overall timeout (ssh has only `ConnectTimeout=10`).
- **Failure scenarios:**
  - A long Run (MAGE or andes, many rounds) makes `hima_context` noticeably slower.
  - A Site whose `find` or NFS stalls makes the owner's primary fact tool hang, although
    `newestRoundCharts` claims to be best effort.
  - A single integrity throw anywhere in the Run's records ("Task result source fact is
    unavailable") makes `GET /reports` a 500 instead of the friendly `error` sentence, because
    `workspaceOf` runs outside the try at :195.
- **Fix:**
  - Read the workspace straight from `store.flowFact(runId,'preparation')`, or add a narrow
    reader `readRunWorkspace`.
  - Cache the frozen method's `reports.dir` and node order per run and revision (they are
    immutable).
  - Move `workspaceOf` inside the try.
  - In `hima_context`, race `newestRoundCharts` against a short deadline (about 2 s), or serve
    only from the warm listing cache.

### I3. The new confinement and admission surface has no negative tests
- **Where:** `test/contract/run-reports.host.test.ts`, `test/contract/hima-chart.host.test.ts`.
  No channel-admission test touches the new `find` or `head` shapes.
- **What:** The `..` test (`reports/synth/../../../etc/passwd`) is refused by the regex alone,
  so the realpath and `inside` confinement and `decideRead` are never exercised. Nothing tests:
  - a report that is a symlink to a file outside the workspace (must be refused);
  - a reports dir or `<node>` dir that is a symlink out of the workspace (must refuse or not be
    listed);
  - a binary or NUL report;
  - a FIFO or non-regular file;
  - `admit` refusing `head -c 0`, `head -c 1 /rel`, `head` without `--`, or `find` with
    `-L`/`-exec`;
  - one project's session reading another project's `/runs/<id>/reports` (only the generic
    gate protects it);
  - the `hima_chart` scope test beyond the case where no agent is present.
- **Failure scenario:** A later refactor drops the `inside(...)` check or the `-type f` / `-P`
  flags, and every current test still passes.
- **Fix:** Add symlink-out and symlink-in cases on the local Site fixture, plus a small `admit`
  table test for the new shapes. Add one cross-project 403 test on the route (two sessions, two
  Runs).

### I4. The andes dry route's "forks genuinely overlapped" proof does not test overlap
- **Where:**
  - `test/contract/support/andes-resident-durable-worker.ts:100-105`
  - `test/contract/andes-cell-fmax-durable.host.test.ts:35-37`
- **What:** `startsBeforeJoin` checks only that both branches' engineering jobs were `launched`
  before the join's verdict, and that two distinct `branchId`s were observed. A fully
  serialised fork (branch A launches and finishes, then branch B launches and finishes, then
  the join) satisfies both conditions. The test comment claims "each fork's two branches
  started before either finished", which the code does not check.
- **Failure scenario:** A regression that serialises `parallel` blocks (for example
  `parallelJobs` being honoured as 1, or the branch workflows awaited in sequence) keeps this
  headline proof green.
- **Fix:** Compare `max(launch seq of A, B)` against `min(finished seq of A, B)` using the
  synthesized `job` `finished` records, which are already read in `jobRecords`. If
  `CTU_MOCK_TIME_SCALE=0` makes true overlap nondeterministic, rename the assertion to what it
  proves ("both branches dispatched before join").

## Minor

- **M1. `team-view.ts:181` picks the oldest started invocation, not the latest.**
  `pool.find(...)` returns the oldest non-pending, non-succeeded invocation, but the comment
  says "the latest started wins". With an earlier `failed` and a later `running` invocation of
  the same task in the same round, the line and station show **failed**. Use `findLast` (the
  views are oldest first), or sort by iteration and seq. This is latent today, because duplicate
  current invocations in one iteration are rare.
- **M2. TOCTOU between `decideRead` and `test -f` / `head` (`run-reports.ts:282-285`), and
  between `find` and `wc`.** A resident in the same workspace could swap a parent dir for a
  symlink, or the file for a FIFO, after the realpath check. The read would then follow the
  swap or hang, since there is no command timeout. Impact is low: the resident runs as the
  same Site user and could read the target itself. Mitigations: run `head` on a path re-checked
  by a combined realpath-and-read, or add a channel timeout for the report verbs.
- **M3. Host refusals shown to the person still say "Campaign workspace".**
  `run-reports.ts:143,147,274,279,283` (Reports face) and `chart-files.ts` messages that pass
  them through (chat card) use the old wording. `run-reports.ts:286` and `sizesOf` can also put
  the Site's stderr (with an absolute path) into the UI, which contradicts the "no host path"
  comments. Reword to "project folder" and strip stderr from user-facing messages.
- **M4. Duplicate React keys in the chart card.** The chart schema does not require unique
  `categories` or series `name`s (`charts.ts:28-29`), and `HimaChartCard.tsx:50,57,114,121`
  keys on them. Duplicates give React key warnings and possible row mix-ups on re-render. Add a
  uniqueness refine, or key by index.
- **M5. Every Reader metric gets a leading `+` (`team-view.ts:281`, `saidReader(..., true)`).**
  This is right for gain metrics (andes `best_gain_pct`) and wrong for an absolute metric
  (Fmax would show "+1951.60 MHz"). Sign only when the type is a delta, or add a `sign` option
  to the view metric.
- **M6. Dead or unfinished port residue:**
  - `RunReportFile.modifiedAt` is never set (`remote.ts:646`).
  - The `hima-studio-secondary` class has no CSS (`HimaWorkbench.tsx:206-217`, deferred by
    comment).
  - The `runId` prop is threaded into `Station` and `Member` but unused (`TeamCanvas.tsx`).
  - The `teamOutputAt` export has no consumer (`index.ts:1762`).
  - `bestHeadline` (`results-view.ts:96`) duplicates `readerValue` (`team-view.ts:140`).
- **M7. `packs/andes-cell-fmax/graph.yml:12-18` still describes the retired model** ("the owner
  begins each of those nodes ...", "drives itself in four segments, each handing back to the

  A Pack author or agent reading this file is misled. Rewrite it in one paragraph.
- **M8. The zero-model-calls proof is hard-coded.** `productModelCalls: 0` is a literal in the
