# U3: DBOS and the application fact repository

Issue: [#86](https://github.com/lluzi/hima_harness_reforge_polishing/issues/86). The Host now initializes DBOS against its private PostgreSQL databases and stops DBOS/pools before closing Ledger and PostgreSQL. This unit supplies the durable repository and projection interface. Product Run dispatch, task adapters, composition execution and automatic product projection are later units.

## Mechanism

SDK and node-pg datasource are pinned to 5.2.11; pg is 8.16.3. The finite workflow registry is installed before launch. Application version hashes installed executable/helper bytes, runtime resources and adapter/dependency versions; Pack installation remains data. Loopback pool configurations carry credentials without a database URL in logs. OTLP is disabled and inherited DBOS cloud mode is refused.

The application database holds Run/control identity, effects, immutable phase facts, results and outbox events, separate from the SDK system database. A direct datasource transaction commits result, outbox and datasource transaction receipt together. It is not nested inside a DBOS step, and application code does not write SDK tables. Same identity/content is idempotent; conflicting content is rejected. Actual effect admission uses an uncached query, serializes with control changes and checks current Permit.

Ledger receives immutable facts identified by stable fact ID and application sequence. Projected rows carry no legacy status, control or current-node fields, so this history interface cannot activate the old scheduler. The application row records its DBOS engine and schema version. Product scheduling remains on the old path until U6 replaces that path; this intermediate commit does not claim the full cutover.
