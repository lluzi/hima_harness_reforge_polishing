## Fixes made

Four real parser defects were found and fixed in the Pack, each with a new synthesized fixture (invented instance/net/cell names, no TSMC cell names or customer paths) reproducing the exact real grammar feature, plus a regression test. Fixes 1-2 (both in `atcs.reports`) land together in commit `fix(atcs): collapse duplicate-endpoint paths and tolerate PT's slack annotation`; fixes 3-4 (both in `atcs.adapters`) land together in commit `fix(atcs): parse the real PT per-arc grammar and SPEF NAME_MAP aliases`; this document and the preflight script land in `test(atcs): real report corpus preflight`.

1. **`atcs.reports.parse_path_report` refused this Pack's own default report shape.** `-nworst 20` (`atcs.adapters.DEFAULT_NWORST`) — confirmed as the B_lazy g001 run's own generation flag — means a real `setup.rpt`/`hold.rpt` legitimately lists several of an endpoint's worst paths, all sharing one path group; the old code raised `AtcsError("duplicate-check", ...)` on the second occurrence, refusing essentially every real report this Pack's own default configuration would ever produce (100-126 raw blocks collapsing onto 11-53 unique endpoints across the corpus). Fixed to keep the worst (most negative) slack among same-endpoint/same-path-group repeats, and to still refuse when repeats disagree on path group (the genuinely ambiguous case the original design was meant to catch — confirmed zero such cases exist anywhere in the real corpus, checked programmatically). `complete` was also computed against the *deduplicated* path count instead of the report's own raw block count, which is what `-max_paths` actually bounds; fixed to use the raw count (the Foundation `setup.rpt` files sit exactly at their own `-max_paths 100` cap, so this changes real outcomes). Tests: `flow/tests/test_core.py::ParsePathReportTest` (`test_duplicate_endpoint_same_group_keeps_worst_slack`, `test_duplicate_endpoint_different_group_raises`, `test_incomplete_when_raw_block_count_reaches_cap_despite_dedup`). Fixture: `flow/tests/fixtures.py::path_report`'s new `groups` parameter.

2. **`atcs.reports.parse_path_report`'s slack-line regex rejected a real, common PT annotation.** Real reports emit `slack (VIOLATED: increase significant digits) <value>` whenever a violation's magnitude rounds to a displayed `-0.00` — confirmed present in **161** blocks of the B_lazy g001 corpus alone (the run generated with this Pack's own actual `-nworst`/`-slack_lesser_than` flags), not just the historical Foundation reference material. The old regex required the parenthetical to read exactly `(VIOLATED)`, so every such block failed to match its own slack line and (being a non-trailing block) raised `AtcsError("malformed-report", ...)` — this alone would have made every real B_lazy-shaped report from this campaign unparseable, even after fix 1 above. Fixed to accept any `VIOLATED`-prefixed annotation while still rejecting `(MET)` (a genuinely non-violating row — see "Remaining refusals" below). After this fix the entire B_lazy g001 corpus (the shape closest to this Pack's own production output) parses with **zero** refusals. Test: `test_annotated_violated_slack_is_parsed_not_refused`. Fixture: `flow/tests/fixtures.py::path_report`'s new `slack_annotations` parameter.

3. **`atcs.adapters.parse_path_detail` did not match the real per-arc report grammar at all**, confirmed by cross-checking a real Foundation ROUND3 `setup.rpt` sample (this parser's own module docstring already flagged it as unverified: "no real report sample ... was available to this task"). Three compounding defects, fixed together since they only make sense against the real grammar as a whole:
   - A real report wraps any instance/pin name too long to share its line with the value columns onto its own line, leaving the columns alone on the next physical line with no name prefix — the common case for this design's deep hierarchical paths. The old single-line regex silently skipped every such arc, i.e. nearly the entire path.
   - Every arc's Incr/Path pair has a stray `&` annotation token between them that the old regex's fixed two-number tail did not tolerate, so even short unwrapped lines (e.g. a top-level clock port's own arc) never matched either.
   - A net's own line never carries Incr/Path — only `Fanout` and (except a path's final net) `Cap` — never the five-column shape the old regex assumed; a two-number net line that happened to slip past the old anchored tail had its `Fanout` integer silently misread as an `Incr` delay value in nanoseconds (a wrong *known* number, not a safe `unknown`). The real column order is also `Fanout Cap Trans Incr Path` (`Cap` before `Trans`), not `Fanout Trans Cap Incr Path`.

   Rewritten to classify each arc's numeric tail by shape (a bare integer, or integer+decimal, is a net's `Fanout`[`+Cap`]; three decimals are a pin/port arc's `Trans`/`Incr`/`Path` — PT never prints these two shapes ambiguously), and to decide net-vs-cell delay attribution structurally (a pin arc immediately preceded by a net-info line is net delay; immediately preceded by another pin arc — the same instance's other pin — is cell delay), never by guessing a cell-library-specific pin direction from its name. `location` now keeps the full instance path up to its leaf pin (`name.rsplit("/", 1)[0]`) instead of the old `name.split("/")[0]`, which returned only the top-level block name for any deep hierarchical path — nearly useless as "a value identifying where on the floorplan." Tests: `flow/tests/test_adapters.py::ParsePathDetailTest` (rewritten around `fixtures.path_detail_report`), plus the pre-existing `flow/tests/test_cli_state.py::ResidualPtQueryEvidenceTest`'s inline sample corrected to the real grammar (it was built on the same wrong assumption the old parser was). New fixture: `flow/tests/fixtures.py::path_detail_report`.

4. **`atcs.adapters.parse_spef_net_names` returned the wrong values entirely.** A real StarRC SPEF (confirmed against both Foundation `.spef` corners, ~83 MB / 98780 nets each) writes `*D_NET` lines against a `*NAME_MAP` index alias (`*D_NET *1424 13.6978`), never the literal net name, per the IEEE 1481 name-compression convention StarRC actually uses here. The old function returned the raw `*1424`-shaped alias tokens as if they were net names — every real net name came back as an opaque index no real `new_nets` request could ever match, so `presta_qualification` would have marked every real net "unqualified" regardless of what the SPEF actually modeled. Fixed to resolve every alias through the `*NAME_MAP` block built from the same text; a literal (non-aliased) `*D_NET` name is still supported directly, and an alias with no matching `*NAME_MAP` entry is dropped, never guessed. Tests: `flow/tests/test_adapters.py::ParseSpefNetNamesTest`. New fixture: `flow/tests/fixtures.py::spef_net_name_map_and_d_nets`.

## Remaining refusals (correct fail-closed outcomes — documented, not fixed)

All 8 remaining refusals are Foundation `setup.rpt`/`hold.rpt` files, each on a `slack (MET)` block that is not the report's last block. `slack (MET)` means the path is **not violating** — it exists in this historical corpus only because the old, frozen flow's own script (Foundation reference material, not this Pack's own template) requested `-slack_lesser_than 1000.00` (effectively unfiltered). ## Fix round 1 (controller review)

A follow-up review of this task found one Critical, two Important and one Minor issue. All four are fixed in commit `fix(atcs): keep PT's violation verdict at precision boundaries`.

### Critical: a precision-limited violation could read as clean

`atcs.reports.parse_path_report`'s slack Measure for a `(VIOLATED: increase significant digits)` row carried the *displayed* number (e.g. `-0.00`) as `known`. `float("-0.00") < 0` is `False` in Python, so any downstream code that inferred violation from the numeric sign alone — `atcs.state.compare_checks` in particular — would have silently treated a violation PT itself confirmed as clean.

Fixed: every path row `parse_path_report` returns now also carries `violated: True` (PT's own classification fact — a `slack (MET)` row never reaches this parser at all, see above). For an annotated row, the slack Measure is now `unknown("precision-limited: re-query with more significant digits")` instead of the misleading displayed number; `violated` stays a known `True` regardless. `atcs.state.capture` threads `violated` through into each `checks[<checkKey>]` entry; `atcs.state.compare_checks` now resolves each check's violation status from `violated` first, falling back to the slack Measure's sign only when no `violated` fact is present (backward-compatible with hand-built observation data that predates this fix). A check whose current status resolves to violating — via `violated` alone or a known negative slack — can now never land in `fixed`.

Confirmed from real grammar (re-checked across the full Foundation corpus, all four scenarios' `setup.rpt`/`hold.rpt`): every one of the 73 `(VIOLATED: increase significant digits)` rows displays exactly `-0.00`, and zero *unannotated* `(VIOLATED)` rows anywhere in the corpus display `-0.00`/`0.00` — PT itself never leaves this specific ambiguity unannotated. Since `violated` is recorded uniformly regardless of annotation, this Pack's behavior is correct either way: an unannotated `-0.00` (if PT's behavior ever changed) would still be `violated: True`.

This Pack's own `pt-scenario.tcl` now also requests `-significant_digits 4` (up from PT's own default of 2 — confirmed via the real `report_timing(2)` man page, `/data/eda/software/eda_tools/synopsys/prime/X-2025.06/doc/pt/man/cat2/report_timing.2`, read-only on the server: *"Specifies the number of digits after the decimal point displayed for time values ... the default is determined by the report_default_significant_digits variable, which is 2 by default. ... This option controls only the number of digits displayed, not the precision used internally for analysis."*) to reduce how often a fresh report lands on this boundary at all; it cannot eliminate the case (PT can still have a genuinely smaller violation), which is exactly why the `violated`-fact fix above, not just the display-precision bump, is the real correctness fix. Documented in `knowledge/observation-strategy.md`.

Tests: `flow/tests/test_core.py::ParsePathReportTest::test_annotated_violated_slack_is_parsed_not_refused` (now asserts `violated: True` + `unknown` slack for the annotated row); `flow/tests/test_observation_contract.py::CompareChecksViolatedFactTest` (five new cases: precision-limited remaining-never-fixed, precision-limited entrant, precision-limited prior resolved fixed, a defensive violated-overrides-contradictory-slack case, and the pre-existing sign-only fallback for entries with no `violated` fact); `CaptureTest::test_precision_limited_row_carries_violated_true_and_unknown_slack`.

### Important: SPEF net-name parser against unfiltered real text

Streamed the first 200,000 lines (8,318,228 bytes) of the real Foundation `swerv_wrapper.cworst_T.spef` directly into `parse_spef_net_names` — unfiltered, not the bounded `grep` extract the main preflight run above uses — to check the full real grammar for collisions the pre-filtered extract could hide.

**This found a real defect.** A real SPEF's `*PORTS` section reuses the exact same `*<index> <token>` line shape as `*NAME_MAP` for a completely different purpose — `*<index> I`/`O`/`B` (port direction), not a name. The real file's `*NAME_MAP` maps index `*98784` to `clk`; its `*PORTS` section separately has `*98784 I` (a real line, confirmed via `grep -n "^\*98784 "` on the server: lines 30 and 195238 of the real file). An earlier version of this fix's own `parse_spef_net_names` scanned the whole text for any `*<digits> <token>` line, so this collided as though `*98784` ambiguously named both `clk` and `I` — the same-index-conflict check added for the Minor item below (correctly) raised `AtcsError("spef-name-map-conflict", ...)` on this real file.

Fixed: `parse_spef_net_names` now reads `*NAME_MAP` entries only from inside the actual `*NAME_MAP` section (bounded to the text between the literal `*NAME_MAP` line and the next top-level, letter-led `*SECTION` header, e.g. `*PORTS` or `*D_NET`), never the whole file. The corpus preflight script's own bounded SSH fetch (`fetch_bounded_spef_net_lines`) was updated to match: it now fetches the real `*NAME_MAP` section *verbatim* (`sed -n '/^\*NAME_MAP$/,/^\*D_NET /p'`, ~196k lines / ~10 MB here) instead of grepping only digit-led lines, so the real section headers (`*NAME_MAP`, `*PORTS`) survive into the bounded extract exactly as `parse_spef_net_names` now needs them; every `*D_NET` line across the whole file is still fetched separately and remains bounded (one short header line per net, never its parasitic body).

Result after the fix: the same unfiltered 200,000-line prefix now resolves cleanly (20 net names, matching the bounded-extract result over the identical line range exactly, byte-for-byte identical set) with no exception. The full corpus preflight re-run against both real SPEF corners resolved 98,780 net names each (unchanged from the original run), zero refusals, using the corrected bounded fetch. Tests: `flow/tests/test_adapters.py::ParseSpefNetNamesTest::test_ports_section_direction_line_never_collides_with_name_map` reproduces this exact real-corpus shape with invented names.

### Minor: duplicate `*NAME_MAP` index entries

`parse_spef_net_names` now raises `AtcsError("spef-name-map-conflict", ...)` when the same `*<index>` appears twice in the (correctly bounded) `*NAME_MAP` section naming two *different* nets — a genuine identity conflict, previously resolved silently by "last one wins". An identical repeat (same index, same name) is tolerated. This check is what surfaced the `*PORTS`-collision defect above during its own verification against real data. Tests: `test_identical_duplicate_name_map_line_is_tolerated`, `test_conflicting_duplicate_name_map_line_raises`.
