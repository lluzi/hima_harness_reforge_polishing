# E1–E4 execution

The graph is `qualify-api -> read-qualification -> qualification-gate -> baseline facts -> candidate facts -> delta -> Insight report -> rule result -> proposal`, with a Reader after every derived output.

Fabric uses its existing `beforeLaunch` callback, after ordinary Permit/workspace resolution and inside the serialized Site slot claim, to attest the exact Host-loaded Permit and Site-bound E1 manifest. The Host authorizes the manifest, Permit, sources, Python, API paths, wrapper spelling and resolved target; pins Python and `/usr/local/bin/edarun` bytes; checks the private Campaign workspace; and writes the admitted Run/node/attempt/Job-session identity at the exact workspace attestation path.

That file carries launch identity to the worker and Reader; it is not a trust root by itself. Before a positive E1 Reader value becomes an Observation, Fabric matches the identity to a successfully finished qualification Job in the same Run. Authority remains the Host `beforeLaunch` decision and durable Job history. A blocked or absent E1 receipt routes to the hard blocker and cannot open later work.

E2–E4 tools use the Site-permitted `/usr/bin/python3`, take only hash-bound prior outputs plus the Site-owned baseline/candidate analysis manifest, and write create-once JSON under `flow/library`. Their Readers independently re-open the manifest, qualification receipt, source, full representative table and entire derived lineage rather than trusting a producer self-hash. The Insight producer writes the strict document body; its Observation supplies the immutable report envelope consumed by Data Insight. The result and proposal retain the same workspace and never acquire a Library write action.

A later E1 attempt may replace a pre-dispatch attestation only for the same Run and node with a strictly greater attempt. Once `flow/qualification` exists, in-place retry is refused because the create-once evidence cannot be safely reused or overwritten; start a new Campaign workspace after reviewing the failed evidence.

The E1 tool holds the exact `QuaLib-2026-new-59099` Site claim. `capacity.parallelJobs: 1` prevents both overlap orders with XTop for Jobs launched and tracked by this Host, without recording a false XTop seat on a Library Job. It does not detect an external process. A future multi-Job Site needs a truthful shared runtime-selection claim declared by both tools. Representative E2 facts, an identical-source zero delta, and a no-mutation proposal are not full corpus qualification, design impact, Library release approval, or business value.
