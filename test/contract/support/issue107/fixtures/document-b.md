# 叠衡 Sketch：工程立项建议

文档 ID：D3D-B；版本：0.9；记录日期：2026-10-09（虚构）；作者：工程负责人姜澄（虚构）。

### B-00｜使用说明

【虚构资料】工具、客户、作者、指标与访谈都是 synthetic demo 设定。本建议比 D3D-A 日期晚，但未经产品负责人采纳，不是对 A 的替代。没有真实竞品资料或签核证明。

### B-01｜谁先试用

【工程主张】首版应面向封装实现工程师。我们担心架构阶段数据过粗，比较页面会产生虚假的精度。建议先接客户已有两 die 布局，再在封装层检查连接可达性；架构师只读报告。这个取舍与 D3D-A/A-01、A-02 不同，理由是实现可复现性，不是批准记录。

### B-02｜输入门槛

【提案】启动即要求每 die 的 DEF 摘要、网表端口表、完整 bump map、确定的功耗表、冷却边界和封装层规则；缺项则整单退回。只接受固定双 die，暂不支持架构 CSV 的 2–4 die 方案。团队估计一个客户的导入要三天，但没有真实集成计时。名称映射、坐标原点、旋转、单位和各版本的关联关系尚未定义；不能宣称这些格式现在已可读。

### B-03｜排序办法

【待验证假设】建议用单一适宜度分数给推荐方案：热指标权重 0.6、互连指标权重 0.4，缺热边界则用内部示例的 85°C 代入。UI 默认只展示最高分方案，认为这样可以缩短第一次演示。权重、85°C 及演示效果均为预置想法，没有业务批准或热求解依据。若资料不足，最多只能说明这是工程组建议，不能称为客户要求。

### B-04｜实现衔接

【提案】输出封装连接修订表与脚本草案，并在演示结束时给一个“实现就绪”标记。这里的“就绪”原意是字段检查完整，未定义接收工具成功导入、热/互连验证或签核责任。建议首版提供商业工具双向连接器，但没有合法 API 样例、许可条件、版本合同或调用证据；它是范围建议，不能写作已具备自动衔接能力。

### B-05｜演示与成功定义

【提案】用虚构客户岚汀计算的两 die 样例演示一次自动排序，十分钟内选出一个方案即算成功；这个十分钟是演示目标，没有测量。工程组认为无需保留落选方案的完整来源；只导出获胜方案会让接收方更省事。材料没有说明误选成本，也没有证据证明“选得快”能代表研发可采用。

### B-06｜范围和风险

【工程主张】首版不做 RTL 综合、die 内布局布线、详细多物理场求解或 signoff。提案中的双向连接器是否已经过大，需要产品决定。温度假值可能掩盖缺项，排序可能掩盖冲突，格式看似完整也不能证明物理可行。工程组愿意被反证；如果无法证明自动推荐优于解释性对比，可否决该提案。

### B-07｜待澄清

【未知】谁批准首版用户？试用是探索划分还是接收已有实现？输入缺项要部分工作还是整单退回？“实现就绪”谁签字、涵盖什么证据？总分权重与客户决策有什么联系？目前没有答案，也没有实测收益。请研究团队列出最少必要问题和可推翻建议的例子，不要因为本稿版本号更高就默认采用。
